# 路由机制详解：确定性关键词路由全解剖

> 2026-08-24 · 设计窗口产出（skill_router.py 284 行 + skill_catalog.py 匹配原语逐行核实）

---

## 一、一句话定性

**是关键词匹配，而且是最朴素的「子串包含」判断——连正则都没用，就是 Python 的 `in` 运算符。** 路由器不让模型猜：纯代码按固定优先级判定，毫秒级、零方差、每次同样输入必得同样结果。

## 二、匹配原语：只有两个函数（skill_catalog.py）

```python
def match_any_keywords(text, keywords):
    return [k for k in keywords if k in text]
    # 语义：关键词列表里任何一个「子串」出现在问题里 → 命中
    # 例：keywords=["用电户与配变","户变关系"]，text="所有用电户与配变户变关系"
    #     → "用电户与配变" in text ✓ 命中

def match_all_groups(text, groups):
    # 语义：groups 是「组」的列表，每一组内所有词都必须同时出现在问题里才算该组命中
    # 例：groups=[["用电户","配变"],["负载率","过载"]]
    #     text="用电户和配变的关联" → 第1组全中 ✓；text="台区负载率过载分析" → 第2组全中 ✓
```

**三个精确性质**（容易想当然的地方）：
1. **大小写敏感**："SQL" 能匹配、"sql" 不能（中文触发词无此困扰，英文触发词要小心）；
2. **无词边界**：「户变」能命中「户变关系」也能命中「非户变状态」——子串匹配天然宽进；
3. **无序性**：all_groups 只要求都在句中出现，不管先后和距离。

## 三、触发词从哪来：SKILL.md frontmatter

每个场景 SKILL.md 头部的 `x_tupu.triggers` 声明两级触发：

```yaml
triggers:
  any: ["用电户与配变", "户变关系", "配变户变"]        # 任一子串出现即场景命中
  all_groups:
    - ["用电户", "变压器"]                            # 组内全部出现也算命中
steps:
  - id: relationship
    triggers: {any: ["户变关系", "关联"]}             # 步骤级再选一步
  - id: overload
    triggers: {any: ["重载", "过载", "负载率"]}
```

目录加载时（SkillCatalog）读所有启用技能的触发词表；路由时逐个技能比对。

## 四、六级优先级逐级解剖（源码注释声明 6 级，主流程走 1→2→3→4）

### P1 连续上下文沿用（_route_confirmed_context, :109-145）
```
条件：checkpoint 里有 last_skill+last_step（上一题走过场景）
      AND 上轮技能仍启用、步骤仍存在
      AND 本轮问题里【没有】任何新的场景触发词
动作：直接沿用上轮场景+步骤，scope 也继承（客户名集合/承诺）
关键规则：本轮一旦出现新触发词 → 新场景胜出，放弃沿用（:122-124）
例子：上轮问「所有用电户与配变户变关系」，本轮问「那上个月的呢」
     → 「那上个月的呢」不含任何触发词 → 沿用户变关系场景
```

### P2 场景命中（_route_scenario → _select_step, :163-221)
```
遍历所有启用技能 → match_any_keywords 或 match_all_groups 任一命中 → 收集 hits
恰好 1 个命中 → 进入步骤选择：
    依次用每个 step 的 triggers 再比一遍 → 命中的步骤入选
    全都不中 → 取第一个步骤兜底（:202-204）
产出：scenario 契约（模板强校验/引擎锁/输出模式全套绑定）
matched_rules 记录证据：「triggers.any: 用电户与配变」——审计可回放
```

### P3 澄清（:171-179）
```
≥2 个场景同时命中 → 不猜。返回 candidates 列表（skill_id+描述），
前端出澄清卡让用户选。用户选定后以「已确认上下文」身份重新进入（下次走 P1）。
```

### P4 generic 兜底 + 两项附属判定（_route_generic, :252-267）
```
未命中任何场景 → 低权限只读通用契约。
附赠两次纯规则意图扫描（委托 intent_classifier 单模块，批6-R2 已收拢）：
① detect_aggregate_intent：命中「分布/占比/构成」类词 → 契约挂 aggregate_intent
   （追加 GROUP BY 指令+结果层硬校验）；「数量/总数」不算分布，不挂
② detect_vague_intent：含模糊词（情况/怎么样/如何/分析一下…）
   且无明确查询词（数量/清单/排序…）→ clarify_required=True
   （契约收敛为空工具集，模型只能反问一句澄清，不许乱查）
注意：这两个判定只「修饰」generic 契约，不改变 route_type 本身。
```

（P5 fallback 与 P4 等价仅标记不同；P6 reject 用于命中禁止场景，主链路少触发。）

## 五、四个真实问题走一遍

| 问题 | 走到哪级 | 为什么 |
|---|---|---|
| 「所有用电户与配变户变关系」 | P2 场景命中 | 「用电户与配变」是问题子串 → distribution-overload 命中 → 步骤级「户变关系/关联」选中 relationship |
| 「统计用电客户数量」 | P4 generic | 不含任何场景触发子串；「数量」不在聚合词表也不在模糊词表 → 純 generic |
| 「那上个月呢」（上轮=户变关系） | P1 沿用 | 本轮无新触发词 → 继承上轮场景+客户范围 |
| 「各台区负载率分布和户变关系」 | P3 澄清 | 「负载率」命中 overload、「户变关系」命中 relationship → 双命中出卡 |

## 六、为什么这么设计（设计要点）

1. **确定性三收益**：同话同路（金标 eval 可复现）、权限不由采样决定（安全）、毫秒零成本；
2. **全程留证**：RouteResult 带 matched_rules/route_reason/confidence="deterministic"，每问写治理账 record_route——答错可以回放到「是哪个词把它带进了哪条路」；
3. **失败方向是安全的**：匹配不上只会落到权限更小的 generic（只读+17 工具），绝不会落到大权限；
4. **澄清优于猜测**：双命中不仲裁而是交还用户——把歧义显式化。

## 七、已知弱点（诚实清单，治理已在批6）

| 弱点 | 实例 | 缓解 |
|---|---|---|
| 措辞敏感 | 「总数」稳过、「数量」曾漏（无场景覆盖时落 generic） | 触发词变体组守护+示例直通降低路由重要性 |
| 维护成本 | 新场景必须人工维护 triggers 词表 | 发布门槛：triggers 变更→金标 eval 全量 |
| 大小写/边界盲区 | 英文触发词大小写敏感；否定前缀不识别（「不要户变关系」也命中！） | 登记待办：否定模式检测（低成本正则升级可选） |
| 双命中只能澄清 | 长句复合诉求被拆成选择题 | 未来可加权重仲裁（命中词数/位置加权），暂 YAGNI |
| P1 沿用的状态污染 | 错误 last_skill 会跨题传染（预解析实体错挂案例） | 批11-F：来源标注+重置按钮 |

## 八、一句话总结

> 路由 = 「两级触发词子串表 × 固定四级优先级」的纯代码决策器：沿用 > 场景 > 澄清 > 兜底。朴素到只用 `in` 运算符，换来的是可复现、可审计、抗操纵——代价是措辞敏感和维护成本，这组取舍是整个受控平台哲学的缩影。
