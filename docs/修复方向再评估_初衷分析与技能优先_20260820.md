# 修复方向再评估：初衷考古 × 技能优先还是平台优先

> 2026-08-20 · 设计窗口产出（只读分析）
> 输入：用户挑战--「针对四步修复方向，再判断下，当时设计的初衷是什么，不一定非要改设计，可以考虑改技能，但是先要进行分析为什么修复，合理与否」。
> 方法：对冲突各方逐一做设计初衷考古（注释/docstring/代码结构为证），再重新评判四个修复方向的合理性与优先级。
> **结论先行：用户的直觉是对的。原排序（Fix 1 平台根治优先）应推翻，改为技能优先。**

---

## 一、初衷考古：冲突各方各自自洽吗？

### 1.1 validate_sql 的「Select-only」初衷（secure_query_executor.py）

**证据**：
- 文件头设计原则（:9-13）：「设计原则（**评审第二批 + YAGNI**）：只做机械安全校验，不改语义；校验失败返回结构化错误，**不自动修复**」；
- :23-24 注释：「只允许 **SELECT / WITH ... SELECT**（只读查询）」+ `_READONLY_STMT_TYPES = frozenset({"Select"})`；
- :26-29 `_FORBIDDEN_STMT_TYPES`（Insert/Update/Delete/Drop...）吃「禁止」错误语；Union 落在第三分支吃「**不支持**」错误语。

**解读**：
- WITH 是**有意覆盖**的（sqlglot 中 `WITH...SELECT` 根节点就是 Select，所以集合里只有 "Select" 就够）；
- UNION 被拒**不是安全立场**（真禁止会进 `_FORBIDDEN_STMT_TYPES`），而是**当时没有 UNION 用例，按 YAGNI 不实现**；
- 「机械安全校验」的职责边界：多语句/只读/副作用函数/表白名单/强制 LIMIT（DEFAULT_MAX_LIMIT=500），配合「不自动修复」原则--它是一个**保守的、已测试面的**安全底座。

**判定**：该模块自身自洽。UNION 缺失是**未实现**，不是**误设计**。

### 1.2 template_guard 的 UNION 白名单初衷

**证据**：:184-190 `_is_select_only` 显式处理 `exp.Union`：「UNION ALL 合法（模板自身用于合并两段查询），**要求两侧都是 SELECT**」；:330-331 注释「防绕过靠表集合校验（UNION 引入模板外表必然被表集合检查拦截）」。

**解读**：这是**更晚、更具体的已决设计**--P0-2 强牢笼时期，为了让户变关系模板能过结构校验，作者明确推理过 UNION 的安全性（表集合兜底）并写下白名单。**平台对「什么算只读」的定义，在两个模块里不一致，且 template_guard 的定义更完整**（它必须处理真实模板）。

**判定**：该模块自身自洽，且留下了书面决策记录。

### 1.3 scenario_strict 的初衷（结构保真哲学）

**证据**：template_guard :193-204 `_dynamic_fragments`：「提取模板 `-- 【动态】...` 声明式扩展点（**scenario_strict 允许的唯一 AST 变化**）」。

**解读**：平台设计哲学是「**结构冻结（含 UNION 骨架），用户差异通过【动态】WHERE 片段表达**」。户变关系模板里的「【动态】用户指定客户状态/分类/限定客户」正是这个机制的使用。

**推论**：「删掉发电户 UNION 段」是**结构性变化**，在本平台哲学下**本来就不被允许**--不管 validate_sql 修不修。SKILL.md :209「用户只问用电户 -> 只跑对应 UNION 段」承诺了平台不可能兑现的事。

### 1.4 模板作者的初衷（为什么模板里有 UNION）

**证据**：模板头注释 :2「用户问**户变关系/用电户与配变关系/发电户与配变关系**」--一个模板服务三种问法，`客户类型` 列区分；SKILL.md :209 降级规则「只跑对应段」。

**解读**：作者本意是**全模板作为 canonical 答案**（三种问法都执行完整 UNION，靠列区分/答案聚焦），:209 是后来加的「效率优化」性质规则，与单体模板 + strict 模式**没对齐**。且模板只过了 template_guard 的语义校验，**从未真实过一遍 execute 链路**（否则立刻发现 Union 被拒）。

### 1.5 考古总结：谁不自洽？

| 层 | 自洽性 |
|---|---|
| validate_sql（Select-only，YAGNI 未实现 UNION） | ✅ 自洽 |
| template_guard（UNION 白名单，书面决策） | ✅ 自洽 |
| scenario_strict（结构冻结 + 动态片段） | ✅ 自洽 |
| **SKILL.md :209（承诺结构性删段）× 单体 UNION 模板 × strict 模式** | ❌ **三方互斥，矛盾在技能层** |

**真正的缺陷定位是技能编写层的不一致**，平台各层各自自洽。这直接支持「改技能优先于改平台」。

## 二、四个修复方向的逐项再评判

### Fix 1（validate_sql 放行 UNION）——合理但非首选，推迟

- **初衷对齐性**：与 template_guard 的既定决策对齐，属「补齐已决决策」而非「改设计」--这个方向本身没错；
- **反对现在做的理由**：
  1. **YAGNI**：当前只有 1 个模板受益；为一个技能扩展 4 条执行路径共用的安全核心，爆炸半径不成比例；
  2. **工程风险**：`_ensure_limit` 的强制 LIMIT 语义需在 Union 根上重新保证（LIMIT 加在哪个分支/最外层）；
  3. **顺带发现的潜在冲突**：`DEFAULT_MAX_LIMIT=500` 强制 LIMIT 与系统提示词「row_count 就是全部数量」的承诺矛盾（全量户变关系 >500 行会被**静默截断**；测试数据小未暴露，普通 SELECT 同样带此隐患）。放行 UNION 前必须先回答「全量语义查询要不要豁免 LIMIT」--这是新设计决策，不是纯补齐；
- **判定**：**推迟**。仅当「双类型/泛问法合一表」被证实为真实需求时做，且必须一并回答 LIMIT 豁免问题。

### Fix 2（改技能：变体模板 + 修 :209）——首选，P0 止血

- **平台早已支持**：步骤 `templates` 是列表，precheck 遍历**命中任一即过**（overload 步骤生产中已列两个模板）--加变体**零平台改动**；
- **完全符合平台哲学**：单段变体（`WITH 台区配变 AS (...) SELECT 用电户段`）根节点是 Select+WITH（validate_sql :23 注释明示覆盖），模板匹配 + 安全校验**双通过**；
- **修正 :209 语义**：「用户只问用电户 -> **选用电户变体模板**」而非「删段」--把不可兑现的结构性承诺改为可兑现的模板选择；
- **立竿见影**：本问题（「所有**用电户**与配变」）模型第一次就会选对变体，直接通过；日志里模型的第一次尝试（只跑用电户段）本来就是语义正确的，被 strict 拦下纯属模板缺变体；
- **代价**：变体间 JOIN 链/CTE 重复（技能维护成本，SKILL.md 注释标注同源即可）；
- **诚实披露局限**：双类型问法（「用电户和发电户的户变关系」）与泛问法（「所有户变关系」要全量）仍只有 UNION 模板可用，仍死锁--这部分的出路要么 Fix 1，要么技能层接受「泛问法按主类型变体走+答案说明」。
- **判定**：**首选**。

### Fix 3（错误分类 + fail-fast）——无条件做，属补全而非改设计

- **初衷对齐性**：错误分类学六类的初衷是「按可恢复性路由纠错」，全是引擎层错误（模型可改 SQL 重试）；安全校验拒绝是「层间裁决不一致」--**模型无错、不可自愈**，纠错循环「上限 2 次可自愈」的假设被打破，5 分钟超时纯属烧 token；
- **独立性**：就算 Fix 2 修了死锁，未来任何「模板守卫放行/执行层拒绝」的新形态（层间不一致是结构性风险，不是一次性事件）都靠它兜底；
- **判定**：**做**。分类学覆盖全部失败来源本就是其设计初衷，这是补全。

### Fix 4（金标 + 冒烟 + 单测锁定）——无条件做，带一个关键技巧

- **逃逸根因**：金标 5 条无 UNION 形态；技能模板从未真实过 execute 链路；
- **关键技巧**：给 validate_sql 加一条**「当前拒绝 Union 根」的锁定单测**--把「未实现」显性化为「已定义的行为」。未来任何人放行 UNION（Fix 1）必须**显式改这条测试**，防止语义无声漂移；这也等于给推迟的 Fix 1 留了明确的翻转锚点；
- **金标用例设计**（配合 Fix 2）：加「用电户与配变户变关系」单段变体用例（走通全链）；UNION 全量行为的去留随 Fix 1 决策；
- **技能作者流程补一条**（治逃逸本源）：**模板发布前必须真实过一遍 execute 链路**（只过 template_guard 语义校验不算数）--加入技能编写 checklist/发布清单。
- **判定**：**做**。

## 三、修正后的修复决策（推翻原排序）

| 序 | 动作 | 改动层 | 性质 | 解锁什么 |
|---|---|---|---|---|
| 1（P0 止血） | Fix 2：加用电户/发电户单段变体模板 + :209 改为「选变体」 | **技能层**（零平台改动） | 内容修正 | 本问题及一切单类型问法立即通 |
| 2（制度防御） | Fix 3：错误分类学 +SECURITY_VALIDATION + 模板忠实仍被拒不重试直接失败卡 | 平台层（小） | 设计补全 | 层间不一致不再烧 5 分钟 token |
| 3（回归防线） | Fix 4：金标单段用例 + validate_sql「拒绝 Union」锁定单测 + 技能模板过链路 checklist | 测试层 | 防线 | 此类缺陷不再逃逸；Fix 1 有翻转锚点 |
| 4（按需） | Fix 1：validate_sql 放行 UNION + LIMIT 豁免决策 | 平台层（安全核心） | 设计补齐（推迟） | 仅当双类型/泛问法合一表被证实为真实需求 |

**为什么这个顺序对**：
1. 缺陷在技能层（三方互斥矛盾），先修矛盾源头而不是修被矛盾撞击的平台；
2. 平台改动成本/风险（安全核心、4 路径、LIMIT 语义）与当前收益（1 个模板）不成比例--工作区原则第 1 条「真的需要吗」；
3. 顺序 1-3 全部做完后，Fix 1 的真实需求会自然浮出或消失（用户实际问不问双类型合一），届时决策有据。

## 四、遗留风险登记（修复后仍存在的，诚实登记）

| 风险 | 说明 | 处置 |
|---|---|---|
| 双类型/泛问法合一表仍死锁 | Fix 2 不解决全量 UNION 执行 | 观察真实问法频率；证实需求后启 Fix 1 |
| 强制 LIMIT 500 vs「row_count 就是全部数量」 | 全量语义查询（所有/全部类）超 500 行被静默截断；当前测试数据小未暴露 | 独立议题登记：全量查询 LIMIT 豁免或显式「已截断」披露，随 Fix 1 一并决策 |
| 变体模板维护成本 | 3 个变体 JOIN 链重复，schema 漂移要同步改多处 | SKILL.md 注释标注同源关系；金标覆盖变体用例守护 |
| skill_runnable 等其他 SQL 通道 | 若存在不经 validate_sql 的执行路径，UNION 白名单与拒绝语义不一致可能还有第二现场 | 建议做一次「全 SQL 执行通道盘点」（本次已盘点 4 个 execute 工具，均走 validate_sql） |

## 五、一句话结论

**当初的设计各自都没错**：validate_sql 是 YAGNI 的机械安全底座（UNION 属未实现），template_guard 是有书面决策的白名单（UNION 属已决合法），scenario_strict 是结构冻结哲学（删段本就不可表达）；**错的是技能层把三者拧在一起**（单体 UNION 模板 + 承诺删段的降级规则 + strict 模式）。所以修复顺序应当**技能优先**：加单段变体模板解锁当前问题（零平台改动），平台侧只做错误分类补全和回归锁定；validate_sql 放行 UNION 推迟到「双类型合一表」需求被证实时，且届时必须一并回答 LIMIT 500 与全量语义的冲突。
