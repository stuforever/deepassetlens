# 剧本定位提速设计（历史缓存 + 批量定位 + 契约预解析）

> **批准记录（2026-09-09）**：头脑风暴会话定调三件套——①实体查找持久化历史缓存（避免每次一点点向量查）；②一次查完所有实体（不一个个查再替换）；③契约服务预先解析。外加 SKILL.md 文案兜底（A1）。用户已批准本设计。
> **取证基线**：git HEAD `5358632`；同日四个实测 run（§九）；后端 28000 运行中。

## 一、定位与背景（实测根因）

「配电变压器重过载分析」（RUN B）总耗时 **263s**，其中定位环节 **151s（57%）**：10 次定位工具 66s + 9 轮 LLM 判断 88s。根因三层：

1. **剧本声明与模型行为脱节**：distribution-overload 的 SKILL.md `entity_aliases`（L53-65）已将 **9/9 占位符的物理表名全量预解析**，L156 明示「只调一次批量接口，不要逐表查询」、L164「直接使用模板即可」——但模型仍逐个 search_entities 验证（批13-M「定位优先」纪律压过了剧本直用指令）。
2. **平台规则强制串行**：决策门一轮单工具规则（`decision_gate.py` L165-167）——RUN C 实测模型一轮发 6 个并行定位被全数拒绝，被迫改串行 10 轮。
3. **每次未命中都走向量召回**：`kg_action_handlers.py` L373-379——keyword 非精确命中→同义词扩展→**逐 variant 串行 embedding 网关调用**→Qdrant（首查 7 路=31.2s）；entity_code 精确查 0 命中同样触发 2.4s 网关调用。

`skill_policy.py` L204-206 注释已预留语义：「直通与**预解析契约**不标记 locate_first，天然豁免」——本设计把该「预解析契约」做实。

## 二、目标与非目标

**目标**：① scenario_strict 剧本命中且 aliases 全覆盖 → 定位 10 轮→**0 轮**（263s→~110s）；② 有缺口 → **1 轮批量**（一次 embedding ≈3-5s）；③ 首次 keyword 向量召回 7 路串行 31s→一次网关调用 ~3s；④ 重复实体查询 → **ms 级缓存命中**。

**非目标**：不动决策门一轮单工具规则（可审计性基石）；不动 generic 流定位纪律；不解决 embedding 网关本身延迟（RUN A/B 同题首轮 62s vs 19s 的波动不在范围）；金标种子（用户未选）。

## 三、设计件（四件，互相兜底）

### 件① 持久化历史缓存：新表 `kg_entity_lookup_cache`（第 84 张表）

| 列 | 类型 | 说明 |
|---|---|---|
| id | String(36) PK | uuid |
| query_key | String(255) 唯一索引 | 归一化查询（NFKC/小写/去空白）；keyword 或 entity_code |
| query_kind | String(20) | keyword \| entity_code |
| result_json | JSON | 命中结果（实体+字段，与 search_entities 返回同构） |
| hit_count | Integer 默认 1 | 命中计数（观测） |
| last_used_at / created_at / updated_at | DateTime | 末次使用/创建/更新 |

- **查**：先查缓存，命中直接返回（**零向量零重查**），bump hit_count/last_used_at；未命中→走件②→回写。
- **失效**：实体建模/元数据写操作（entity_relation_manage、metadata_service 写路径、字段导入）→**全表清空**（DELETE，重建代价=下次一次批量查；写操作低频；同 engine_health invalidate 模式）。
- **降级**：缓存表读写失败→降级直查+warning 日志——**缓存是加速件，不是正确性件**。
- **落点**：ORM 类加 `models/base.py`（与 `kg_entities` L74 同文件）；init_db create_all 自动建（幂等）。

### 件② 批量定位工具：kg_api 新动作 `search_entities_batch`（动作 16→17）

- **契约**：输入 `{"keywords": [...], "entity_codes": [...]}`，输出逐项结果数组（每项与 search_entities 单查返回同构，含 hit/miss 状态）。
- **内部三层合并**：精确+LIKE 查询**合并成一批 SQL 一次连接查回**；未命中的 keywords 收拢后**一次 embedding 网关调用（数组入参）**——替代现状逐 variant 串行（这是 31s 的来源）+一次 Qdrant 批检索；与件①共享缓存层（先批量查缓存，miss 项才走网关）。
- **守卫语义**：定位预算计 **1 次** locate 调用（`_locate_budget_check` L219 现行预算口径下更省）；不入 scope_gated（只读定位类）；决策门一轮单工具规则天然兼容（本工具就是单个工具）。
- **注册面**：`init_db.py` 工具种子清单（L160 同簇）、scenario 剧本 SKILL.md 各步骤 `allowed_tools` 增列、工具清单 risk_level。

### 件③ 契约预解析：`query_contract.py` 组装段

- **触发三查**：`route_type=scenario` + `template_mode=scenario_strict` + 模板 ⟦占位符⟧ 集合 ⊆ `entity_aliases`（差集为空）。
- **全覆盖路径**：用现成 `resolve_entity_aliases()`（`template_guard.py` L397）服务端替换模板文本；guidance 注入【已解析表名清单（含 catalog 前缀）+ 替换后模板 + 「模板已预解析，直接使用，无需定位确认」指令】；9 实体写入 `_runtime.confirmed_entities`（字段现成）；**locate_first 置 False**（对齐 skill_policy L204-206 预解析契约语义，locate_order_warn 天然豁免）。
- **缺口路径**：下发【缺口清单+原始模板】+ guidance 指令「一次 `search_entities_batch` 补齐缺口」——模型一轮批完，不再逐个。
- **模板读取**：按文件指纹缓存（stat mtime_ns+size，批15 件2 同款语义——改 SKILL.md/模板不重启下次生效）。
- **降级**：模板读失败/占位符正则异常→现状流程（原始模板注入）+warning，不阻断。

### 件④ SKILL.md 文案兜底（A1）

- 定位顺序块（L148-152）首加「⓪ **scenario_strict 剧本且 entity_aliases 覆盖模板全部 ⟦⟧**：直接使用+一次 batch_entity_source_mode，跳过逐个定位（服务端已预解析注入）；仅当契约提示有未覆盖占位符时才走 ①-④」。
- 「禁止凭 entity_aliases 猜表」（L150）加限定：「（本条适用于 generic 流与未预解析场景）」。
- 修订范围：全部 scenario_strict 且含 entity_aliases 的剧本（skill_catalog 扫描得出），不止 distribution-overload。

## 四、数据流（前后对比）

```
现状（RUN B 实测 263s）：
  契约(原始⟦⟧模板) → 模型逐个定位×9(工具66s+LLM轮88s) → batch源模式(2.6s) → SQL构造(51s) → Doris(3.7s) → 终答(35s)

设计后（目标 ~110s）：
  契约组装：
    ├─ 全覆盖 → 下发【已替换模板+表名清单+confirmed_entities+locate_first=False】
    │     → 模型直接 batch源模式(1轮2.6s) → SQL构造 → Doris → 终答        [件③主路径]
    └─ 有缺口 → 下发【缺口清单+原始模板】
          → 模型一次 search_entities_batch(1轮，缓存优先，miss 一次 embedding)  [件②兜底]
  SKILL.md ⓪ 文案                                                            [件④兜底]
  重复实体查询：kg_entity_lookup_cache 命中即返                                [件①]
```

## 五、错误处理

| 面 | 行为 |
|---|---|
| 模板文件读失败/占位符正则异常 | 降级现状流程+warning（不阻断） |
| aliases 值缺 catalog 前缀 | 不拦截（三段名守卫既有校验兜底） |
| 预解析后执行报 Unknown table | 现有兜底链不变（execute_sql 降级一次重试） |
| 缓存表读写失败 | 降级直查+warning（加速件非正确性件） |
| 批量 embedding 网关调用失败 | 降级逐个串行（保可用性，恢复现状行为） |
| batch 工具部分项未命中 | 逐项 hit/miss 返回，模型仅对 miss 走后续定位顺序 |
| 缓存与元数据漂移 | 实体写操作全表清空（O(1) 触发）+ hit_count/last_used_at 观测 |

## 六、测试与验收

**单测**：预解析三态（全覆盖/缺口/无模板）；缓存命中/全表清空失效/回写；batch 合并查询；**embedding 单次网关调用断言**（mock 网关计数=1）；confirmed_entities 与 locate_first=False 联动。

**e2e（Playwright headless 串行，唯一验收口径）**：
1. 重跑「配电变压器重过载分析」——断言：run_events 中 search_entities 单查次数≤1；`.ant-table` 82 行结果不变；总时长 ≤150s（较 263s 显著下降，网关波动留余量）；
2. **二次运行断言走缓存**：同关键词查询无向量召回耗时（工具耗时 ms 级）；
3. 回归：金标直通（「统计重过载台区数量」1.5s 路径）不受影响；generic 概念题（「什么是变压器」）定位行为不回归；pytest 全量绿不下降。

**grep 判据**（实施后可复验）：`grep -r "search_entities_batch" backend/app` 命中 kg_action_handlers/init_db/SKILL.md；`grep -r "kg_entity_lookup_cache" backend/app/models` 命中 ORM；`grep -rn "locate_first = False\|locate_first=False" backend/app/services/query_contract.py` 命中预解析分支。

## 七、风险与诚实账

1. **模型仍自发定位**：件③注入指令 + confirmed_entities + 件④文案 + 件②批量工具，四层兜底，最坏 1 轮批完；
2. **首轮 LLM 网关波动**（RUN A 62s vs RUN B 19s 同题）：不在本设计范围，~110s 为典型值非保证；
3. **表数与动作数口径变化**：83→84 表、kg_api 动作 16→17——套例回写见 §八；
4. **aliases 与元数据漂移**：batch_entity_source_mode 逐表返回模式已覆盖存在性核验，不另加校验（YAGNI）。
