# M15 知识库与工单 设计规格（金标准）

> 套件：DeepAssetLens 全量金标准 M15（总纲见 m00）。as-if-greenfield 视角。
> 取证基线：HEAD `0d67f4c`（2026-09-06）。本模块改动须先过两技能管线并回写本 spec 状态。

## 一、模块定位

两个轻域打包：**自定义知识库（RAG）**——上传文档→分块向量化→检索增强，每库一个 Qdrant collection；**业务工单查询 API**——供 n8n 跨 API 编排的只读 JSON 接口。二者无业务耦合，仅同属轻量辅助面。

**边界**：向量库客户端与嵌入函数复用 M09（本模块是消费方）；知识库管理界面寄宿在向量管理页（M09 前端锚点）；问数侧 knowledge 答案类型消费方在 M16/M18。

## 二、知识库 RAG（kg_knowledge_base + kg_knowledge_document）

**模型设计**（models/knowledge_base.py 文件头契约）：
- 复用 Qdrant（TupuQdrantClient）存向量——**每个 KB 一个 collection**（collection_name unique：`kb_` 前缀 + id 去连字符）；
- 复用 semantic_retrieval.embed_texts 做嵌入（M09）；
- **文档原文存磁盘** `backend/data/kb_documents/{kb_id}/`（storage_dir=kb_id）——库表只存元数据与路径。

**KnowledgeBase**：name(index)/description/collection_name unique/storage_dir/**doc_count/vector_count 计数列**/status(ready|processing|error)/error_msg；documents 级联删除（cascade all,delete-orphan）。
**KnowledgeDocument**：filename/file_path(磁盘路径)/file_size/**chunk_count**/status(pending|vectorized|error)/error_msg。

**状态机**：KB：ready⇄processing（vectorize 期间）→error；Doc：pending→(vectorize)→vectorized|error。

**端点**（8 个，prefix /knowledge-bases）：
| 端点 | 语义 |
|---|---|
| GET /（列表） | 库清单（含计数与状态） |
| POST /（创建） | 建库（collection + 磁盘目录） |
| GET /{kb_id} | 详情（含文档清单） |
| DELETE /{kb_id} | 删库（级联文档 + 删 collection + 删磁盘目录） |
| POST /{kb_id}/upload | 上传文档（multipart，落磁盘，doc pending） |
| DELETE /{kb_id}/documents/{doc_id} | 删文档（删文件 + 删该 doc 向量） |
| POST /{kb_id}/vectorize | 全库向量化（分块→嵌入→upsert；KB processing 态；更新计数） |
| POST /{kb_id}/search | 检索（query+top_k→Qdrant 相似→回原文块） |

**前端**：向量管理页知识库区（VectorManagePanel L164-340：list/create/delete/upload/vectorize/deleteDoc/search 全消费）。
**问数消费**：conversation answer_type 含 `knowledge`（conversation/types.ts L61）——知识块可作为问数答案素材。

## 三、业务工单 API（biz_work_order）

> 文件头契约（L1）：「供 n8n 跨 API 编排用」——外部自动化编排的只读数据面。

- **无 ORM 模型**：裸 SQL（text()）直查 MySQL `biz_work_order` 表（该表不在 83 表模型内——业务数据表，非平台元数据表）；
- **两端点**（prefix /api/v1/biz_work_order）：GET /list?limit=100（字段白名单：work_order_id/cust_id/work_order_type/apply_date/expect_finish_date/status/apply_capacity_kw/fee/handler/remark；返回 {count,data,source:"MySQL tupu"}）；GET /{cust_id}（按客户查工单）；
- **无前端消费**（外部 n8n 专用）；只读无写面。

## 四、设计原则（本模块特有）

1. **复用不自建**：RAG 三件基础设施（向量库/嵌入/客户端）全部复用 M09——本模块只做编排（文档→分块→嵌入→检索）；
2. **原文在磁盘、向量在 Qdrant、元数据在 MySQL**——三存各司其职，删库三处同步清（目录+collection+行）；
3. **计数列冗余可重建**：doc_count/vector_count 是缓存性质（vectorize 后更新），对账以实际为准；
4. **外部 API 只读白名单**：工单 API 字段白名单 SELECT——不暴露 `SELECT *`，无写面（n8n 场景够用）；
5. **级联一致**：删库 cascade 文档行；删文档先删向量再删文件（顺序：先可重建的）。

## 五、验收标准

1. 建库→上传→vectorize→search 全链：chunk 计数>0；检索命中回原文段；
2. 状态机：vectorize 中 KB=processing（并发防护）；失败 doc=error+error_msg 不拖垮整库；
3. 删库三处清理（Qdrant collection/磁盘目录/两表行）；删文档向量与文件同步清；
4. 重复 vectorize 幂等（已 vectorized 文档跳过或按 hash 重算——以实现为准登记）；
5. 工单 API：list limit 生效；cust_id 过滤正确；字段白名单不含表外列；source 标注；
6. 问数 knowledge 答案类型联测（M16）。

## 六、风险与偏差登记

| 项 | 说明 |
|---|---|
| 文档解析格式面 | upload 支持的文件格式取决于 vectorize 实现（pdf/docx 等解析依赖）——支持清单在实现层登记 |
| vectorize 同步执行 | 全库向量化是同步端点（大文档阻塞）——量大时改任务队列（YAGNI 登记） |
| 工单裸 SQL | 无 ORM/无索引保障（依赖业务表自身）——外部 n8n 限流责任在使用方 |
