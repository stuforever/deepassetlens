# M07 映射与 API 编排 设计规格（金标准）

> 套件：DeepAssetLens 全量金标准 M07（总纲见 m00）。as-if-greenfield 视角。
> 取证基线：HEAD `0d67f4c`（2026-09-06）。本模块改动须先两技能管线并回写本 spec 状态。

## 一、模块定位

数据资产域的**整合层**：实体↔源表映射规则（多源物理表整合）、多源 API 编排（DuckDB 联邦虚拟表——配置驱动零改代码）、对象级 API 映射（实体整合多 API）、多源 SQL 整合（含 LLM 辅助重写）、实体溯源路径（实体→映射→源表）。

**边界**：源表登记归 M06；实体与 source_mode 三模式归 M03/M04（本模块是三模式的数据整合实现面）；DuckDB 执行引擎归 M21；SmartJoinReview 为预留表（见 §七）。

## 三、实体映射规则（EntityMappingRule，物理表模式）

**模型**（L143-153）：name / **source_table_ids JSON**（多源表）/ **entity_ids JSON**（多实体）/ **field_mappings JSON**（字段映射）/ **is_advanced_sql** / **sql_content**（高级模式整段 SQL）。

**语义**：一条规则=「若干源表 → 若干实体」的字段级映射；高级模式直接给 SQL 整合逻辑。**溯源端点** /lineage/{entity_id}（L317-376）：实体→匹配规则（entity_ids JSON 包含判断，**UUID 32/36 位连字符兼容** L331-340）→三类源表聚合，输出 rule/mapping_logic/sql_fragment/source_table 链路——这是当前已实现的实体级血缘（前端智能溯源大盘为占位，M04 §五）。

## 四、API 编排（ApiEndpoint，DuckDB 联邦虚拟表）

**模型**（L822-840，docstring：「多源API映射端点（DuckDB联邦查询用，**配置驱动，加新API零改代码**）」）：

| 列组 | 列 | 说明 |
|---|---|---|
| 标识 | name / **table_name unique**（DuckDB 虚拟表名，SQL 里引用）/ entity_id FK(可空) | |
| 请求 | api_url / method(GET/POST) / headers JSON / **body_template**（如 ES _search 的 query DSL）/ params JSON（过滤参数列映射 map_to） | |
| 响应 | **columns JSON**（name/json_path/type/dtype——返回列契约）/ data_path（响应提取路径） | |
| 运行 | **cache_ttl_seconds**（批2：内存缓存 TTL，0=禁用）/ **pagination JSON**（page_param/size_param/page_size/max_pages，批2）/ **run_config JSON**（P3：rate_limit_min_interval_ms / circuit_threshold / circuit_open_seconds——限流+熔断） | |

**端点**：CRUD 六端点 + `GET /api-endpoints/tables`（虚拟表清单）+ `POST /api-endpoints/execute`（直接执行）+ `POST /api-endpoints/{id}/test`（连通/契约测试）。

## 五、对象 API 映射（EntityApiMapping）与多源 SQL 整合

**EntityApiMapping**（L843-853，对齐 EntityMappingRule 模式）：entity_id / **api_endpoint_ids JSON**（虚拟表资源池）/ field_mappings JSON / **pseudo_sql（伪逻辑 SQL，不含 WHERE——LLM 调用时动态加）**。端点：CRUD + `POST /execute`（按映射整合执行）+ `POST /{id}/verify`（校验映射与端点契约一致）。

**integration-sql 三端点**（多源 SQL 整合模式，source_mode=sql_integration 实体）：
- `POST /integration-sql/verify`：语法/引用表校验；
- `POST /integration-sql/ai-rewrite`：**LLM 辅助重写**（产出建议 SQL，人工确认后入库——LLM 只重写不落库）；
- `POST /integration-sql/execute`：受控执行（走 M21 引擎执行链）。

**数据预览**：`POST /entity-data/{entity_code}`（按实体取数）+ `GET /entity-preview/{entity_id}`（映射管理页预览，M04 数据预览弹窗的后端）。

## 六、前端契约

- **MappingManager 三 Tab**（与 M04 source_mode 跳转 tabMap 对齐：physical_table→Tab1 / sql_integration→Tab2 / api_integration→Tab3）；接收 store 的 mappingFilterEntityId（自动过滤当前实体）与 mappingJumpTab（预选 Tab）；
- **ApiMappingTab**：端点配置表单（headers JSON 编辑、body_template、columns 契约编辑）；**HttpEditor**：HTTP 请求编辑器（鉴权配置 bearer/apikey 等——前端编辑态，与后端 ApiEndpoint.headers 对应）。

## 七、预留与现状登记

- **kg_smart_join_reviews**（L235-250：app_type/intent/candidate_payload/confidence/need_manual_review/approved/executed/reviewer——智能 join 候选评审 HITL 工作流设计）：**全仓无消费代码**（仅模型定义）。金标准登记为**预留表**：表结构保留，启用须过设计批次（如问数 join 候选人工评审落地时）。
- kg_source_field_imports 的引用表语义（ref_table_en）与本模块映射互补：字段级血缘素材。

## 八、设计原则（本模块特有）

1. **配置驱动联邦**：新 API 接入=填 ApiEndpoint 配置行（虚拟表+列契约+提取路径），零代码——新增任何「写代码才能接 API」的路径都违反本原则；
2. **伪 SQL 无 WHERE**：pseudo_sql 模板不含 WHERE 子句，过滤条件由调用期动态拼装——模板与用户输入隔离的安全边界；
3. **溯源是推导不是存储**：lineage 从映射规则实时推导（无独立血缘表），单一事实源原则；
4. **LLM 只建议**：ai-rewrite 产出候选 SQL，落库/执行由人确认；
5. **JSON 列宽容解析**：entity_ids/source_table_ids 等历史数据可能是 JSON 字符串或列表（L334-339 双形态解析）——读写两侧都兼容。

## 九、验收标准

1. 映射规则 CRUD + 溯源：32/36 位 UUID 兼容匹配；三源表类型聚合正确；无规则实体返回空链路非 500；
2. ApiEndpoint：配置新端点→/tables 可见→execute 按列契约返回（columns json_path 提取）；test 失败给结构化错误；cache_ttl 生效（重复执行命中缓存，M21 联测）；pagination 翻页取全量；
3. EntityApiMapping：verify 能发现列缺失/类型不匹配；execute 多端点整合；
4. integration-sql：verify 拒绝引用不存在虚拟表；ai-rewrite 返回建议不落库；execute 走安全链；
5. 前端：三 Tab 与 source_mode 跳转对齐；实体过滤联动；预览弹窗数据闭环；
6. 预留表存在且无消费代码（登记一致）。
