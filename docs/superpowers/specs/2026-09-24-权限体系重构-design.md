### 4.2 后端验签改造（provider 抽象，双跑）

`backend/app/core/auth.py` 现状 `_verify_jwt` 硬编码 Authentik（RS256/JWKS 600s 缓存/userinfo 合并）。改造为 provider 表驱动：

```python
AUTH_PROVIDER = os.environ.get("AUTH_PROVIDER", "authentik")   # authentik|supertokens
_PROVIDERS = {
  "authentik":  {"jwks": AUTHENTIK_JWKS_URL, "issuer": AUTHENTIK_ISSUER, "aud": AUTHENTIK_AUDIENCE},
  "supertokens": {"jwks": os.environ.get("SUPERTOKENS_JWKS_URL",
                  "http://127.0.0.1:13567/.well-known/jwks.json"),
                  "issuer": None, "aud": None},   # ST access token 不校验 iss/aud，验签+exp 即可
}
```
> 实施实测（T3，2026-09-25）：Core 9.x 公开 JWKS = **/.well-known/jwks.json**（无需
> api-key、无 recipe 门控）；初稿 `/auth/jwt/jwks.json` 为废弃路径（镜像 "Unknown API"
> 实证）。另 9.3.0 镜像不解析 POSTGRESQL_CONNECTION_URI（连接池落 localhost 默认致
> 启动失败），compose 用显式分项变量（POSTGRESQL_HOST/PORT/USER/PASSWORD/DATABASE_NAME）。
```

- `_verify_jwt(token)`：读 unverified header/claims 的 `iss` 判定来源（含 `api.supertokens.io` 或无 iss → ST 路径），双跑期依次尝试 ST → Authentik，任一通过即放行。
- ST 会话 token 从两处取：`Authorization: Bearer`（前端 axios 注入，沿用现有通道）或 `sAccessToken` cookie（ST web-js SDK 自动管理，兼容 H5）。
- JWKS 缓存结构改为按 provider 分桶（`_JWKS_CACHE[provider]`），TTL/回退语义不变。
- 依赖：`supertokens-python[fastapi]` 仅用于**登录签发与用户 CRUD**（调 Core API），验签仍走自研 JWKS 路径——中间件结构零改动。

### 4.3 用户镜像与 sub 迁移

- ST user id 同为 UUID 但与 Authentik sub 不同。登录 upsert 时按 **email 优先、username 兜底**匹配既有 `auth_users` 行：
  - **匹配前查重**：同 email 多行 → 跳过 + 审计日志告警，人工裁定归属；迁移前 grep 全库 `user_sub|principal_id` 确认三表之外无第四处 sub 键引用。
  - 命中 → 同事务更新该行 `sub` 为新 ST id，**旧值写入新增 `legacy_sub` 列**（String(64) nullable，回滚保险见 §4.5），并同步更新 `auth_user_roles.user_sub`、`auth_resource_acl.principal_id`（principal_type='user'）的引用（两表 FK 无 ON UPDATE CASCADE，显式 UPDATE）。
  - 未命中 → 新建镜像行（现有 upsert 逻辑）。
- 角色来源切换：现状 `_upsert_user` 从 Authentik group claim 映射角色（每次登录覆盖 user_roles）。**双跑期开始（T3 上线）即停 group-claim 覆盖**——authentik 登录同样只做镜像 upsert 不动角色，`auth_user_roles` 自 T3 起即为唯一权威（W2 管理页维护），`GROUP_ROLE_MAP` 整体退役。
- 兜底：无任何角色的用户登录后自动挂 `viewer`（保留现语义）。

> 🛠 R3+R6+R12。**为什么**：①（R3）sub 迁移是同事务改写，回滚 AUTH_PROVIDER=authentik 后旧 token 的 sub 匹配不上已改写的行（authentik 分支按 sub 精确匹配、不按 email），迁移过的用户会失联或产生重复行——`legacy_sub` 列 + authentik 分支兜底匹配顺序（sub → legacy_sub → email）让回滚成为真双向门；②（R6）双跑期 Authentik 登录若仍按 group 覆盖 user_roles，W2 管理页的角色编辑每次登录被冲掉，§4.5 的角色比对永远对不齐——权威必须从双跑第一天就单点；③（R12）email 非唯一键，不查重会静默错绑授权。

### 4.4 登录签发端点与前端

后端新增（`app/api/auth.py` 扩展）：

| 端点 | 说明 |
|---|---|
| `POST /api/v1/auth/session` | body {email,password} → SDK signin → 返回 {access_token, user}；同时写 sAccessToken + sRefreshToken(HttpOnly) cookie |
| `POST /api/v1/auth/session/refresh` | 读 sRefreshToken cookie → SDK refresh_session → 新 access_token（🛠R2） |
| `DELETE /api/v1/auth/session` | 登出（revoke session） |
| `GET /api/v1/auth/config` | 改返回 `{provider:"supertokens", enable_auth}`（不再暴露 Authentik OIDC 端点） |

前端：
- 新登录页 `/login`（自研表单，沿用门户视觉；POST session 后 token 入 axios 默认头 + localStorage，与现状 dev token 通道一致）。
- 移除 `src/auth/oidc.ts` 跳转流（切 supertokens 后删文件）；`services/http.ts` Bearer 拦截器不变。
- 401 处理：拦截器先试 /auth/session/refresh 并重放原请求，失败才统一跳 `/login`（替代现 OIDC authorize 跳转）。

> 🛠 R2 补会话刷新机制（原文缺失）。**为什么**：自研登录页不引 supertokens-web-js，无 SDK 自动刷新；ST access token 默认 1h 有效——不闭环则每小时被踢回 /login，验收 #2"会话刷新"没有实现载体。已否决的替代：调长 access_token_validity（会话窗口放大、安全性差）；嵌 web SDK（新增前端依赖，违背组件极简定调）。

### 4.5 切换与回滚

- 双跑：`AUTH_PROVIDER` 缺省 authentik → 部署 ST 后前端配置切登录页，后端接受两路 token（旧 Authentik 会话不过期不受影响）。
- 比对：双跑期在 `_verify_jwt` 记录两条路径的验签命中日志，抽样核对同一用户两 provider 镜像行的 **sub/legacy_sub 链路正确**（角色不再比对——权威已单点，§4.3 R6）。
- 切换：所有活跃用户改用 ST 登录后（观察窗 3 天），`AUTH_PROVIDER=supertokens`，下 Authentik 4 容器。
- 回滚：env 回退 + authentik 分支按 **sub → legacy_sub → email** 兜底匹配已迁移用户（§4.3 R3），不产生重复行、不丢授权；ST 数据独立成库，互不染指。

> 🛠 R3/R6。**为什么**：原"容器重起 + env 回退即可"与 §4.3 的同事务 sub 改写矛盾（单向门，回滚即失联）；比对项"角色一致"在权威单点后已无意义，改为验签链路核对。

## 6. W3 工具门控

### 6.1 数据模型（零新表 + 一张审计表）

- 权限数据：复用 `auth_resource_acl`，`resource_type='tool'`，`resource_id`=工具注册名（`execute_sql` / `fetch_l1_l2_tree` …），`actions=["execute"]`。
- **TOOL_REGISTRY 全集 = mcp_server 实际注册的工具集（19 件，含 `search_kb`；W5 回挂教学 11 件后 = 30 件）**，单点化到 `permission_vocab.TOOL_REGISTRY`（`query_contract` 改从这里 import 保持兼容），内部三分类：`READONLY_TOOLS` / `EXEC_TOOLS` / `WRITE_TOOLS`。
- 角色默认：`auth_roles.default_permissions` 的 `"tool": ["execute"]` **只覆盖只读类**；细粒度单工具授权走 ACL 行（principal 可为 user 或 role）。
- 工具三分类（映射三态）：
  - 只读类（MCP 注册集 19 件 − 执行类 4 = **15 件，含 `search_kb`**）→ 允许/拒绝二态；
  - 执行类（`EXEC_TOOLS`：execute_sql 等 4 个 execute_*，自 GENERIC 内部单列）→ 需显式授权（角色默认不含，只能 ACL 授予），允许/拒绝；
  - 写类（ABSOLUTE_FORBIDDEN_TOOLS：write_file/edit_file/execute/grep/glob/task）→ v1 维持绝对禁止，数据模型预留 `approval` 动作位，真开放时走"审批"第三态。
- **门控面外声明（v1 不管控，🛠R14，v1.3 修订）**：`read_file` 是 deepagents 框架工具、非 MCP 注册（query_contract.py:48 注释自证），装载/派发两执行点均碰不到，v1 放行不管控。**TUTOR_TOOLS 教学族 11 件 v1.3 起移回面内**——W5（§8）将其重新 MCP 化并纳入门控三分类；在 W5 交付前它们仍由 `dt_agent_orchestrations` 编排承接、门控碰不到（过渡态）。
- 上线种子：执行类 4 件现属 GENERIC 白名单人人可用，转 ACL-only 前给现有活跃角色（viewer 除外）批量补 `resource_type='tool'` 的 execute ACL（admin 一票通过不受影响）。

## 8. W5 教学工具 MCP 化与技能体系融入（v1.3 追加）

### 8.1 现状与唯一阻断点

- 教学 11 件 impl 单源仍在：`learning/tutor_inprocess.py` SPECS 表（name/description/impl 三元组，impl 调 learning_dao/service/tutor_llm/tutor_select，user 由 `memory_runtime.current_user_strict()` 严格解析，fail-closed）。被摘的只是两个"面"：mcp_server 薄包装（⑤R R1）与进程内 twin（tupu_deepagent.py:1029-1031）。
- 当前教学能力由 `dt_agent_orchestrations` 硬编码编排承接（mastery_status 脚本节点、wrong_question_save 确认流）——模型看不到工具面，行为固化在 Python 流程里，这正是要回正道的部分。
- **唯一阻断点（🔴-4 史）**：原 MCP 面走 HTTP SSE 跳数，独立 ASGI 请求 → ContextVar 恒 None → 全落 anonymous 共享桶（ENABLE_AUTH=1 即跨用户泄漏）。回挂必须先解用户上下文跨 MCP 边界传递。

### 8.2 用户上下文跨 MCP 边界传递（🔴-4 解法）

```
tupu_deepagent._build_agent                     mcp_server（/mcp SSE 挂载面）
  MultiServerMCPClient headers ──────────────►  UserContextASGIMiddleware（新，包装 mcp.sse_app()）
    Authorization: Bearer <internal token>        ① 验 internal token（沿用现口径）
    X-Tupu-User: <user_slug>          ──►       ② 取头 → memory_runtime 置 ContextVar
                                                  ③ 缺头 → anonymous；教学工具经
                                                     current_user_strict fail-closed 抛错
```

- 信任级论证：/mcp 面本就凭 `TUPU_INTERNAL_TOKEN` 全通，附加用户头与 Bearer 同信任级，不扩大攻击面；**铁律①不变**——user 绝不进模型可见参数面，只走传输头。
- 加固备选（同任务内实现，成本低）：`X-Tupu-User-Sig = HMAC_SHA256(internal_token, user:ts)` + ±300s 新鲜度校验，防 buggy client 误串用户。v1 默认开启。
- 外部 MCP client（无头）行为不变：教学工具对 anonymous fail-closed，与 ⑥-2a 语义一致；问数 19 件不含用户态数据，不受影响。

**密钥与暴露面管理（v1.4 补强）**：
- `TUPU_INTERNAL_TOKEN`（HMAC 密钥同值复用，不另设第二把）只存 `.env.infra`（与 MySQL/PG 密码同级），**禁进 git、禁下发前端**；前端/浏览器没有任何路径能拿到该头——`/mcp` 面只接受带 internal token 的调用，前端请求一律走后端 API 而非直连 `/mcp`；
- 部署约束：`/mcp` SSE 挂载面与 agent 进程同机（loopback），docker compose 网络内不对外发布端口；若未来跨机部署，加来源 IP 白名单（仅 agent 主机）；
- 轮换：v1 手写流程——改 `.env.infra` 的 token 值 → 重启后端与 mcp 面（同一进程则单重启）；±300s 新鲜度窗口内旧签名自然失效，无需双密钥并行。

### 8.3 回挂与旧面退役

### 8.4 门控三分类更新（30 件）

| 类 | 构成 | 判定 |
|---|---|---|
| READONLY（22） | 现 15 + 教学读面 7：fsrs_due / mastery_query / wrong_question_query / select_exercises / analyze_wrong_questions / grade_answer / generate_practice（后两件 LLM 臂、无 DB 写，数据面只读，落审计） | 角色默认 tool:execute 覆盖，允许/拒绝 |

**EXEC 确认层时序（v1.4 补强，钉死责任边界）**——确认不是编排层自觉，是**工具执行层强制**：

```
模型调用 execute_*/教学写 4 件
  → 工具体①（预检臂）：不执行写，返回 {status:"pending_confirmation", summary:"将写入错题本：xxx"}
  → 编排/agent 层渲染确认卡（写前确认 UI，产品语义不变）
  → 用户确认 → 工具体②（执行臂，携 confirm_token=HMAC(tool,args,user,ts)）才真正写
  → 全程双审计（预检一次、执行一次）
```

铁律：**任何路径（技能直调/agent 直调/编排调用）都绕不过①→②两段**——无 confirm_token 的执行臂直接 fail-closed。确认卡 UI 只是②的触发器，不承担安全职责；安全由工具层的 confirm_token 校验承担。
