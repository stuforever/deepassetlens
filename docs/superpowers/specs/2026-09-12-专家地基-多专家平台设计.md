## 一、定位与背景

**总纲**：「一个底座，多个专家，各自入口，共享基建」——专家不是平台子页面，是平台孵化的独立产品；平台收敛通用件（模型/知识库/用户/审计/守卫），专家只声明差异（提示词/工具面/技能组/知识源/记忆策略/入口）。

**本子项目是九项建设的地基（P0）**：专家配置卡实体 + 多入口路由 + 装配按卡分发 + 双维隔离 + 关停判据。其余子项目（②记忆插槽 ③LLM 目录化 ④文档 KB ⑤教学引擎 MCP 化 ⑥远期）全部挂在本地基之上。

**核心张力与解法**：逻辑一体化（共享底座/统一治理）vs 入口解耦（专家独立/关停无感）。解法=专家的物理边界可枚举（卡行 + URL 前缀组 + 路由组），关停=卡 `enabled=false`，判据写成测试（验收 B 组）。

**专家品类**（用户修正，2026-09-12）：专家不限于问答——还有管理专家（图谱生成/文档初始化）、生成专家（教案）、录入专家（错题录入）、分析专家（学情）。品类落在两处：`entry_kind` 判别壳形态（①期仅 chat）；`tools` 判别能力面（管理/教学工具将来进注册表即可，卡机制不动）。管理专家所需的管理动作 MCP 化为独立 backlog 项，不在本子项目。

## 二、目标与非目标

**目标**：①专家=配置实体（DB 卡），非代码；②每专家独立入口（`/e/{slug}/*` + 门户）；③装配按卡分发（6 因子缓存键）；④用户×专家双维隔离（checkpoint/记忆/审计）；⑤关停判据硬验收；⑥问数等值切换零回归。

**非目标**：记忆插槽策略（②）；LLM 目录化管理页（③）；文档 KB 与 `kb:{id}` 知识源（④）；教学引擎/PG 槽（⑤）；专家间协同（远期）；workspace 壳（到第一个非问答专家立项时开）；卡的 DELETE（只关不删，审计安全）；管理动作 MCP 化（独立 backlog）；租户维度（单点收口预留，不实现）。

## 五、装配链改造与 6 因子缓存键

### `_build_agent` 参数化（卡字段 → 装配参数映射）

`get_tupu_agent(connection_id, expert_id)` 新增第二入参；`_build_agent(checkpointer, connection_id, caps, card)` 增 `card`：

| 卡字段 | 装配落点 | 等值锚点（问数卡） |
|---|---|---|
| `system_prompt` | `_build_dynamic_system_prompt(base=卡基座)`；**动态部分（rubric 自检段/技能概要装载）仍由代码拼**，平台能力不进卡 | 基座=现状常量 → 产物逐字节等值 |
| `tools` | `mcp_tools` 全量拉取后按卡窄化：`[t for t in all if t.name in card.tools]`；**空交集拒装配**（沿 subagent_specs 惯例） | 注册表全集（18）等值；批5-C2 排序保留 |
| `skills` / `memory` | `create_deep_agent(skills=..., memory=...)` 按卡 | L1044-1045 等值 |
| `llm_connection_id` | 解析顺序：**请求携带 > 卡默认 > 平台默认** | null → 等值 |
| `skills`/`memory` 路径 | ①`FilesystemPermission` allow 规则按卡路径生成；②`CompositeBackend` routes + `_seed_files` 种子按卡路径；③`_compute_files_hash` 按卡路径算 f 因子 | 同路径 → 权限三规/routes/种子/哈希全等值 |
| `knowledge_sources` | ①期消费方=门户徽标 + CRUD 白名单校验 | `["ontology_graph"]` |

### 缓存键：4 → 6 因子

```
现状:  {connection_id}#g{守卫版}#c{能力版}#f{文件指纹}
设计:  {connection_id}#g{守卫版}#c{能力版}#f{该专家路径树指纹}#e{expert_id}@{卡版本}
```

`#e` 因子是「身份@版本」而不仅是版本：两个专家即使版本号相同也是两个 Agent。LRU 逐出按 expert_id 分组各留最近 2 版（防互相挤占）。`_ASSEMBLY_MANIFEST` +2 项：`expert_id`、`card_version`（+ 各卡字段消费记录）——等值判据 A1 的对照物。

### 请求链

`ChatRequest` + `expert_id: str = "wenshu"`（默认值保证存量请求/测试/e2e 零改动）→ endpoint 校验卡（存在+enabled）→ `get_tupu_agent(connection_id, expert_id)` → `expert_config` 服务读卡（TTL 5s，照抄 guard_config）。

## 七、前端：门户页与 `/e/{slug}/*` 动态路由组

**核心认知：卡是数据，页面是代码。** 问数的 UI 本质是通用问答壳（FreePlanChat 泛化为 `ExpertChat`：读 `useParams().slug` 拉卡 → 标题/欢迎语/建议问题/placeholder 全从卡来）。

| 路由 | 现状 | 设计后 |
|---|---|---|
| `/` | 重定向 `/home` | **门户页 `ExpertPortal`**：`GET /api/experts?enabled=true` → 卡片墙（icon/名称/tagline/知识源徽标）；全关空态 |
| `/home` | FreePlanChat | **重定向** `/e/wenshu/chat`（老书签兼容） |
| `/e/:slug/chat` | — | `ExpertChat`（lazy）——核心入口；渲染前校验卡 entry_kind |
| `/e/:slug/*` | — | 专家自定义页预留位（①期无实现者；`EXPERT_PAGES: {slug: [自定义页]}` 静态注册表，①期空映射） |
| `*` | FreePlanChat 兜底 | 门户兜底 |

App 壳适配：**AppSider** 导航分两区——「专家」区（按卡动态，卡关即消失）+「平台管理」区（守卫/能力/审计/设置，永不属于任何专家）；**AppTabs** 专家页签 key `e:{slug}:chat`；`pathToMenuKey`/`menuKeyToPath` 从静态常量改为「静态平台项+动态专家项」合成；**请求链** `_streamChat` body + `expert_id`（七字段，默认 `"wenshu"`）。

**等值保护**：wenshu 卡的 placeholder/建议问题=现状值——e2e 选择器（`想问什么数据？`、`.ant-table`）零改动。

**关停判据前端语义**：卡关 → 门户不渲染 + 侧栏消失 + 直敲 URL 重定向门户+提示。

|---|---|---|---|

| 4 | **checkpoint 三段键迁移**（lifespan 启动任务，服务就绪前完成）：**对库内全部含 thread_id 列的表执行**——实测 `checkpoints`（4561 行）+ `writes`（8229 行），langgraph 双表结构（`backend/scripts/_diag_checkpoint_schema.py` 可复查）；检测谓词=thread_id **恰含一个冒号**（实测 thread 部分无冒号）；变换=**在第一个冒号后插入 `wenshu:`**（`{user}:{thread}` → `{user}:wenshu:{thread}`——**严禁** `'{user}:wenshu:' || 原串` 式整串拼接，那会产出四段错键）→ 每表记日志（迁移行数） | 幂等（三段键含两个冒号，不满足谓词自然跳过） | **try/except：失败记日志+继续启动**（旧键失联但服务活）——迁移失败不允许打死平台 |

## 十、错误处理与 fail-safe

| 故障面 | 处理 | 先例 |
|---|---|---|
| 卡读取失败（DB 崩/表空） | wenshu 特例：内置 `DEFAULT_WENSHU_CARD` 基线照跑；其他专家：不可用，如实上屏，不降级成 wenshu（身份错乱比不可用更糟） | guard_config 查库异常→全启用基线 |
| 未知/停用 expert_id | endpoint 前置校验：未知 404；停用拒绝+SSE error；**入口拦截先于装配**——已缓存旧 Agent 不被误杀（LRU 自然逐出） | 守卫 PATCH 语义 |
| 卡内容非法（CRUD 后路径被删的竞态） | CRUD 源头校验；装配空交集拒装配（fail-closed）→ 回退 `_LAST_GOOD_ASSEMBLY`（扩展为含卡快照）→ 仍败 raise + `expert_events` 落 `assembly_failed` | subagent_specs 空交集 + create_tupu_agent 三级保险 |
| checkpoint 迁移失败 | 记日志+继续启动，幂等可重跑 | L1 永不抛错精神 |
| expert_events 落账失败 | fire-and-forget | record_event 惯例 |

**两条「不是故障」的明示**：版本竞态由双检锁+键含版本天然覆盖（零新代码）；守卫/能力台账对关停专家继续平台级记录（逻辑一体）。

## 十二、风险与诚实账

1. **改动面横跨前后端主干**（装配/缓存键/路由/表/迁移）——是九项建设里回归风险最大的一件，但每一步有等值判据兜底；实施必须分批（见交棒提示词的长任务模式）；
2. **系统提示词逐字节等值**是强约束——A2 对拍单测若失败，任何「语义等价」辩解都不接受，回修到逐字节；
3. **checkpoint 迁移的窗口期**：迁移运行中如果有请求并发写旧键——锁（部署窗口单实例）+ 迁移在 lifespan 启动期（服务未就绪前）天然规避——步骤 4 的迁移在步骤 1 新后端的启动序列内、服务就绪前完成；
4. **第二张卡（echo 专家）是测试件**——验收后应关停（无 DELETE，留着 disabled 即可）；
5. **`entry_kind=workspace` 未实现**——CRUD 白名单挡住，不是占位符是收口；
6. **管理动作 MCP 化不在本件**——管理专家的完整落地依赖该 backlog 项，地基只保证 `tools` 机制容纳。
