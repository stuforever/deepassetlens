# 二、批次规格书

## 批13-A 单帧交付 v2【第一优先】

**现状**：answer_draft 经 flushTokens 写 ThinkStream 'answer' 项+streaming_answer 双写（批1-A 已实施），done 补框架造成两段式。

**改法**：
1. 撤销双写：flushTokens 中 answer_draft 分支不再写 streaming_answer/ThinkStream 正文，仅驱动状态机；
2. 输出区状态机（FreePlanChat）：

| 触发事件 | 状态文案 |
|---|---|
| 提交 | 正在理解问题… |
| 首个 tool_start | 检索数据中… |
| first_answer_token | 答案生成中… |
| answer_committed | 答案整理中，正以结构化方式输出，请稍候… |
| done | 渲染完整交付卡（标题+徽标+表格+正文+推荐 chips） |

3. 不变式：输出区任意时刻 = 状态行 XOR 完整交付卡；
4. 可选开关 `TUPU_EARLY_TABLE`（默认关）：sql_result 到达即表格先行入卡；
5. done 兜底链第三优先级由 draft 改回 payload.final_answer。

**边界**：多会话隔离沿用 streamingSidRef 覆盖新状态字段；rubric 异步徽标翻转不得触发重排版。
**量级**：前端 1d。**验收**：e2e 全程零逐字文本；committed→done 间可见整理中文案；done 后无二次排版跳动。

## 批13-B 自评后置

**B'-1 规则跳过扩展**：
```python
def apply_rubric_tier(contract):
    if contract.route_type != "generic" or not contract.rubric: return
    if getattr(contract, "aggregate_intent", None): return          # 分布类不豁免
    hits = contract._runtime.get("golden_hits") or []
    if hits and max(h["score"] for h in hits) >= GOLDEN_ANCHOR_SIM: # 0.85
        contract.rubric = None
        contract._runtime["rubric_skipped"] = "golden_anchored"
        return
    rt = contract._runtime.get("last_result") or {}
    if rt.get("verification_clean") and rt.get("row_count_type"):   # 干净单值结果
        contract.rubric = None
        contract._runtime["rubric_skipped"] = "clean_aggregate"
```
插入点：data_intelligence_stream 契约消息构造后、rubric 注入前。

**B'-2 异步化**：answer_committed 到达即发 final+done(evidence.rubric_status="pending")；grader 移后台任务；rubric 事件原地翻转徽标；needs_revision 时显式「复核修正」标注替换正文并治理留痕（max_iterations=1）。恢复交互沿用 Command(resume) 协议形态。

**量级**：0.5d+1d。**验收**：干净统计题日志无 grader 调用；done≤答案完成+1s；徽标异步到位无二次排版。

## 批13-E 守卫策略管道 + 后台配置

**统一接口**：
```python
@dataclass
class GuardContext:
    contract: "QueryContract | None"; tool_name: str; tool_args: dict
    sql: str | None; state: dict; phase: str   # pre_tool|pre_sql|post_answer

@dataclass
class GuardResult:
    guard_id: str; passed: bool; reason: str = ""; action: str = "block"  # block|warn|log

class Guard(Protocol):
    guard_id: str; tier: str     # redline|policy|param
    def check(self, ctx) -> GuardResult: ...
```

**六守卫映射**（原实现包壳不搬家）：

| guard_id | tier | 包裹实现 | 原位置 |
|---|---|---|---|
| whitelist | redline* | 契约白名单检查 | skill_policy 内联段 |
| sql_safety | redline | validate_sql 只读+函数黑名单 | secure_query_executor.py |
| absolute_tools | redline | task/write_file 等 6 个绝对禁止 | query_contract |
| engine_lock | policy | 引擎一致性比对 | skill_policy |
| stop_when | policy | 已获数据收窄 | query_contract+skill_policy |
| template_fingerprint | policy | AST 结构指纹 | template_guard.py |
| output_contract | policy | 明细清洗 | delivery |

\* whitelist/sql_safety/absolute_tools 三者归红线：管理页只读展示+触发统计，API 拒改（403+审计）。

**管道算法**：
```python
DEFAULT_PIPELINE = ["whitelist","absolute_tools","engine_lock","stop_when",
                    "sql_safety","template_fingerprint"]   # post_answer 另跑 output_contract
def run_guards(ctx):
    policy = load_policy()      # DB+TTL5s 缓存；失败→全默认启用(fail-closed)
    for gid in DEFAULT_PIPELINE:
        p = policy.for_(gid)
        if not p.enabled: continue
        r = GUARDS[gid].check(ctx)
        if r.passed: continue
        if p.mode == "log": audit(gid, r, ctx); continue
        if p.mode == "warn": audit(gid, r, ctx); emit_warning(r); continue
        return r                # block 短路
    return GuardResult(guard_id="pipeline", passed=True)
```

**DDL**：
```sql
CREATE TABLE guard_policies (
  guard_id VARCHAR(64) PRIMARY KEY,
  enabled BOOLEAN NOT NULL DEFAULT TRUE,
  mode VARCHAR(16) NOT NULL DEFAULT 'block',
  params JSON NULL,
  locked BOOLEAN NOT NULL DEFAULT FALSE,
  updated_by VARCHAR(64), updated_at DATETIME, remark VARCHAR(255));
```

**接入三点**：SkillPolicyMiddleware 内部改调 run_guards(phase=pre_tool)；secure_query_executor 执行前 pre_sql；delivery 段 post_answer。中间件壳保留（挂载点不变）。

**管理页**：「安全策略」面板=守卫列表×级别×状态(block/warn/log)×近24h触发统计 + 参数区(LIMIT[500]/纠错上限[2]/阈值[0.85/0.90/0.95])；变更写审计即时生效。

**量级**：3d。**验收**：默认配置行为与现状一致；关模板守卫预期生效且审计可见；红线 API 拒改；断库全启用。

## 批13-M 定位优先主流程恢复【用户定调】

**背景**：实体定位的主流程被剧本层改写——场景 SKILL.md 的 calling patterns 让多数题直接 `search_entities` 名称直查，locate 技能包（L1-L2 树→validate_l2→fetch_subgraph 以 L2 为顶点取子图，MySQL 关系表实现）沦为「按需挑用」。用户定调：**先定位、找不到再搜索**。

**实体定位标准作业顺序**（写入契约消息 + 各剧本 calling patterns）：
```
① 契约已预解析实体（带来源标注）→ validate_l2/fetch_subgraph 确认后直接用
② 问题可锚定业务域（明示业务域/板块，或上轮 L2 上下文）
   → locate 流程：validate_l2 → fetch_subgraph(l2_id) 从子图选实体
③ 定位失败（L2 下无该实体 / 无业务域线索）
   → search_entities 混合检索兜底（精确→LIKE→同义词+向量三级融合已上线）
④ 仍失败 → fetch_l1_l2_tree 层级树请用户选择
```

**落点三处**：
1. 各场景 SKILL.md calling patterns 改写为上述顺序（locate/sql-query/distribution-overload 等）；
2. 契约系统消息追加「实体定位顺序」标准作业段（随批13-I C1 文案模板化一并固化）；
3. 批13-E 守卫管道加 policy 级提示：调 search_entities 且本轮无任何 locate 类调用且契约标记 locate_first → warn 不拦截（防误伤直通/预解析快捷路径）。

**成本控制**：冷路径多 1~2 轮的缓解——契约预解析升级为「L2+实体对」联合预解析（模型只需 validate 一轮）；fetch_subgraph 结果同会话按 l2_id 缓存复用；L0 直通完全跳过定位（金标 SQL 自带表）。

**量级**：1d（SKILL.md 改写×N + 契约段 + 守卫提示）。**验收**：探索类新问题轨迹首步为 locate 类工具；户变关系回归仍 <4s（直通不受影响）；错挂案例（业扩表）不再出现。

## 批13-N 首响应延迟治理【用户痛点：问句→运行中约10s】

**根因**（详见《首响应延迟解剖》）：首个 yield 在编排尾部（:250），此前串行跑了三次重复 aget_state（:84/:104/:125）、可能白付的 8s 追问改写（先改写后路由再丢弃，场景题最冤）、同步金标检索（0.5~3s）。

**六招**：
1. N1 前端提交即显「正在理解问题…」（不等后端事件，一行改动）；
2. N2 后端首个 status yield 提至生成器第一行（锁之前），后端反馈 <300ms；
3. N3 三次 aget_state 合并为一次，scope/last_skill/历史文本共用；
4. N4 改写移到 generic 路由确认之后 + 超时预算 8s→3s；
5. N5 金标检索异步化：status 先发，后台 task 检索，注入前未完成则本题降级不带锚定；
6. N6 agent 单例服务启动预热（治重启后首问冷启动 2~5s）。

配套：prep 细分计时（lock/state/rewrite/route/retrieval/update 各段 ms）入结构化日志，随批13-K 外露。
**量级**：1d。**验收**：任意问题首个可见反馈 <500ms；场景短问题不再出现改写 LLM 调用日志；长会话 prep 段耗时较基线 -60%。
