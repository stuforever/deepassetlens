## 1. 概述与目标

### 1.1 功能定位

数据智能问答是图谱平台的核心交互入口。用户用自然语言提问，系统通过「技能编排 + 向量召回 + LLM」路由到不同能力，最终产出**可执行的 SQL** 或**知识性回答**。

两类目标：
- **sql_assembly（默认）**：定位实体 → 锁定属性 → 拼装 SQL → 执行，奔向数据查询。
- **knowledge_only**：纯知识探索，基于向量召回 + LLM RAG 给出自然语言回答。

### 1.2 能力依赖全景

```
用户输入
  → boss_router 技能（LLM 分类 + 状态机约束）
  → LangGraph 条件边路由
     ├─ 探索 → explore_node → RAG（向量召回 + LLM）→ explore_answer 卡片
     ├─ 定位 → locate_node → 向量召回候选 → clarification 卡 → 用户确认 → SQL流水线（自动链）
     ├─ 分类 → explore_node(classification 模式) → classification_result 卡片
     └─ 兜底 → fallback_node
  → exit_router / locate_exit（条件边出口）
  → next_step_node → 推荐下一步
  → SSE 流（trace + think + done[含 message_card]）→ 前端渲染
```

### 1.3 核心依赖组件

| 组件 | 作用 | 实现 |
|------|------|------|
| LangGraph 状态机 | 技能编排与条件边路由 | `data_intelligence_graph.py` |
| Qdrant 双向量库 | 实体名/属性名向量召回 | `entity_embeddings` / `attribute_embeddings` |
| 知识图谱 (MySQL) | 定位树层级 + 分类查询 | `kg_entities` / `kg_concepts` / `kg_concept_relations` |
| LLM 连接 | boss_router 分类 + explore RAG | `LLMConnectionConfig` 表（capability=chat） |
| SecretaryState | 跨节点/跨轮次单一状态源 | `secretary_state.py` |

### 2.2 单一状态源：SecretaryState

LangGraph 的 `GraphState` 本质就是 `SecretaryState` 的 dict 序列化形态。所有节点读写同一个 state，跨轮次通过 `InMemorySaver`（checkpointer）+ 文件持久化双保险。

核心字段分区：

| 区块 | 字段 | 说明 |
|------|------|------|
| 用户输入 | `user_input / original_query / dialog_history` | 当前问句 + 原始问句 + 对话历史 |
| 已确认项 | `confirmed: ConfirmedItems` | L1/L2/L2X/L3/L4/L4X/attributes/relations/assembled_sql |
| 任务状态 | `current_task / goal / completed_tasks` | 当前任务/目标/已完成任务列表 |
| 5 旗标 | `chain_locked / entity_locked / attribute_locked / relation_locked / sql_executed` | 驱动推荐链路 |
| 任务结果 | `task_result / task_result_summary` | 当前任务的结构化结果（answer/sql/results 等） |
| 思考历史 | `think_history: List[Dict]` | 每个节点的思考步骤，推送 SSE think 事件 |
| 澄清 | `pending_clarification` | 非空时弹澄清卡，阻塞流程 |
| 用户选择 | `user_selection / user_has_selected_fields` | 用户在候选卡上的选择 |

> ⚠️ **已知问题**：`task_result` 早期未纳入 `secretary_state_to_dict` 序列化，导致 explore 答案进不了 message_card。**已修复**，但说明「序列化白名单」是易漏点。

### 2.3 5 旗标驱动机制

旗标是定位流程的进度指示，驱动 `next_step_node` 的推荐：

```
chain_locked (大类 L1/L3)
  → entity_locked (实体 L2X/L4X)
    → attribute_locked (属性)
      → relation_locked (关系)
        → sql_executed (SQL 执行)
```

`goal=knowledge_only` 时跳过推荐链路；`goal=sql_assembly` 时按锁定状态推荐下一步未完成的环节。

## 3. 能力一：技能编排与图路由

### 3.1 图结构

```
START → boss_router
boss_router ─┬─→ 定位        （条件边：current_task）
             ├─→ SQL流水线
             ├─→ 探索
             ├─→ 兜底
             └─→ clarify     （意图确认，低置信度时）

定位 ──locate_exit──┬─→ clarify      （有 pending_clarification）
                    ├─→ SQL流水线    （entity+attribute 都锁 + goal=sql_assembly，自动链）
                    └─→ next_step

SQL流水线 ──exit_router──┬─→ clarify
探索                    └─→ next_step
兜底

clarify → END
next_step → END
```

**关键设计**：
- `locate_exit` 是图里唯一的「跨节点自动推进」边：定位锁完不回 boss_router，**直接进 SQL流水线，省一轮路由**。
- 其余节点共用 `exit_router`：有澄清 → clarify，否则 → next_step。
- checkpointer 默认 `InMemorySaver`，递归上限 25。

### 3.2 boss_router 节点

`boss_router_node` 职责：调 boss_router 技能拿决策 → 任务名映射 → 低置信度分支。

**决策流程**：
1. **显式任务切换**：若 `user_selection[0].value` 以 `go_task_` 开头，直接映射任务（`intent_knowledge` → 探索，`intent_sql` → 定位），跳过 LLM。
2. **调 boss_router 技能**：动态 import 技能 `main.py` 执行，传入 `user_query / secretary_state / llm_connection_id`。
3. **任务名映射**：`_map_router_task` 把技能返回的 8 个 task（实体定位/属性定位/关系定位/溯源定位/SQL拼装/SQL执行/探索/分类查询/兜底）压缩成 4 个图节点名（定位/SQL流水线/探索/兜底）。
4. **低置信度分支**：`confidence < 0.6` 且无显式选择 → 弹意图确认卡（`stage=intent_choice`，两个选项 intent_knowledge / intent_sql）。
5. **异常降级**：技能抛异常 → `current_task=兜底`，`router_confidence=0.0`。

> ⚠️ **已知问题**：`_map_router_task` 把「溯源定位」归到 SQL流水线而非定位，与 `enforce_state_machine` 的处理不一致。**待对齐**。

### 3.3 boss_router 技能（LLM 决策 + 状态机约束）

技能层 `boss_router/scripts/main.py` 是「LLM 决策 + 状态机约束」双保险。

**双路降级**：
- **路径 A**：`with_structured_output(RouterDecision)` 走 function calling（优先）。
- **路径 B**：手写 JSON 解析（剥 `<think>` 标签 + markdown 包裹 + Pydantic 强校验）。

**SYSTEM_PROMPT 要点**：
- 两类意图：`location`（默认，奔向 SQL）/ `exploration`（纯知识）。
- 8 个合法 task：实体定位、属性定位、关系定位、溯源定位、SQL 拼装、SQL 执行、分类查询、兜底。
- `intent_type` 判定：出现"X在哪个大类下/有哪些字段/了解一下" → exploration，其余 → location。
- `locked_hint`：confidence≥0.8 且实体明确可直锁，跳过 Think 循环。
- 输出 JSON：`intent_type / task / goal / confidence / extracted_keywords / reason / vector_store_hint / locked_hint`。

**状态机硬约束 `enforce_state_machine`**（防 LLM 误判锁定状态）：
- 探索型直接放行。
- task 需要 entity 但未锁 → 强制回"实体定位"。
- SQL 拼装但未锁 attribute → 强制回"属性定位"。
- SQL 执行但未拼装 SQL → 强制回"SQL 拼装"。

**置信度阈值**：`CONFIDENCE_THRESHOLD = 0.7`，低于 0.6 弹意图选择卡。

### 3.4 条件边路由汇总

| 出口节点 | 路由函数 | 分支 |
|----------|----------|------|
| boss_router | `lambda s: s.current_task` | 定位/SQL流水线/探索/兜底/意图确认→clarify |
| 定位 | `locate_exit` | clarify/SQL流水线(自动链)/next_step |
| SQL流水线 | `exit_router` | clarify/next_step |
| 探索 | `exit_router` | clarify/next_step |
| 兜底 | `exit_router` | clarify/next_step |

### 3.5 ⚠️ 已知问题与 🚀 改进方向

**已知问题**：
1. `_map_router_task` 的「溯源定位」归类与 `enforce_state_machine` 不一致。
2. `current_task` 中英文混杂（技能返回中文，图节点用中文，但部分英文残留）。
3. InMemorySaver 不跨进程，重启丢失会话状态（靠文件持久化兜底）。

**改进方向**：
1. 统一 task 命名空间，全链路用中文 canonical 名。
2. 引入 Redis checkpointer 支持多进程 + 重启不丢状态。
3. 把 `_map_router_task` 的映射表抽到配置文件，新增 task 不改代码。

## 4. 能力二：向量召回与定位

### 4.1 双向量库设计

| 维度 | entity_embeddings | attribute_embeddings |
|------|-------------------|----------------------|
| 数据源 | `kg_entities`（仅 L2/L4 概念下） | `kg_entities.properties_schema` 全量 |
| Embed 文本 | `entity_name`（单字段） | 属性中文名 `cnName`（单字段） |
| 向量维度 | 1024（bge-large-zh-v1.5） | 1024 |
| 距离度量 | Cosine | Cosine |
| 索引配置 | Qdrant 默认 HNSW（m=16, ef_construct=100） | 同左 |
| Payload | entity_code/entity_name/level/chain_type/l1/l2/is_main_table/data_layer | attribute_name/attribute_code/entity_code/entity_name/data_type |
| Point ID | `uuid5(NAMESPACE_URL, entity_code)` | `uuid5(NAMESPACE_URL, entity_code:attribute_code)` |

**设计要点**：
- **双库解耦**：实体名和属性名分别建库，独立向量化、独立召回，避免短文本（属性名）被长文本淹没。
- **单字段 embedding**：刻意只用名称做向量，匹配定位场景下用户问句通常是"实体名+属性名"的短文本。
- **幂等同步**：point id 用 uuid5 确定性生成，重复 upsert 不产生重复点。

> ⚠️ **已知问题**：单字段 embedding 对"同义不同名"的实体（如"客户档案"vs"用电客户主数据联接表"）召回率低，依赖 LLM 兜底。

### 4.2 向量召回函数

`search_entity_vectors(query, top_k=15)` / `search_attribute_vectors(query, top_k=15)`：

- **不做阈值过滤**：不传 `score_threshold`，不在 Qdrant 侧过滤，返回 top_k 全部结果。
- **不做 payload 过滤**：纯向量近邻检索。
- **score = Qdrant 余弦相似度**，范围 [0, 1]（归一化向量下）。
- **沙箱桥接**：`skill_injections` 把这两个函数包装成注入 callable，默认 top_k 覆盖为（实体 8 / 属性 10），但 locate 技能会显式传参覆盖。

### 4.3 locate 技能候选生成

`locate_entity_attribute/scripts/main.py` 的并行召回 + 单次 LLM 推理：

```
用户问句
   ├──→ 并行向量召回
   │      ├─ 实体向量 TOP 10
   │      └─ 属性向量 TOP 4
   ├──→ 1 次 LLM 推理（prompt 带候选 + score）
   └──→ 按置信度三段式分流
```

**三段式分流**（LLM 置信度，非向量 score）：
- `confidence ≥ 0.8` → `locked`（直接锁定实体+属性）
- `0.5 ≤ confidence < 0.8` → `candidates`（弹候选选择卡）
- `confidence < 0.5` → `needs_clarification`（弹澄清卡）

**candidates 结构（3 种场景）**：
- **场景 A**（LLM 不可用但有实体候选）：实体候选转选项，top 5。
- **场景 B**（candidates 且已定位实体）：属性候选转选项，top 6。
- **场景 C**（candidates 且未定位实体）：实体×属性笛卡尔积（同 entity_code 匹配），空则退化为纯实体候选。

**score 的作用**：向量 score 主要用于**排序候选喂给 LLM**（prompt 中以 `score=x.xx` 展示），LLM system prompt 明确要求"优先选 score 最高的"。最终判定用的置信度由 LLM 输出。

### 4.4 自动链：定位 → SQL流水线

`locate_exit` 条件边实现自动链：
```python
if sec.pending_clarification:
    return "clarify"
if sec.entity_locked and sec.attribute_locked and goal == "sql_assembly":
    return "SQL流水线"    # 自动链，省一轮路由
return "next_step"
```

这是图里唯一的跨节点自动推进，定位锁完直接进 SQL 拼装。

### 4.5 ⚠️ 已知问题与 🚀 改进方向

**已知问题**：
1. 单字段 embedding 对同义不同名实体召回率低。
2. 属性候选 top_k=4 偏少，用户问"联系电话"时属性候选可能为空（向量库里没有完全匹配的属性名）。
3. 召回层不做阈值，全靠 LLM 判断，LLM 不可用时降级为纯向量候选（可能不准）。

**改进方向**：
1. embedding 文本拼接实体名+英文名+描述，提升语义覆盖。
2. 属性召回增加 payload 过滤（按已锁实体 entity_code 过滤），提升精度。
3. 引入向量 score 预过滤阈值（如 <0.3 丢弃），减少 LLM 噪声输入。
4. 增加"同义词词典"预处理，用户问句先做同义扩展再召回。

## 5. 能力三：LLM 注入与探索 RAG

### 5.1 LLM 连接管理

**两套 LLM 获取策略**（需对齐）：

| 调用方 | 策略 | 文件 |
|--------|------|------|
| boss_router 技能 | 指定 `name=="minimax-m3"` → `is_default==True`，读 `mode_profiles.quick` | `boss_router/scripts/main.py` |
| explore 技能（via build_llm_client） | `capability=="chat"` + `is_default` 降序取首条 | `skill_injections.py` |

`build_llm_client` 流程：
1. DB 读 `LLMConnectionConfig`（enabled + capability=chat + is_default 降序）。
2. 环境变量 fallback（`TUPU_LLM_BASE_URL` / `TUPU_LLM_API_KEY` / `TUPU_LLM_MODEL`）。
3. 构造 `ChatOpenAI`（temperature=0.1, timeout=60）。
4. 包装成 `_LLMClient`，提供 `call_openai_compatible_chat` 和 `__call__` 两个入口。

**注入方式**：`_inject_new_skill_globals` 通过 `setattr` 注入到技能模块全局命名空间，技能内用 `_injected("_injected_llm_client")` 读取。注入是单例的，模块缓存到 `_NEW_SKILL_MODULES`，只注入一次。

> ⚠️ **已知问题**：两套 LLM 获取策略不一致（boss_router 找 minimax-m3，explore 找 default chat），可能取到不同模型，行为不一致。

### 5.2 explore RAG 模式

`explore/scripts/main.py` 的 RAG 流程：

```
用户问句
  ├──→ 向量召回（实体 + 属性）
  ├──→ _format_context 拼成 markdown 上下文
  ├──→ _invoke_llm（system_prompt + user_msg，temperature=0.3）
  ├──→ _json_loads_lenient 三级降级解析
  ├──→ _strip_think_tags 剥离推理标签
  └──→ 返回 {answer, related_entities, related_attributes, suggest_classification}
```

**EXPLORE_SYSTEM_PROMPT 规则**：
1. 优先基于检索到的实体和属性信息回答。
2. 信息不足时如实说明并建议换问法。
3. 不编造不存在的实体或属性。
4. "XX有哪些子类/分类" → 建议走分类查询模式。
5. 输出严格 JSON：`answer / related_entities / related_attributes / suggest_classification`。

**JSON 解析降级链**（`_json_loads_lenient`）：
1. 直接 `json.loads(text)`
2. 正则 ` ```json {...}``` ` 提取后解析（贪婪 `\{.*\}`）
3. 正则 `(\{.*\})` 提取首个 JSON 对象

**最终兜底**：三级都失败时，手动正则提取 `"answer"` 字段值；再失败则去 markdown 包装返回纯文本。

### 5.3 explore classification 模式

`_classification_query` 走 MySQL `kg_concepts` 表，三种 query_type：
- `children`：按 `parent_id` 查直接子分类。
- `subtree`：BFS 遍历子树，受 `depth` 限制，`visited` set 防环。
- `relations`：查 `ConceptRelation.relation_type=="CROSS_CHAIN"` 的跨链关系。

辅助函数 `_find_concept` 解析 `L1-CUSTOMER` 编码（正则 `^(L[1-4]X?)[-_](.+)$`），带英文→中文字典，三级查找（level+name → name → level）。

### 5.4 ⚠️ 已知问题与 🚀 改进方向

**已知问题**：
1. LLM 返回 ```json``` 包装时解析易失败（已多重兜底，但仍偶发 raw 串泄漏）。
2. `<think>` 推理标签需手动剥离（不同模型标签不同）。
3. classification 模式的 `_find_concept` 英中字典是硬编码，新增分类需改代码。
4. RAG 上下文只拼名称，缺描述/数据类型，LLM 信息不足时回答质量低。

**改进方向**：
1. 统一 LLM 获取策略，boss_router 与 explore 共用 `build_llm_client`。
2. 用 `with_structured_output` 让 explore 也走 function calling，避免 JSON 解析问题。
3. RAG 上下文拼接实体描述 + 属性数据类型 + 业务含义，提升 LLM 回答质量。
4. classification 的英中字典抽到数据库配置表。
5. 引入 reranker 对召回结果二次排序，提升 top-K 精度。

## 6. 能力四：前端交互与卡片体系

### 6.1 整体交互架构

```
┌─────────────────────────────────────────────┐
│  左侧：会话列表 + 输入框                      │
├──────────────────────────────┬──────────────┤
│  中间：对话区                 │  右侧：定位树 │
│  ┌────────────────────────┐  │  ┌─────────┐│
│  │ 用户气泡                │  │  │未确定候选││
│  │ 助手气泡                │  │  │(黄色区)  ││
│  │  ├─ ThinkStream         │  │  ├─────────┤│
│  │  │  (思考过程，折叠)     │  │  │主数据链  ││
│  │  └─ CardRenderer        │  │  │L1→L2→L2X ││
│  │     (7种卡片)           │  │  ├─────────┤│
│  └────────────────────────┘  │  │业务链    ││
│                              │  │L3→L4→L4X ││
│                              │  ├─────────┤│
│                              │  │关系/溯源/SQL│
└──────────────────────────────┴──────────────┘
```

### 6.2 SSE 流式协议

**三个事件**：

| event | data | 触发 | 前端处理 |
|-------|------|------|----------|
| `think` | 单条 think 历史 dict | 每节点完成 | `onThink` 增量追加到 `thinkStream` |
| `trace` | 单条 trace dict | 每节点输出 | ⚠️ 前端未处理 |
| `done` | 完整最终响应 dict | 流结束 | `onDone` 构建助手消息 + 卡片 |
| `error` | `{"error":"..."}` | 异常 | `onError` 提示 |

**SSE 格式**：
```
event: think
data: {"task":"实体定位","strategy":"vector_llm","action":"...",...}

event: done
data: {"thread_id":"...","current_task":"...","message_card":{...},...}
```

前端 `chatStream` 按 `event:`/`data:` 行解析，按 currentEvent 分发回调。返回 `AbortController` 支持中断。**90s 超时保护**：超时自动恢复 loading 并提示。

> ⚠️ **已知问题**：前端未处理 `trace` 事件，定位流程的节点 trace 信息丢失。

### 6.3 message_card 单卡优先级

`_build_message_card` 只返回**一张卡**，优先级：

```
clarification（澄清卡）
  > classification_result（分类结果卡）
  > explore_answer（探索答案卡）
  > sql_preview（SQL预览卡）
  > confirmed_entities（已锁实体卡）
  > progress_flags（进度旗标卡，done_count>0）
  > recommended_next（推荐下一步卡）
```

每张卡结构：`{card_id, card_type, title, summary, data}`。

### 6.4 卡片类型与渲染

| card_type | 渲染组件 | data 关键字段 |
|-----------|----------|---------------|
| `clarification` | ClarificationCard | question/options[{label,value,entity_code,...}]/multi_select |
| `classification_result` | ClassificationResultCard | query_type/results/cross_chain_relations |
| `explore_answer` | ExploreAnswerCard | answer/related_entities/related_attributes |
| `sql_preview` | SqlPreviewCard | sql/executed/row_count/columns/rows_preview |
| `sql_execution_result` | SqlExecutionResultCard | sql/rows/columns/row_count/took_ms/error |
| `confirmed_entities` | ConfirmedEntitiesCard | items[{type,code,label}] |
| `progress_flags` | ProgressFlagsCard | flags[{key,label,done,icon,tip}]/done_count |
| `recommended_next` | RecommendedNextCard | recommendations[{task,label,shortcut}] |
| `rich_text` | 内置 Card+Paragraph | text |

> ⚠️ **已知问题**：`sql_execution_result` 后端无独立 builder，sql_preview 卡 executed=True 时内嵌结果；独立 card_type 仅前端有渲染器，来源路径不明确。

### 6.5 ThinkStream（思考过程）

对话气泡内渲染思考过程（替换了原来的 WorkflowExecutionTimeline）：
- `Collapse` 折叠面板 + `Timeline` 时间线。
- 每条 think 项展示：action + 策略 Tag、input_query、result_status、candidates_count、reason、level+code。
- 策略映射表支持 7 种：`vector_llm / vector_recall / llm_classify / precise_query / llm_infer / graph_traverse / llm_generate`。

### 6.6 LocationTree（定位树，未确定/已确定双态）

**未确定候选区**（黄色背景 `#fffbe6`）：
- `pendingCandidates` prop 驱动。
- 分「实体候选（未确定）」「属性候选（未确定）」两组，最多 8 条。
- 橙色 Tag 标记，显示 score 百分比。

**已确定主区**：
- 主数据链：L1→L2→L2X(主实体)→属性子节点；无数据时占位骨架。
- 业务链：L3→L4→L4X(业务实体)；无数据时占位。
- 关系区：三色 Tag（main_related 蓝 / main_business 绿 / business_business 金）。
- 溯源区：`flags.entity_locked && (L2X||L4X)` 时展开「实体→物理表→字段」。
- SQL 区：`assembled_sql` 非空时显示。

**状态流转**：用户在对话框确认候选 → `applyResponse` 更新 `pendingCandidates=[]` + `confirmed` 填充 → 定位树候选区消失，主区显示已确认实体（打"已确定"标记）。

### 6.7 ⚠️ 已知问题与 🚀 改进方向

**已知问题**：
1. `trace` 事件前端未处理，节点 trace 信息丢失。
2. `sql_execution_result` 卡来源路径不明确（后端无独立 builder）。
3. 单卡优先级导致同轮多结果只能展示一张（如 confirmed + recommended_next 只显示 confirmed）。
4. LocationTree 占位骨架在无数据时显示"示例1/示例2"，用户易误解为真实数据。

**改进方向**：
1. 前端处理 `trace` 事件，在 ThinkStream 里展示节点路由轨迹。
2. 明确 sql_execution_result 的推送路径，或统一到 sql_preview 卡。
3. 支持多卡堆叠（cards 数组），按优先级排序展示多张。
4. LocationTree 无数据时显示空状态引导文案，而非假数据骨架。

## 7. 数据与依赖

### 7.1 知识图谱数据源

| 表 | 作用 | 关键字段 |
|----|------|----------|
| `kg_concepts` | 概念分类树（L1-L4） | id/level/name/parent_id |
| `kg_entities` | 实体（L2X/L4X） | id/entity_code/entity_name/concept_id/properties_schema/is_main_table |
| `kg_concept_relations` | 概念间关系 | relation_type(CROSS_CHAIN)/from_id/to_id |

**定位树层级映射**：
- L1（业务域大类）→ L2（业务域）→ **L2X（主数据实体）** → 属性
- L3（标准域大类）→ L4（标准域）→ **L4X（业务实体）** → 属性

### 7.2 向量库同步

**同步入口**（`data_sync.py`）：
- `POST /api/v1/sync/entity-vectors?force=True` — 实体库同步
- `POST /api/v1/sync/attribute-vectors?force=True` — 属性库同步
- `POST /api/v1/sync/all-vectors` — 一键同步双库（串行）
- `GET /api/v1/sync/entity-vector-stats` / `attribute-vector-stats` — 点数统计
- `POST /api/v1/sync/query-vectors` — 测试查询

**同步参数**：
- embedding 批次：32（API 限制）
- Qdrant upsert 批次：64
- force=True：先 delete_collection 再重建
- Point ID：uuid5 确定性生成，幂等

### 7.3 Embedding 模型

| 模型 | provider | dimension | 说明 |
|------|----------|-----------|------|
| `bge-large-zh-v1.5`（默认） | local | 1024 | 本地推理 |
| `bge-m3` | local | 1024 | 多语言 |
| `glm-embedding-3` | openai_compatible | 2048 | 在线 API |

向量维度通过探测获得（`_get_vector_size` 用短文本试跑一次 embedding）。

### 7.4 LLM 连接配置

`LLMConnectionConfig` 表关键字段：
- `name` / `model_name` / `base_url` / `api_key`
- `capability`（chat / embedding）
- `is_default` / `enabled`
- `extra_config.mode_profiles`（quick/normal，含 `extra_body` / `timeout_seconds` / `temperature`）

boss_router 读 `mode_profiles.quick.thinking.type=disabled` 关闭 MINIMAX-M3 深度思考。

## 8. 关键接口与数据契约

### 8.1 `/chat`（同步）

**请求** `ChatRequest`：
```json
{
  "thread_id": "uuid（自动生成）",
  "user_input": "用户问句",
  "user_selection": [{"label":"","value":"","entity_code":"","attribute_code":""}],
  "format": "card",
  "llm_connection_id": null
}
```

**响应** `ChatResponse`：
```json
{
  "thread_id": "...",
  "current_task": "定位/探索/SQL流水线/兜底",
  "goal": "sql_assembly / knowledge_only",
  "pending_clarification": {"task":"","stage":"","question":"","candidates":[],"multi_select":true},
  "confirmed": {"L1":null,"L2X":"...","attributes":[...],"assembled_sql":null},
  "completed_tasks": ["探索"],
  "flags": {"chain_locked":false,"entity_locked":true,"attribute_locked":false,...},
  "think_stream": [{"task":"","strategy":"","action":""}],
  "next_step_recommendation": {"recommendations":[{"task":"","label":"","shortcut":""}]},
  "message_card": {"card_id":"","card_type":"clarification","title":"","summary":"","data":{...}}
}
```

### 8.2 `/chat/stream`（SSE 流式）

请求体同 `/chat`。响应为 SSE 流：
- `event: think` → 增量思考
- `event: trace` → 节点 trace（前端未处理）
- `event: done` → 完整最终响应（结构同 `/chat` 响应，含 `message_card`）
- `event: error` → 异常

### 8.3 前端 ChatResponse 类型

前端 `ChatResponse` 与后端字段一一对应。`ConversationCard` 类型：`{card_id?, card_type, title?, summary?, data?}`。

### 8.4 卡片 data 契约（关键卡）

**clarification.data**：
```typescript
{
  question: string,
  hint: string,          // "阶段：{stage}"
  multi_select: boolean,
  manual_allowed: true,
  options: [{
    label, name, value, submit_value, description,
    code, level, entity_code, entity_name,
    attribute_code, attribute_name, is_main_table, score
  }]
}
```

**explore_answer.data**：
```typescript
{
  answer: string,
  related_entities: [{entity_code, entity_name, level}],
  related_attributes: [{entity_code, attribute_name, attribute_code}],
  suggest_classification: boolean
}
```

**sql_preview.data**：
```typescript
{
  sql: string,
  executed: boolean,
  row_count?, columns?, rows_preview?, exec_time_ms?  // executed=true 时
}
```

## 9. 演进路线

### 9.1 短期（稳定性与一致性）
1. 统一 task 命名空间，全链路中文 canonical 名。
2. 统一 LLM 获取策略，boss_router 与 explore 共用 `build_llm_client`。

3. classification 英中字典抽到数据库配置表。
4. 引入同义词词典预处理，用户问句先做同义扩展再召回。
5. 探索 `with_structured_output` 全链路 function calling，消除 JSON 解析问题。
