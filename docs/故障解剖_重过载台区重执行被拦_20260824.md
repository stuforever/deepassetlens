# 故障解剖：重过载台区重执行被拦截（21:15 案例）

> 2026-08-24 · 设计窗口产出 · 症状：改写后契约钉错步骤 → 模板守卫正确拦截 → 合法请求失败

---

## 一、故障链还原（六步，全部有代码依据）

```
用户原句：「再次查询重过载台区，我数据更新了，重新执行一遍」
     │
     ▼ ①「再」命中指代词表 _FOLLOWUP_PRONOUNS = (那,它,上述,该,也,再)
追问改写触发（followup_rewrite.py）
     │
     ▼ ② 改写提示词要求「结合会话上文与上一轮口径」→ LLM 以【上一轮】为锚改写
改写句偏向上一轮口径（上一轮=户变关系），「过载」语义丢失/替换
     │
     ▼ ③ 路由吃的是【改写后文本】
场景命中 distribution-overload，_select_step 按改写句选步骤 → step1 relationship
（若改写句连场景词都丢了则走 P1 沿用 last_step=relationship，结果相同）
     │
     ▼ ④ 契约钉死 step1 户变关系模板（QueryContract.from_step）
     │
     ▼ ⑤ L180「非 generic 路径丢弃改写，用原问题」→ 模型收到的是【原句】
模型按原句真实意图（重过载判定）读 SKILL.md → 拼 step2 功率汇集 SQL（96点功率表+CTE）
     │
     ▼ ⑥ template_guard 以 step1 模板为基准比对 → 表/CTE 越界 → 拒绝×2
纠错上限 2 耗尽 → SkillPolicy 拦截 → 模型诚实报告失败（未编造、未绕过）
```

**关键证据**：
- 指代词表含「再」：followup_rewrite.py `_FOLLOWUP_PRONOUNS`
- P1 沿用只查场景级触发词、last_step 直接沿用：skill_router.py:122-124, :118
- 步骤级触发词表（本该救场）：step overload = any:[重载,过载,负载率,96点功率,用电负载,上网负载,发电负载]——**原句含「过载」本必命中 step2**
- 丢弃逻辑：data_intelligence_stream.py:180-181「非 generic 路径丢弃改写，用原问题」——改写只影响给模型的问题，**不影响已经用改写句跑完的路由**

## 二、根因定性：三方各自都「对」，合起来错

| 角色 | 行为 | 对错 |
|---|---|---|
| 改写器 | 按指令以上一轮口径改写 | 遵循了提示词 |
| 路由器 | 对它收到的文本做确定性匹配 | 算法正确 |
| 模型 | 对用户原句的语义（重过载）做 step2 拼装 | 语义正确 |
| 守卫 | 按契约（step1 模板）校验 SQL | **fail-closed 完全正确** |

**病灶 = 改写句喂给路由、原句喂给模型，契约与语义脱钩。** 模型知道用户要什么，守卫知道契约是什么，两者说的不是同一件事。

## 三、修复设计（批13-P，四层）

| # | 修法 | 层级 | 说明 |
|---|---|---|---|
| P1 | **先路由、后改写**（并入批13-N4） | 根修 | 路由永远吃原句（用户意图的唯一权威来源）；改写移到 generic 路由确认之后，只服务省略补全。scenario 题根本不该改写——本案例若此条成立，后面全部不发生 |
| P2 | **改写词保留硬约束** | 根修 | 提示词加「必须逐字保留领域触发词（过载/重载/负载率/户变关系/用电户与配变…），改写仅补全省略的主语与范围」 |
| P3 | **双文本触发检测兜底** | 防御 | 路由对原句与改写句各跑一次场景触发检测，任一句命中即视为 fresh（防 P1 误沿用）；步骤选择以原句优先 |
| P4 | **守卫拒绝理由透明化** | 体验 | template_guard 拒绝消息注明「校验基准=step1 户变关系模板；SQL 含 step2 功率汇集表」——模型两次盲试变一次定位（当前模型是在最终答案里才推理出来的） |

**可选第 5 层（需定调）**：连续两次模板失败且 SQL 恰好完整匹配同技能另一步骤的模板指纹 → 一次受审计的契约重锚定（确定性指纹匹配，不放松安全模型）。因为给守卫开例外口子，列为可选项。

## 四、立即解法（当下可用）

重发一句不含指代词的完整问题：如「查询当前过载台区」或「重载和过载台区有哪些」——原句直达路由，必命中 step2。或新开会话（无 last_step 沿用风险）。

## 五、亮点登记（这个 case 里系统做对了什么）

1. fail-closed 全程生效：未编造数据、未绕过守卫、两次纠错有界、最终解释清晰可行动；
2. 模型行为合规：拼的 SQL 语义正确、失败后如实报告并给出合理建议；
3. 拦截信息里带足够线索（口径、步骤、校验器行为），使本次根因定位仅靠日志与代码即完成。

> 结论：守卫无罪，输在路由上游的语义保真。批13-P 一并修「改写-路由-步骤选择」链的文本一致性，配合已排期的批13-N4（改写后置）形成双保险。
