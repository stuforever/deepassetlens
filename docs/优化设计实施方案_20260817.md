## 〇、设计原则与约束（所有设计不得违反）

1. **YAGNI**：不为想象的需求设计；每个设计都要有明确收益点。
2. **KeepAlive 语义不可破坏**：`AppTabs.tsx:120-141` 所有已开页签同时挂载（`display:none` 隐藏非活动页）。任何懒加载/卸载方案都必须保持「已打开页签不丢状态」。
3. **端口铁律**：后端固定 28000（`__start_8000.py`），前端 23000；前端代码禁止硬编码后端端口（一律相对路径 + `setupProxy.js` 转发）。
4. **GLM 兼容**：后端 `_response_format=None` 不可改回（GLM 不兼容嵌套 schema）。
5. **DecisionGate 是硬闸门**：后端查询执行链路的安全设计不可削弱。
6. **不动代码**：本文只出设计，实施需另开改码窗口并先复核。

## 一、设计一：路由 lazy 化 + KeepAlive 兼容方案（P1，投入产出最高）

### 1.1 现状（已复核）
- `routes.tsx:1-14` 16 条路由条目，**13 个去重组件**（`GraphManager` 复用 3 次：`/graph`、`/tree-model`、`/matrix`；`*` 兜底指回 `FreePlanChat`）。
- `App.tsx:244` 把 `routes` 整个传给 `AppTabs`；`AppTabs.tsx:120-141` 按 `tab.menuKey` 查 route 并渲染，KeepAlive 常驻。
- `index.tsx:14-24` 无 `Suspense`、无 `ErrorBoundary`。
- 全 src `React.lazy` 零命中。

### 1.2 目标 chunk 边界
| 路由 menuKey | 组件 | 建议 chunk | 说明 |
|---|---|---|---|
| home / * | FreePlanChat | `home`（首屏） | 含全部 conversation/* 子组件 |
| graph / tree_model / matrix | GraphManager | `graph`（三合一，共用画布组件） | g6 系画布（ForceCanvas/TreeCanvas/MatrixCanvas/Neo4jForceCanvas）+ LineageGraph |
| master_data / activity / entity_relation | Master/Activity/EntityRelation | `entity` | 主数据/活动/实体关系，可合一个 chunk |
| source | SourceManager | `source` | 巨型组件，独立 chunk |
| mapping | MappingManager | `mapping` | 巨型组件，独立 chunk |
| metrics | MetricManager | `metrics` | 巨型组件，独立 chunk |
| skills | SkillManagerV2 | `skills` | 含 monaco |
| datasource / doris_config | DataSource/DorisConfig | `config` | 小页可合并 |
| vector | VectorManagePanel | `vector` | 独立 |
| llm_config | LLMConfigManager | `llmconfig` | 独立 |

### 1.3 关键设计决策
1. **`routes.tsx` 只改 `element` 字段为 `React.lazy(...)`**，`RouteConfig` 结构不变 → `AppTabs` 几乎零改动。
2. **Suspense fallback 落点**：放在 `AppTabs.tsx` 内容区外层（`<Suspense>` 包住整个 KeepAlive 内容区），fallback 用轻量 `Spin`/占位骨架。理由：lazy 只在**首次打开某页签**时触发加载，KeepAlive 已挂载页签不受影响；包在内容区外层可同时覆盖「首次点开即加载」与「已开页签重渲染」两种场景。
3. **KeepAlive 兼容性**：lazy 只影响「模块是否已在 bundle」，**不影响「已挂载组件是否卸载」**——KeepAlive 语义天然兼容，无需为 lazy 改 AppTabs 的 display 逻辑。
4. **重依赖独立 chunk + preload**：`@antv/g6`（4 个 import 点）、monaco（2 个 import 点）会随各自组件进入对应 chunk。设计上对 `/graph` 与 `/skills` 两个入口可做 `<link rel="modulepreload">` 预热（CRA 下可用 `webpackPrefetch`/`webpackPreload` 注释标注），避免首次点开明显白屏。
5. **ErrorBoundary**：`index.tsx` 增加全局 ErrorBoundary（设计为懒加载失败的兜底，展示「页面加载失败，刷新重试」，不抛裸错）。

### 1.4 收益与风险
- 收益：首屏不再下载 g6/monaco/巨型页 → 首屏 JS 体积预计下降 40~60%；与 KeepAlive 叠加后「开哪个页签才拉哪个 chunk」。
- 风险：首次点开新页签有瞬时 fallback → 用 preload + 轻量骨架缓解；CRA（react-scripts）对动态 import 的 chunk 命名支持有限，建议实施时验证 chunk 命名可读性（可用注释 `/* webpackChunkName: "mapping" */`）。

## 二、设计二：巨型组件拆分蓝图（P1）

### 2.1 拆分通则（四个组件共用）
1. **先抽纯展示子组件**（无业务逻辑、仅 props 渲染）→ 立刻获得 memo 化可能。
2. **再抽 hooks**（数据加载、表单状态、抽屉开关）→ 减小主组件状态面。
3. **最后重组页面骨架**（布局 + 分栏 + 抽屉挂点）。
4. 状态提升策略：**跨区共享才进 zustand**（已有 `store/useStore.ts`）；局部状态留在 hooks 内部；**禁止新建全局 store 承载单一页面状态**。
5. 目录约定：`src/components/<domain>/`（如 `model-tree/`、`mapping/`）放子组件与 hooks；页面文件保留为「薄壳」。

## 三、设计三：API 治理与类型契约（P2，掐灭 any 源头）

### 3.1 类型契约范围（三件套）
- `services/api.ts`（/api/v1，55 处 any）：先为最高频域定型——`conceptApi`、`entityApi`、`entityRelationApi`、`mappingApi`、`kgApi`。
- `services/skillV2Api.ts`（/api/v2）：`SkillDTO`/`SkillVersionDTO`/`ExecutionDTO` 接口已在文件内，缺的是**请求/响应包装类型**（如 `{ code, data, message }` 的统一响应壳）。
- `services/dataIntelligenceApi.ts`（/api/data-intelligence）：`ChatRequestPayload`/`ChatResponse`/`ConversationCard` 已有雏形，缺**流式事件类型**（thinkStreamReducer 的事件 union 应与后端 SSE 事件对齐）。

### 3.2 设计要点
1. **先建 `services/types.ts`**：统一响应壳 `ApiResp<T> = { code: number; data: T; message?: string }`；按领域导出 DTO。
2. **API 方法签名优先**：`createConcept(data: ConceptCreateInput): Promise<ApiResp<ConceptDTO>>`——把「返回类型」写死，消费方不再需要 `as any` 解构。
3. **流式事件契约**：`dataIntelligenceApi` 的 SSE 事件与 `utils/thinkStreamReducer.ts` 的 reducer action union 对齐（rejected/superseded 语义保持现状，勿动已测逻辑）。

### 3.3 axios 收敛（5 处绕行 → 统一实例）
- 现状（已复核）：统一实例 `api.ts:6-33`；绕行 5 处——`DataSourceConfig.tsx:11`、`DorisConfig.tsx:12`（裸实例）、`ModelTreeManager.tsx:863`（裸 `axios.get`）、`skillV2Api.ts:5`、`dataIntelligenceApi.ts:15`（自建实例）；`ResourceAclDrawer.tsx:47-54` 自管 token。
- 设计：
  1. 从 `services/api.ts` **导出共享的 `authedApi`**（带 token + 401 拦截），供 skillV2Api/dataIntelligenceApi 复用同一拦截器逻辑；
  2. DataSourceConfig/DorisConfig/ModelTreeManager 改为从 `services/api.ts`（或新增的 `dataSourceApi`）导入既有方法，删除文件内 `axios.create`；
  3. ResourceAclDrawer 删除 `authedClient()`，改注入 `authedApi`（401 跳转由拦截器统一负责）。
- 验收：全 src `axios.create(` 仅剩 `services/api.ts` 一处；`import axios` 仅存于 services 层。

### 3.4 错误处理统一层
- 设计：`authedApi` 响应拦截器在 401 之外增加**统一 `message.error` 兜底**（可读 `error.response.data.detail`），并预留「静默」选项（请求级 `config.silent = true` 跳过全局提示，供轮询/导出等场景用）。
- 目标：组件 catch 块只负责「可选补充文案」，不再各写一套 `message.error`。

## 四、设计四：渲染性能设计（P2）

### 4.1 现状（已复核）
- `React.memo` 全库 = 0；`useMemo=58`、`useCallback=18`（全库）；高频对话链路四件套（FreePlanChat/AssistantCanvas/ConversationMessageList/CardRenderer）全 0。

### 4.2 设计落点
1. **卡片层 memo**：`conversation/CardRenderer.tsx` 按 `card_type` 分发的卡片（SummaryCard/ThinkStream/SqlResultTable 等）整体包 `React.memo`；props 为不可变 data 的卡片收益最大。
2. **消息列表项 memo**：`ConversationMessageList.tsx` 的单项消息组件包 `React.memo`，配合「仅最后一条流式消息更新」的增量渲染策略（流式期间只重渲染活跃消息项，不重渲染整树）。
3. **useCallback 补位**：传给 memo 子组件的回调（如 `onCardAction`、`onSelect`）补 `useCallback`，避免 memo 失效。
4. **不做的事（YAGNI）**：不为每个卡片过度细分 memo；不引入虚拟列表库（当前消息量级不必要）。

### 6.2 沙箱威胁模型决策（P0 边界确认）
- 现状（已复核）：`core/execution_engine.py:60-131` `SandboxExecutor`（白名单内置函数 + 按权限摘除 open/__import__/文件系统）；`api/smart_skills.py:1756-1775` 手写白名单（弱）。危险模式扫描全零（无 os.system/subprocess/pickle/yaml.load/shell=True）。
