# 缺陷分析：generic 模式 P0 功能回归（架构演进不同步）

- 日期：2026-08-20
- 等级：P0（generic 自由问答默认路径整体不可用，落地页首条示例即命中）
- 修复方案：方案 A（白名单对齐真实工具名，推荐方案）
- 状态：已施工 + 全量测试 + 活体验证通过

---

## 一句话根因

工具层已把统一 `kg_api`（16 个 action）拆成 16 个单一职责 MCP 工具（`app/mcp_server.py`），
但 **generic 契约白名单、系统提示词、测试断言三处没有同步更新**：
白名单里留着不存在的幽灵工具 `kg_api`，而模型真正需要的 10 个只读元数据工具全不在白名单。

## 完整故障链

| 步 | 发生了什么 | 代码证据 |
|---|---|---|
| 1 | 未命中场景剧本 → generic 低权限模式，契约允许清单 = `read_file, kg_api, batch_entity_source_mode, execute_*` | `skill_router.py` → `query_contract.py`（GENERIC_ALLOWED_TOOLS，修复前） |
| 2 | 契约以 SystemMessage 注入「允许工具：…kg_api…」 | `data_intelligence.py:84` |
| 3 | 模型第 1 反应是对的：调 `fetch_l1_l2_tree`（真实只读工具）→ Policy 逐字匹配白名单，**拒绝** | `skill_policy.py:123-125`（`contract.allows()` 字面匹配） |
| 4 | 模型改调 `search_entities`（同样真实且正确）→ 再次被拒 | 同上 |
| 5 | 模型听话去调白名单里的 `kg_api` → Agent 工具集 = 16 个 MCP 工具，**根本没有 kg_api** → 调用报错 → 模型得出「kg_api 并非有效工具」 | `tupu_deepagent.py` create_tupu_agent（tools=mcp_tools）；`@tool kg_api` 是死代码 |
| 6 | 只剩 `batch_entity_source_mode` 可调，但入参要 `entity_codes`（物理表名）——正是模型想发现的东西 → 鸡生蛋死锁 → 「已执行 0 步」 | `mcp_server.py` batch_entity_source_mode |

**雪上加霜**：系统提示词仍教模型用幽灵工具（`_COMMON_RULES`「直接调 kg_api 工具」、`_KNOWLEDGE_FLOW_RULES`、execute-sql 确认流）——契约消息和提示词双重指向不存在工具。

## 为什么测试没拦住

`test_query_contract.py` 旧断言 `assert "kg_api" in c.allowed_tools` 把幽灵名锁死成了规格；
没有任何测试做「白名单 ⊆ MCP 实际注册工具集」的交叉校验。这是「测试验证规格、不验证集成」的典型案例。

## 影响面

- generic 模式整体不可用（最高频默认路径）；落地页示例「统计用电客户总数」直接命中；
- scenario 模式不受影响（其步骤 allowed_tools 均为真实工具名）。

## 修复落地（方案 A）

### 1. 契约白名单对齐真实工具（`query_contract.py`）
`GENERIC_ALLOWED_TOOLS` 去掉 `kg_api`，替换为 16 个真实 MCP 工具 + `read_file`：
- 定位类：`fetch_l1_l2_tree / validate_l2 / fetch_subgraph / search_entities / search_concepts / get_entity_relations / list_tables`
- 校验类：`validate_attributes / fetch_join_expr / validate_safe_sql`
- 源模式：`get_entity_source_mode / batch_entity_source_mode`
- 执行类：`execute_sql / execute_doris_sql / execute_api_sql / execute_entity_api`
- 框架：`read_file`

**安全不降级**：`ABSOLUTE_FORBIDDEN_TOOLS`（task/write_file/edit_file/execute/grep/glob）仍全局硬禁；
执行类仍走 `validate_safe_sql` / ScopeChecker / 引擎锁定既有闸门。语义与设计「低权限只读 fallback」一致。

### 2. 系统提示词去幽灵措辞（`tupu_deepagent.py`）
- `_COMMON_RULES`：「直接调 kg_api 工具」→「直接用只读工具（fetch_l1_l2_tree / search_entities / list_tables / get_entity_relations）定位」
- `_KNOWLEDGE_FLOW_RULES`：「调 kg_api 的搜索/查询 action」→「调只读元数据工具（…）」
- execute-sql 确认流：`kg_api(action="execute_sql")` → `execute_sql` 工具
- 模块 docstring 更新为 MCP 架构描述

### 3. 测试断言对齐（`test_query_contract.py`）
- 旧 `assert "kg_api" in c.allowed_tools` → 断言真实只读工具在列、`kg_api` 不在列。

### 4. 工具名册补全（`skill_catalog.py`）
`GLOBAL_TOOL_REGISTRY` 由 `GENERIC_ALLOWED_TOOLS | ABSOLUTE_FORBIDDEN_TOOLS` 派生，
白名单对齐后 `validate_l2 / search_concepts / get_entity_relations / list_tables / validate_safe_sql`
5 个此前缺失的真实工具自动入册（场景声明不再被「未知工具」误禁），并加注释说明。

### 5. 死代码清理（`tupu_deepagent.py`）
删除 `@tool kg_api`（631-647）整段死代码 + 不再使用的 `from langchain_core.tools import tool` 导入。

### 6. SSE 事件解析确认（无需改）
`data_intelligence.py` / `data_intelligence_support.py` 对工具名已是**双路径兼容**
（`kg_api` 旧名 + 真实工具名均处理），真实工具名有优雅回退，非阻塞。

### 7. 契约注入确认（无需改）
`data_intelligence.py:84` 是动态 `contract.allowed_tools` 拼接，白名单修复后 SystemMessage 自动展示真实工具。
