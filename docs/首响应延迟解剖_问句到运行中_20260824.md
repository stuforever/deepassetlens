# 首响应延迟解剖：「问句 → 小探正在运行中」的十秒去哪了

> 2026-08-24 · 设计窗口产出
> 现象：点击发送后约 10s 屏幕上没有任何助手侧反馈，直到首个 SSE 事件「小探正在运行中」到达。
> 根因定位：`data_intelligence_stream.py` 的**首个 yield 在 L250**——此前编排器要跑完全部准备工作，浏览器在首个字节前收不到任何东西。代码内既有佐证：L240 注明「v3.6 分段计时埋点：定位首响应延迟来源（6.73s 归因）」，说明此问题曾被测量过。

## 二、三个结构性浪费（不是慢，是不该花）

### W1 「先改写、后路由、再丢弃」顺序倒置 ★最冤
S3b 改写在路由**之前**执行（:112 区在路由前），而 :180 又规定「非 generic 路径丢弃改写用原问题」——意味着**场景命中的短问题白白付了最多 8 秒改写费然后扔掉结果**。改写应该只在 generic 路由确认后进行。

### W2 同一份 checkpoint 状态读了三遍
:84 / :104 / :125 三次独立 `aget_state`，各自完整反序列化全部历史消息（长会话时每次都随消息体积线性膨胀）。scope、last_skill、历史文本完全可以一次读取三处共用。

### W3 反馈被编排尾部阻塞（架构性）
首个可见事件排在全部准备之后。哪怕准备工作只花 2s，用户也要盯着空白等 2s——**感知延迟 ≥ 真实延迟**。

## 三、各场景的实际构成估算

| 场景 | 构成 | 总计 |
|---|---|---|
| 长会话短问题（如「那华东呢」） | 3×checkpoint 读 + **改写 ≤8s** + 检索 1~3s | **8~12s** ← 用户遇到的典型 |
| 长会话正常问题 | 3×读 + 检索 1~3s | 2~4s |
| 重启后第一问 | agent 冷启动 MCP 握手 2~5s + 读×3 + 检索 | 4~9s |
| 新会话首问 | 有 has_history 守卫跳过改写 ✓ + 检索 | 1~4s |

## 四、修复设计（新增批13-N，六招按性价比排序）

| # | 招 | 改动 | 收益 |
|---|---|---|---|
| N1 | **前端提交即显状态行**「正在理解问题…」 | 纯前端一行，不等任何后端事件 | 死区感知归零（治标但立竿见影） |
| N2 | **首个 status yield 提到生成器第一行**（锁之前） | 后端移动一段 | 后端反馈 <300ms |
| N3 | **三次 aget_state 合并为一次**，scope/skill/history 共用同一份 | 中等重构 | 省 2/3 checkpoint 反序列化 |
| N4 | **改写移到 generic 路由确认之后** + 预算 8s→3s | 顺序调整+常数修改 | 场景短问题 -8s；generic 最坏 -5s |
| N5 | **金标检索异步化**：status 先发，检索后台 task，注入前未完成则本题降级不带锚定 | 并行化+降级路径 | 首事件再 -1~3s |
| N6 | 冷启动预热：服务启动时预建 agent 单例 | 启动钩子 | 重启首问 -2~5s |

配套：prep 细分计时（lock/state×N/rewrite/route/retrieval/update 各段 ms）打进结构化日志，随批13-K timing 五段一起外露——修完有数可证。

## 五、结论

> 十秒 = 「三遍重复的状态读取 + 一段可能白付的 8 秒改写 + 一段同步的向量检索 + 一个排得太靠后的首个反馈事件」。其中 W1/W2 是纯粹的顺序与重复错误（修复零风险），W3 是感知问题（N1/N2 两行改动即可消除大半体感）。修复后目标：**任意问题的首个可见反馈 <500ms**，「小探正在运行中」不再是等待的结果而是发送的回声。
