# Skills 加载方式对照分析：我们的实现 vs Claude Code「方式三」

> 2026-08-20 · 设计窗口产出
> 对照对象：Claude Code 式生产实现——元数据以 user 角色 meta 消息注入上下文末尾（<system-reminder> 包裹）+ 增量发送 + 专用 Skill 工具按需加载全文。

---

## 一、我们先摆清自己的事实（基于历史代码分析）

| 环节 | 我们的实现 |
|---|---|
| 元数据 | SkillsMiddleware(skills=["/skills/"]) 把技能目录（name+一行简介，共 11 个技能）注入**系统提示区** |
| 全文加载 | 模型主动调 `read_file("/skills/sql-query/SKILL.md")`（FilesystemMiddleware 提供，只读权限） |
| 二级披露 | SKILL.md 之外还能读 templates/*.sql（户变关系单段变体模板就是 #2 步 read_file 读的） |
| 域后处理 | read_file 返回内容经 SkillEntityResolverMiddleware 把 ⟦中文名⟧ 机械替换成物理表名 |
| 路由 | **模型不选技能**——SkillRouter 在 Agent 外确定性路由，契约直接声明场景与步骤；模型只在 generic 兜底路径里自主挑技能文件 |

## 二、逐维度对照

| 维度 | Claude Code 方式三 | 我们 | 评注 |
|---|---|---|---|
| 元数据通道 | user-role meta 消息、**上下文末尾**、<system-reminder> 包裹 | system 提示区（技能目录段） | 通道哲学不同：他们把元信息当「消息」，我们当「规则」 |
| KV Cache | 不动 system 前缀 ✅；增量发送稳态零增量 ✅ | 目录在 system 前缀内=缓存覆盖区，稳态边际成本≈缓存价 ≈0 ✅；但技能增删会 bust 系统前缀 ⚠️ | **殊途同归**：都不做「每轮重发动列表」。差异只在技能库变更频率敏感度 |
| 注意力位置 | 末尾当轮最优；材料自己承认：增量元数据随后会话增长**滞留中部，优势衰减** | system 区注意力天然高且位置恒定；但同样存在滞留现象（见 §四） | 双方各有一半的同一问题 |
| 加载工具 | 专用 `Skill(skill:"pdf")`，语义化入口 | 通用 `read_file` | 执行倾向原理相同（都是「模型自己刚调用的工具」返回的 tool result）——方式三引以为傲的这点**我们天然也有** |
| 内容加工 | 无（原文返回） | ⟦⟧→物理表名机械替换（EntityResolver） | 我们多一层域加工，Claude Code 场景不需要 |
| 披露深度 | Skill 工具一般只出 SKILL.md | SKILL.md → templates/*.sql 两级 | 渐进披露粒度不同 |
| **路由权** | **模型看目录自己选**（模型=路由器） | **SkillRouter 在 Agent 外确定性路由**，模型选择空间被契约前置收窄 | **最大架构差异**，见 §三 |

## 三、最大差异：路由权在我们手里，不在模型手里

Claude Code 的方式三本质是「模型自治路由」：目录摆在那，模型自己判断哪个合适。这对通用助手是对的——任务千变万化，规则写不全。

我们的场景恰恰相反：**任务域窄且权限敏感**。所以做了双层分离：

```
Claude Code:  元数据 → 模型选 skill → Skill 工具加载 → 执行
我们(场景):   SkillRouter 关键词命中 → 契约直接绑定场景+步骤+模板
              → 模型的"选择"退化为"照剧本执行"（read_file 只是取剧本文本）
我们(generic): 目录在系统提示里 → 模型可自主 read_file 任何技能 ← 这层才接近方式三
```

这正是此前定过的安全立场的延续：**路由决定权限，权限不由采样决定**。模型自治路由意味着一句注入话术可能诱导选错技能；确定性路由面前，话术只能改变「模型想什么」，改变不了「走哪条路」。代价就是老话题——措辞敏感，靠触发词治理和示例直通缓解。

## 四、材料里那个「注意力衰减」问题，我们也有——为什么不怕

材料的洞察：注入当轮的「末尾优势」会随会话增长衰减。我们的对应物：**契约消息每问重建，位于该题 HumanMessage 之前**——第一题的轨迹全在它前面，多轮之后契约确实滞留在「当前题段的开头」而非整体末尾。

为什么我们没有为此改造：

1. **软约束失效有硬兜底**：契约里的关键安全项（允许工具/引擎锁/终止条件）不依赖模型注意力——SkillPolicy 五关每次调用强制执行，模板守卫 AST 级校验。注意力衰减最多让模型「忘了礼貌」，不能让它「越权做事」；
2. **每题重建=局部置底**：契约相对当前题永远是最近的规则文本，衰减速度远慢于「只发一次」的增量方案；
3. **规模小**：11 个技能的目录几百 token，塞 system 区毫无压力。

## 五、要不要改造成方式三？——YAGNI 结论

**不改。** 方式三的真实优势场景我们一个都不面临：

| 方式三的优势 | 对我们是否成立 |
|---|---|
| 技能库大（数十上百）需省目录 token | ❌ 我们 11 个，目录几百 token 且在缓存区内近乎免费 |
| 技能高频装卸（多租户/插件市场）会 bust system 前缀 | ❌ 技能变更以周计，bust 无感 |
| 需要当轮置底注意力 | 🟡 已论证：硬闸门使注意力衰减无害 |
| user-meta 通用注入模式 | 已有等价物：契约消息就是我们的 meta 通道（每题重建、位置受控） |

**登记触发条件**（满足其一再议）：技能数 >50；引入多租户动态技能装卸；实测发现 generic 路径模型选错技能文件的比率显著。

**反而值得偷师的一点**：<system-reminder> 式「包裹标签+角色声明」的元信息自标识写法，可以让契约消息更显式地自我声明（如 `<contract scope="scenario:distribution-overload" step="1">`），帮助模型区分「规则」与「数据」——低成本，可并入批5-C1 文案模板化一起做。

---

## 六、一句话总结

> 形似（都是「目录+按需加载全文」的渐进披露），神不同（他们让模型自治路由，我们在 Agent 外确定性路由并把选择权收进契约）。方式三为「大规模动态技能库+通用助手」而生；我们是「小规模静态技能+权限敏感域」——当前的 system 区目录 + read_file + 域后处理组合在其场景下没有短板，改造收益为零，登记触发条件即可。
