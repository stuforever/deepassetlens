# 第一部分：这套防御机制参考了什么？

## 结论先行

**没有一个现成开源方案被整体照搬。真实构成 = DeepAgents/LangGraph 原生扩展点（承载机制）+ 通用安全工程模式（设计思想）+ 本项目原创（域语义规则）。** 每个原子能力都有公开出处，组合方式是我们的。

### 第二层：通用安全工程模式（设计思想来源，非某仓库）

| 我们的设计 | 对应经典模式 |
|---|---|
| 契约白名单 allowed_tools | 能力制安全（capability-based）/最小权限原则 |
| SkillPolicy 每调用必检 | PEP/PDP 模式（策略执行点/决策点分离，零信任架构术语）：契约=PDP 的裁决书，SkillPolicy=PEP |
| fail-closed（契约丢失全拒绝） | deny-by-default 安全默认值 |
| 三层纵深（模板守卫→validate_sql→引擎锁） | Defense in Depth 纵深防御 |
| 模板指纹+【动态】槽位 | 预编译语句（prepared statement）思想搬到 NL2SQL：结构预编译、参数留槽 |

### 第三层：本项目原创（框架和通用模式都没有的域语义）

QueryContract 数据结构本身、场景剧本体系（SKILL.md+triggers+模板+entity_aliases）、错误分类学（TABLE_MISSING→重定位等语义级纠错路由）、stop_when 的语义终止（拿到结果即收窄）、示例库学习飞轮、金标 eval 双口径——这些是把上述模式**实例化到问数域**的原创部分。

## 一句话回答「引用了哪」

> 机制骨架站在 DeepAgents/LangGraph 肩上（这正是当初选它的理由：中间件协议天然适合插安全闸门）；设计语法来自教科书级安全模式（白名单/纵深/fail-closed/prepared-statement）；具体规则全是本项目为问数域写的。GitHub 上能找到的是「零件」，找不到「整车」。

# 第二部分：上下文拼接机制——一轮内、多轮、与缓存的关系

## 先纠正一个担忧：我们不「自行拼接」

你书上看到的原则（不要每次自行重组上下文，保持前缀稳定以最大化缓存）**正是当前实现的形态**：

- **拼接的所有权在框架**（LangGraph）：一轮问答内的消息列表由 Agent 循环维护，**只追加、不改写**；
- **我们在整条链路里只做一次构造**：入口处 `[SystemMessage(契约), HumanMessage(问题)]`，之后每一轮都是框架往列表尾部追加（AI 的工具调用、工具结果），我们从不动已有消息；
- **多轮对话靠 checkpoint 续接**：下一题读回上一题全部消息再追加新 HumanMessage——同样只追加。

## 一轮内逐步拼接实例（拿「统计用电客户数量」走一遍字节视角）

```
【发给模型的第 1 次请求】
┌─ 系统提示区（跨问题稳定段）
│   框架基础指令 + AGENTS.md 纪律 + 技能目录一行简介
│   + 契约消息（你能用什么/终止条件/输出模式…）      ← 同场景逐字节一致
│   + 工具 schema 列表（17 个，顺序固定）
└─ 消息区（本轮起点）
    [1] Human: 统计用电客户数量

【返回】AI: 我先读技能 → tool_calls=[read_file(/skills/sql-query/SKILL.md)]

【第 2 次请求】= 上面的完整内容原样在前 + 追加：
    [2] AI: tool_calls=[read_file…]
    [3] Tool: SKILL.md 内容（⟦⟧已被 EntityResolver 替换成物理表名）

【第 3 次请求】= 第 2 次 + 追加：
    [4] AI: tool_calls=[search_entities("用电客户")]
    [5] Tool: {entity_code: dim_cst_elec_cons_cust, …}

…以此类推直到第 5 次请求带着 4 轮完整轨迹…
```

**关键性质：第 N 次请求的字节内容 = 第 N-1 次请求 + 纯尾部追加。** 这正是服务端自动前缀缓存最喜欢的形状——R2~R5 可以复用 R1 已计算的前缀（prefill 不重算），TTFT 和费用双降。

## 多轮拼接实例

```
【第二题进入时】
agent.aget_state(checkpoint) → 读回第一题的全部消息 [1]~[N]
追加 [N+1] Human: 那上个月的呢（追问改写后的完整问题）
后续循环继续纯追加
```

第二题的请求前缀包含第一题全程 → 前缀缓存跨题也能吃（直到分叉点为止）。

## 缓存到底带来多少「快」——诚实测算

LLM 响应时间 = **prefill（读入全部上下文并计算）+ decode（逐字生成）**。缓存命中的是 prefill 部分：

- 以单轮 ~25s 为例：大前缀下 prefill 占比可观（估计 5-10s 量级），命中后可压到 1-3s；
- 180s 题（6 次调用）：若 R2-R5 全命中，总节省估计 15-30s——**有感但不是数量级**；
- 因为 decode（生成时间）不受缓存影响，而我们的瓶颈大头在轮次数和生成时间；
- 所以再次呼应架构评估的结论：**缓存是叠加增益（顺带账单降 ~90% 的命中部分），治本轮次仍是第一杠杆**。这也是为什么批5 排在批9（直通管道）之后。

## DeepSeek 自动前缀缓存怎么吃到的（无需代码）

DeepSeek 官方 API 的 context caching 是隐式的：请求进来按前缀查缓存，命中部分按约 1/10 计费且跳过重复 prefill。我们要做的只有两件事：①保前缀稳定（上面自查表）；②观测命中率（usage 里 prompt_cache_hit_tokens/miss_tokens 字段——批5-C4，需先探测 ChatOpenAI 是否透传该字段）。
