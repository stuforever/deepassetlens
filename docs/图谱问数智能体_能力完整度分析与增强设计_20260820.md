# 图谱问数智能体 · 能力完整度分析与增强设计

> 2026-08-20 · 设计窗口产出（不动代码）
> 说明：开源调研基于模型知识库（web_search 因 API key 未配置不可用）；Vanna/DB-GPT/WrenAI/SuperSonic 均为架构稳定的成熟项目，本文引用其核心机制可靠，**版本号新特性建议后续联网复核**。
> 结论预览：tupu 的「语义底座 + 受控执行治理」在同类中属第一梯队，但「**准确性反馈闭环**」缺三块关键拼图：示例检索、自纠错、结果验证。

## 二、开源同行调研

### 2.1 五个代表性项目的能力提取

| 项目 | 核心机制 | 强项 | 弱项 |
|---|---|---|---|
| **Vanna** | RAG Text2SQL：`train(DDL/文档/问答对)` 存向量库，问句时检索 top-k 相似示例注入提示词 | **动态 few-shot 检索**（问过即积累，越用越准）；用户纠正可直接入库；多库多模型适配 | 无语义层治理、无执行管控，纯提示词工程 |
| **DB-GPT** | AI 数据应用框架：Chat Data/Excel/Dashboard/Knowledge 多模块 + AWEL 工作流 | 生态全（仪表盘生成、知识问答）；DB-GPT-Hub 提供微调评测路线 | 框架重；Text2SQL 准确率依赖提示词/微调，无 KG 锚定 |
| **WrenAI** | 语义层（MDL）+ 检索 + 生成 + **纠错循环**（SQL 校验失败自动重写重试） | 语义模型管理 UI；**correction loop 是其准确性核心**；结果摘要 | MDL 手工维护成本高；无图谱 |
| **SuperSonic**（腾讯） | HeadlessBI 语义层（维度/指标/本体）+ ChatBI 双层架构 | 语义层即治理的思路；词表+LLM 混合解析 | Java 技术栈；语义层手工建模重 |
| **Dataherald** | NL2SQL 引擎：表结构检索 + 模板 + **验证答案库** + 列画像 | **列值画像**（枚举值分布供模型参考）；验证答案优先匹配 | 项目已停维护；无 agent 架构 |
| （参照）Chat2DB / PandasAI | AI 数据库客户端 / 对话式 DataFrame | 开发者侧 SQL 生成 | 非 BI 场景，可比性弱 |

### 2.2 同行共性能力清单（成熟度从高到低）

1. **Few-shot 示例检索**（Vanna 核心专名能力，Dataherald 的 verified answers 是其手工版）
2. **自纠错循环**（WrenAI 核心准确性机制）
3. **列值画像/取样**（Dataherald 列画像；各家的 schema linking 配套）
4. **自动可视化**（DB-GPT dashboard、Vanna plot、WrenAI 图表）
5. **反馈学习**（Vanna 用户纠正入库）
6. **语义层治理**（WrenAI MDL、SuperSonic HeadlessBI）--**tupu 已有等价物且更厚（图谱+指标+归一表）**
7. **评测基准**（DB-GPT-Hub 微调评测；各家用 Spider/BIRD 数据集自评）

## 三、能力差距矩阵

### 3.1 tupu 领先项（守住）

| 能力 | tupu | 最强同行 |
|---|---|---|
| 语义底座 | **图谱+向量+指标三层**，行业域层级+JOIN 关系来自图 | WrenAI/SuperSonic 手工语义层 |
| 执行治理 | **契约级**（白名单/引擎锁/模板守卫/受控降级/审计五卡） | 无一家有等价物 |
| 多源联邦 | 三引擎+加速器+缓存+熔断（本期刚建成） | 各家单库为主 |
| 安全 | SQL 只读校验+作用域检查+沙箱白名单 | 一般仅 SQL 校验 |

### 3.2 缺口（按准确性影响排序）

| # | 缺口 | 同行参照 | 影响 |
|---|---|---|---|
| G1 | **验证示例库 + 动态 few-shot 检索**：问过的好查询不沉淀，每次都从零拼 | Vanna | 准确性最大杠杆缺失；基建（Qdrant）已就绪却未用于此 |
| G2 | **自纠错闭环**：错误分类学已建但只用于报错/一次降级，未驱动重写重试 | WrenAI | 可修的错（列名/语法/过滤值）直接失败给用户 |
| G3 | **列值取样**：分类列过滤值靠模型猜（"重过载"具体是什么枚举值） | Dataherald | WHERE 条件错是灵活问数错误主要来源之一 |
| G4 | **结果验证**：空结果/异常值/高空值率不做诊断 | 各家有零星 | 错了不知道错 |
| G5 | **反馈闭环**：无 👍/👎，无纠正入库 | Vanna | 学习飞轮不存在 |
| G6 | **金标评估集**：无准确率回归 | DB-GPT-Hub | 准确性改进无法度量 |
| G7 | **证据链/置信度展示**：用户看不到"这个答案怎么来的、多可信" | - | 信任建立弱 |
| G8 | **自动图表**：只有表格 | DB-GPT/Vanna/WrenAI | 结果消费效率 |
| G9 | **追问改写**：会话记忆存在但无实体/口径继承的语义改写 | 各家多轮能力 | "那上个月呢"式追问体验 |

## 四、灵活问数准确性保障体系（核心专项设计）

准确性 = 五道防线，前两道已有强基础，补后三道：

```
问题 ──> ① 语义对齐 ──> ② 构造正确 ──> ③ 执行验证 ──> ④ 置信披露 ──> ⑤ 反馈学习
        (补G1/G3)      (补G2)          (补G4)         (补G7)        (补G5/G6)
             ▲                                                        │
             └────────────── 验证示例库（学习飞轮） ◄──────────────────┘
```

### 防线① 语义对齐（已有 70%，补 G1+G3）

**G1 验证示例库（Verified Example Store）--本期最重要单项**

```
新表 kg_verified_qa_examples：
  id / question_norm(归一化问题) / question_raw / sql / entity_codes(JSON)
  / metric_id / engine / example_type(user_confirmed | auto_mined | manual)
  / hit_count / last_used_at / status(enabled|disabled) / created_at

Qdrant 新集合 tupu_qa_examples：问题 embedding -> example_id
（复用 TupuQdrantClient 与现有 embedding 管线，零新基建）
```

- **捕获**：a) 用户点 👍 且未改 SQL；b) 用户手动录入（管理界面）；c) 结果被采纳信号（追问/导出，暂缓）
- **注入**：QueryContract 构造时检索 top-3 相似示例，写入契约 SystemMessage 的「参考示例」节（受控上下文，模型只读）；generic 与 scenario 模式都注入
- **治理**：示例 SQL 不直接执行（仍走模板守卫/引擎锁定/作用域检查）；禁用/审核入口挂指标中心同款管理页风格
- **失效**：实体/表结构变更事件 -> 相关示例自动 disabled（挂 schema 漂移检测已有的钩子）

**G3 列值取样工具（MCP 第 17 个工具）**

```python
@mcp.tool()
def sample_column_values(entity_code: str, column: str, limit: int = 50) -> dict:
    """取分类列的 distinct 值+频次（写 WHERE 前必查，防枚举值猜测）。缓存 10 分钟。"""
```

- 系统提示词加一条硬规则：对分类/状态类列写 WHERE 前**必须**先取样
- 加入 GENERIC_ALLOWED_TOOLS 与交叉校验测试（白名单测试会自动覆盖）
- 实现走现有引擎层（DuckDB/Doris 均可 `SELECT val, COUNT(*) ... GROUP BY`）

### 防线② 构造正确（已有 80%，补 G2）

**G2 自纠错闭环（Error-Driven Rewrite Loop）**

- **现状可复用件**：错误分类学 6 类、契约 violations 计数、Unknown column 单点自动修复、受控降级一次、EXPLAIN API（引擎批3）
- **设计**：execute 出错后，SkillPolicy 在 ToolMessage 附结构化纠错指引（非裸错误串），由 agent 在**契约白名单内**重写重试，上限 2 次：

| 错误类 | 纠错指引（注入给模型） | 工具 |
|---|---|---|
| TABLE_MISSING | 附 search_entities/list_tables 建议提示 | 已有 |
| SYNTAX / 列名错 | 附 validate_attributes 校验建议 | 已有 |
| TIMEOUT | 指引去 ORDER BY / 加 LIMIT / 换预聚合 | 已有 |
| 空结果 | 指引 sample_column_values 检查过滤值 + 日期范围复核 | G3 新增 |

- **预检**：执行前先 EXPLAIN（毫秒级）--SYNTAX/TABLE_MISSING 提前暴露，省一次完整执行
- **与受控降级的关系**：纠错=同结构重写（语法/参数层），降级=换引擎/换表（结构层），互补不重叠；每次纠错记 `correction.attempt` 治理事件
- 上限 2 次后仍失败 -> 明确失败卡片（不再无限循环，P0 事故教训）

### 防线③ 执行验证（新，补 G4）

结果返回后自动跑三项轻检查，产出 `verification` 字段：

1. **空结果诊断**：row_count=0 时区分「数据真没有」vs「条件写错」--自动触发列值取样比对过滤值、日期范围检查，结论写进结果
2. **偏差预警**：数值结果与 MetricQueryLog 历史同口径对比，偏差 >3σ -> 附加 warning（不阻断）
3. **空值率检查**：关键输出列空值率 >80% -> warning「可能选错列」

### 防线④ 置信披露（新，补 G7）

- **第六张业务卡 EvidenceCard（证据链）**：本次回答用了哪些实体/表/参考示例/校验步骤/验证结论，复用 contract cards 组件规范
- **置信度三级标注**：高（模板+示例命中+验证通过）/ 中（KG 校验通过）/ 低（自由拼装无验证）--标在答案头部，不装不说

### 防线⑤ 反馈学习（新，补 G5+G6）

- **G5 反馈闭环**：SqlResultTable 与最终答案加 👍/👎；👍+未修改 SQL -> 自动入示例库（user_confirmed）；👎 + 用户改 SQL -> 进审核队列；管理页可审核/禁用
- **G6 金标评估集**：`kg_golden_qa_set`（50-100 条：问题/标准 SQL/期望结果摘要/场景标签）；发布清单新增「金标准确率 ≥90%」硬门槛（执行比对结果而非比对 SQL 文本）；准确率趋势进引擎工作台总览

## 五、建议引入能力总表（优先级与量级）

| 批 | 能力 | 解决 | 量级 | 依赖 |
|---|---|---|---|---|
| **批A 准确性核心** | G1 示例库+检索注入、G3 列值取样、G2 自纠错+EXPLAIN 预检 | 灵活问数准确性主矛盾 | ~5 天 | Qdrant（已有）、错误分类（已有） |

| **批C 学习与运营** | G5 反馈闭环、G6 金标评估集 | 飞轮转起来、改进可度量 | ~3 天 | 批A 示例库 |

顺序 A→B→C→D；批A 完成即可宣称「准确性体系成型」，批C 完成后系统开始自我变准。

## 八、不做清单（明确边界）

| 不做 | 理由 |
|---|---|
| Text2SQL 模型微调（DB-GPT-Hub 路线） | 金标数据量不足百条；few-shot 检索可覆盖大部分收益；微调维护重 |
| 重型图表库（recharts/@ant-design/charts） | 先零依赖轻实现验证价值，YAGNI |
| 通用 BI 仪表盘搭建 | Superset/Metabase 领域，偏离问数定位 |
| Java 式语义层重写 | 图谱+指标+归一表已是等价物且更厚 |
| 无约束自由 agent / 放开工具白名单 | 与受控平台核心设计冲突（P0 事故的反面教训） |
| NL2Cypher 图原生查询 | CypherTemplate 已有基础，作为独立课题另立（不在本期混做） |
| 多用户协同/权限体系扩展 | 现有 scope 检查够用，单机演示场景 |
