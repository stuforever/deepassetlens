## 批1-A 答案直流产出区（前端，消灭「日志上屏」+ 30s 观感死等）

### 现状（已核实）

- `FreePlanChat.tsx:302-326`：think_token 事件按 round_id 缓冲，rAF 批量刷新；
- `:797-834 flushTokens`：answer_draft 写入 ThinkStream 项 `{kind:'answer', field:'draft', task:'答案生成'}`——**答案全文流进思维链面板**（用户看到的「日志」）；
- `:429-461 answer_committed`：完整正文写入 `payload.final_answer`（done 兜底用）；
- `:296-298 final 事件`：`patchAssistant({final_answer})` → 输出区；
- `:639-657 done 兜底链`：`done.final_answer → payload.final_answer → liveThinkStream 中的 answer draft`。

### 改法（四处）

**A1. 新增流式答案字段**（flushTokens 内，:810-827 循环体中 answer_draft 分支）：

```ts
// answer_draft token 双写：ThinkStream 只留状态，正文进 payload.streaming_answer
if (kind === 'answer_draft') {
  const prevStreaming = messages[i].payload?.streaming_answer || '';
  const roundChanged = lastAnswerRoundRef.current && lastAnswerRoundRef.current !== roundId
                       && messages[i].payload?.answer_committed;   // rubric 修订：新一轮答案
  messages[i].payload = {
    ...(messages[i].payload || {}),
    streaming_answer: roundChanged ? combined : prevStreaming + combined,
    answer_revising: roundChanged ? true : (messages[i].payload?.answer_revising || false),
  };
  lastAnswerRoundRef.current = roundId;
  // ThinkStream 的 answer 项只保留状态（不再累积全文）：
  ts[idx] = { ...ts[idx], draft: '', phase: 'drafting' };  // 或该项 task 显示「答案生成中」
}
```

- `lastAnswerRoundRef = useRef<string>('')`（组件顶部，与 tokenBufRef 并列）；
- ThinkStream answer 项**不再承载正文**（draft 置空，仅作「答案生成中/已完成」状态步骤）；跨轮归并逻辑（:815-819）保留。

**A2. 答案气泡实时渲染**：消息渲染区（payload.final_answer 渲染处）改为：

```tsx
const live = m.payload?.final_answer || m.payload?.streaming_answer || '';
// loading 中显示 streaming_answer（流式），final 后 final_answer 校准覆盖
```

- 加「校验修订中」小徽标：`m.payload?.answer_revising && m.loading` 时显示（warning 色，12px）。

**A3. answer_committed 联动**（:432-461）：置 `payload.answer_committed = true`、`answer_revising` 保留至 rubric 事件到达再清；正文校准逻辑不变。

**A4. done 兜底链更新**（:639-657）：`resolveFinalAnswer` 第三优先级从「ThinkStream answer draft」改为「payload.streaming_answer」（A1 后 ThinkStream 不再存全文）。

### 数据流

```
模型 answer_draft token ──> payload.streaming_answer ──> 答案气泡实时成型
rubric 评分中（后端）     ──> 无事件 ──> 气泡已可读，无死等
rubric 需修订            ──> 新 round answer_draft ──> 气泡重置续流 + 「校验修订中」徽标
final 事件              ──> payload.final_answer 校准（防丢字）
rubric 事件（:974）      ──> 清 answer_revising + 更新置信度徽标（见批1-B 前端部分）
```

### 验收点

1. Playwright e2e 跑「统计用电客户数量」：答案**首 token 起即在输出区气泡逐字成型**；ThinkStream 面板无答案全文（只有状态步骤）；
2. rubric 触发改写时（构造一个高风险问题），气泡显示「校验修订中」且内容续流替换，无 30s 白屏；
3. done 兜底链不回归：断开 final 事件的异常路径仍能从 streaming_answer 兜底；
4. 多会话切换不串流（streamingSidRef 机制覆盖新字段）。

## 批1-B rubric 分档直通（后端，消灭每问 30s 税）

### 现状（已核实）

- `query_contract.py:163`：generic 契约一律 `rubric=GENERIC_RUBRIC`；
- `data_intelligence_stream.py:264-267`：`_contract.rubric` 非空 → 注入 invoke state → RubricMiddleware 激活；
- `data_intelligence.py:109-133`：示例注入在契约消息构造时完成，命中写 `_runtime["example_hits"]`（hits 含 `score`/`sql`，qa_example_service.build_examples_payload 返回 `{block, hits:[{id,score,question_raw,sql,route_type}]}`）。

### 改法（两处）

**B1. 分档函数**（query_contract.py 新增，~15 行）：

```python
EXAMPLE_ANCHOR_SIM = 0.85   # 环境变量 TUPU_RUBRIC_ANCHOR_SIM 可调

def apply_rubric_tier(contract) -> None:
    """示例锚定直通：有高分已验证示例锚定的 generic 查询跳过 rubric 自评。
    依据：模板/示例锚定的 SQL 已有确定性保障（守卫+引擎锁定+金标回归），
    grader 边际价值≈0 且固定 +20~40s。未锚定查询保留自评。"""
    if contract.route_type != "generic" or not contract.rubric:
        return
    hits = (contract._runtime or {}).get("example_hits") or []
    if hits and max((h.get("score") or 0) for h in hits) >= EXAMPLE_ANCHOR_SIM:
        contract.rubric = None
        contract._runtime["rubric_skipped"] = "example_anchored"
```

**B2. 调用点**（data_intelligence_stream.py，:187 契约消息构造之后、:264 rubric 注入之前）：

```python
# 批1-B：示例注入完成后按锚定强度分档（_build_contract_system_message 已写 example_hits）
from app.services.query_contract import apply_rubric_tier
apply_rubric_tier(_contract)
```

- 观测：`rubric_skipped` 经 run_event_sink 记录（`rubric.skipped` 事件），运营可看直通率；前端 EvidenceCard 自评区显示「示例锚定直通」而非「中」。

**前端配套**：新增 rubric 事件监听（stream :974 已发）：更新 `payload.evidence.rubric` + 置信度徽标 + 清 `answer_revising`。

### 边界

- 示例分不足（冷启动/新问题）→ rubric 照常，无回归；
- 示例 SQL 过时（schema 漂移）→ 执行报错走既有纠错循环（≤2 次），与 rubric 无关；
- 聚合分布类问题（S1 的 P-A 不稳定源）**不豁免**：aggregate_intent 命中时不直通（在 apply_rubric_tier 加 `if getattr(contract, "aggregate_intent", None): return`）——这类正是需要自评兜底的。

### 验收点

1. 单测 test_rubric_tier：高分命中→rubric=None；无命中→保留；aggregate_intent→保留；
2. e2e：「统计用电客户数量」（与金标「统计用电客户总数」高相似）不再产生 grader 调用（后端日志无 rubric 评分记录）；
3. 无示例问题（如新实体问法）rubric 正常激活。

## 批2-C 示例直通首选计划（后端，5 轮 → 2 轮的核心杠杆）

### 现状

示例块只写「仅供参考，禁止照抄执行」（qa_example_service.build_examples_payload），模型仍需走完整 定位→源模式→执行 流程。

### 改法（data_intelligence.py:109-133 示例注入块内）

```python
_DIRECT_PLAN_SIM = 0.90   # 比展示阈值(0.75)/rubric 直通阈值(0.85)更严，环境变量可调
if _payload["hits"]:
    _top = max(_payload["hits"], key=lambda h: h.get("score") or 0)
    if (_top.get("score") or 0) >= _DIRECT_PLAN_SIM and _top.get("sql"):
        base += (
            f"\n首选计划（已验证示例，相似度 {_top['score']:.2f}）：直接执行以下 SQL 作答，"
            f"跳过实体定位与读技能步骤；示例引擎={_top.get('engine') or '未记录'}，"
            f"用对应执行工具（doris_catalog→execute_doris_sql，物理→execute_sql）。"
            f"仅当执行报 TABLE_MISSING/列名错误时回退常规定位流程（search_entities→batch_entity_source_mode）。\n"
            f"SQL：{_top['sql']}"

```

- kg_verified_qa_examples 已有 engine 列（融合设计 §4.1 表结构）——若当前迁移未含 engine 值回填，直通块降级为「引擎未记录→先 batch_entity_source_mode 一次再执行」（仍省定位轮）；

### 验收点

## 八、缓做项 H：聚合统计场景化（观察期决策）

**不建议现在做**。理由：示例直通（批2-C）+ 实体预解析（批2-D）已把高频统计问法压到 2-3 轮；新场景意味着每类实体一套 COUNT/GROUP BY 模板（scenario_strict 需固定表集合，跨实体参数化模板与 strict 哲学冲突，只能 extensible），维护面大。观察期（2 周）：若金标/线上显示统计类问题在无示例时仍频繁超 60s，再立项做「aggregate-query 场景（extensible 模板 + 触发词全变体：总数/数量/多少/几个/统计）」。

## 九、风险登记

| 风险 | 对策 |
|---|---|
| 示例直通 SQL 过时（schema 漂移） | 既有漂移事件禁用示例 + 执行报错走纠错循环（≤2 次封顶） |
| rubric 直通放过坏答案 | 阈值 0.85 从严 + aggregate_intent 不豁免 + 直通率/准确率金标双看板监控，恶化即回调阈值 |
| 前端 streaming_answer 与 final 校准不一致 | final 为唯一权威源（覆盖式赋值），streaming 仅是 loading 态展示 |
| 修订轮重置误伤（非 rubric 的多轮答案） | roundChanged 判定要求前轮已 answer_committed，否则仍归并（沿用现有跨轮归并语义） |
| 阈值三档（0.75 展示/0.85 rubric/0.90 直通）混淆 | 全部环境变量化 + query_contract.py 顶部集中定义 + 注释说明各自用途 |
