# 五问详解：缓存 / 路由 / 示例写入 / 实体定位与图检索 / 模板直出可行性

> 2026-08-20 · 设计窗口产出（逐条对照代码与配置实查）
> 对应五个追问：①上下文能否完全缓存 ②四级路由是不是 LLM 判断 ③示例库何时写入、新问题耗不耗时 ④实体定位走不走本地向量/图检索 ⑤答案生成不让大模型总结的可行性。

## 问一：上下文机制，能否做到完全缓存？

**结论：协议层做不到「完全缓存」；服务端隐式前缀缓存可以最大化利用；且缓存治标（延迟/账单），治本靠减轮次。**

### 三层事实

| 层 | 事实 |
|---|---|
| 协议层 | 我们走 OpenAI 兼容协议，**没有** Anthropic 式 `cache_control` 显式断点。DeepAgents 0.7.x 新增的 prompt-caching 中间件**只支持 Anthropic/Bedrock**（0.6.12 vs 0.7.7 wheel diff 已分析），对 DeepSeek/GLM 无效 |
| 服务层 | DeepSeek 官方 API 有**自动前缀缓存**（隐式、免代码）：前缀逐字节一致即命中，缓存命中部分按约 1/10 价格计费且 TTFT 显著下降；GLZ/Zhipu 亦有同类 context caching 计费 |
| 结构层 | 命中与否完全取决于「前缀是否稳定」 |

### 我们现状对缓存的友好度盘点

**有利**：轮内 append-only——同一问题的 R2~R5 轮，系统提示+契约消息+历史只追加不改写，天然构成可缓存前缀（R2 起吃 R1 的缓存）。

**破坏点排查**：
- 契约消息无时间戳/run_id ✅（不会逐请求变化）
- 工具 schema 顺序固定（MCP list_tools 顺序稳定）✅
- **Summarization 摘要重写历史 → 前缀全变，缓存全失效**（长会话才触发，短问无感）
- 跨问题共享止于系统提示段（HumanMessage 是问题本身，逐题不同）

### 可做优化（不改协议）

1. 契约文案**模板化稳定措辞**：同场景逐字节一致 → 跨问题也能共享系统提示+契约前缀；
2. 每问变化的内容（用户问题、示例块）放消息尾部，不动前缀；
3. 摘要阈值保守化，避免中途重写历史 bust 缓存；
4. 工具 schema 排序固化。

### 上限认知

缓存省的是「重复前缀」的**预填充计算与费用**；每轮新增的工具结果与答案 token 必须现算。**它降 TTFT 和账单，不减少轮次**——180s 的治本手段依然是批1-B（rubric 分档）+批2（减轮次），缓存是叠加增益而非替代。

## 问二：四级路由，不是 LLM 思考判断的吗？

**结论：不是。四级路由是纯代码关键词匹配（毫秒级/零成本/确定性），这是受控平台的有意设计。**

### 为什么故意不用 LLM 判断

1. **路由=权限边界**。路由结果决定契约（能用哪些工具）。让 LLM 判路由 = 让模型自己决定自己的权限——不可复现、不可审计、有采样方差。安全架构上不能接受；
2. **可测试性**。金标 eval 要求同问题永远同路径，LLM 路由会让评估失真（今天走场景明天走 generic，准确率没法归因）；
3. **成本与时延**。LLM 路由 = 每问 +1 次调用（1-3s）；关键词匹配毫秒级；
4. **模型的思考放在该放的地方**：路由之后的 ReAct 循环（选工具/写 SQL/作答）才是 LLM 判断的主场——路由管「走哪条路」，模型管「路上怎么开」。

### LLM 参与的两个间接点（设计内）

- **追问改写**：LLM 改写后的完整问题再进路由（改写是 LLM 的，路由判定仍是规则）；
- **澄清卡**：多场景撞车时不出 LLM 判断，而是把候选摆给用户选——用户当裁判。

### 代价与折中

代价=**措辞敏感**（「总数」vs「数量」踩过多次）。折中路线（已在设计中）：触发词全变体维护、批2-E 规则意图分类预载指引、示例直通降低路由重要性。若未来引入「轻量 LLM 路由」，约束应为：仅限 generic 内部的意图细分（不碰场景/generic 边界）、快模型+低温+受限枚举输出、结果落治理日志可回放。

## 问三：示例检索是什么时间写入的？新问题耗时吗？

### 写入时机（三个来源，均为一次性写入）

| 来源 | 类型 | 时机 |
|---|---|---|
| 金标集灌入 | example_type=golden | eval/脚本批量写入（已有先例：2974ac3「5 条金标兼灌示例库+Qdrant」；S2 扩容时同步灌） |
| 用户 👍 反馈 | user_confirmed | feedback_service 收到确认 → 入库 + Qdrant upsert（**运行期持续增长的主通道**） |
| 管理页录入 | manual | /qa-examples 页面 CRUD |

写入动作 = 算 embedding + upsert 到 `tupu_qa_examples` 集合，**每条一次，不占问答耗时**。

### 新问题耗时吗？

**耗时，且命中与否都花同样的钱**：每次提问在契约消息构造期同步执行 embedding HTTP + Qdrant search ≈ **0.5~3s**（180s 里的一小笔）；库里没相似示例时返回空、静默跳过注入——检索费照付。

优化（已设计/可选）：
- 批2-D：与实体预解析**共用一次 embedding 调用**（搜两个集合，不加远程调用）；
- 可选小优化：同问题短时间窗内缓存检索结果（重复提问免检）。

## 问四：定位实体走的是本地向量吗？图检索没用到吗？

**核实结果（可能出乎意料）：都不是。MCP 工具层的实体定位是纯 MySQL 关键词匹配；整条问答链路零 Neo4j 引用。**

### 代码实据

| 环节 | 实现 | 向量？ | 图？ |
|---|---|---|---|
| `search_entities`（MCP 工具） | kg_action_handlers：kg_entities 表 LIKE/精确 code 直查（MySQL） | ❌ | ❌ |
| `get_entity_relations` | MySQL `kg_entity_relations` JOIN `kg_entities` 关系表查询 | ❌ | ❌（关系是关系表建模，非 Neo4j 遍历） |
| `fetch_subgraph` | skill_injections.build_fetch_subgraph_by_l2（L2→实体映射，MySQL 支撑） | ❌ | ❌（Neo4j 零引用） |
| 整条 freeplan 链路中唯一的向量消费点 | G1 示例注入（qa_example_service，契约构造期） | ✅ 仅此一处 | - |
| hybrid_retrieval（同义词扩展+向量混合） | 服务于 standard_semantic_service（标准语义服务），**不在 Agent 工具层** | - | - |

### 架构事实与判断

「图谱问数」当前实际跑在 **MySQL 元数据关系表 + 关键词工具** 上；Neo4j 服务于链路之外（可视化等），Qdrant 在主链路仅示例库一处。这既是坦白也是机会：

**改进建议（低风险高收益）**：把 `search_entities` 内部升级为混合检索（同义词扩展+向量召回+MySQL 过滤融合排序）——hybrid_retrieval 能力现成，工具签名/白名单/调用方式全不变（对模型透明）。收益：「配变」「专变」这类口语词的召回显著改善（现在 LIKE 匹配不上就找不到）。风险控制：向量引入排序不确定性 → 分数阈值+同分确定性排序兜底，金标 eval 回归护航。

## 问五：答案生成不让大模型总结的可行性？

**结论：可行，且应分档实施——这是比 rubric 分档更大的提速杠杆。高频问题可以做到 0 次 LLM 调用、2~4 秒出完整答案。**

### 模板直出的成立条件（三条同时满足）

1. SQL 已验证（场景剧本或示例锚定，sim≥0.95）；
2. 结果形态可枚举（row_count / 聚合行——答案槽位能从工具结果直接取值）;
3. 不需要自由推理的发现（不做「样本显示运行容量普遍高于合同容量」这类判断）。

### 先例已经存在

distribution-overload SKILL.md :202 本来就是一份**填空模板**（「一句话结论：共 X 个台区…重载 A 台…占有率最高用户 W（V%）…」）——现在是模型照着填，完全可以换成代码渲染器填槽。

### 激进形态：直通管道（高频问题零 LLM 轮）

```
触发：示例锚定 sim≥0.95 且问题无未解析动态条件（无日期/客户名过滤诉求）
流程：契约(直通标记) → 代码直取验证 SQL(example.engine 定执行工具)
      → validate_sql 安全校验 → 引擎执行 → 模板渲染器填槽(row_count/聚合行/scope 注释)
      → 流式输出答案 + sql_result
全程 0 次 LLM 调用；rubric 免评（确定性输出无需自评）；SkillPolicy 闸门照过（安全不降级）
```

### LLM 必须保留的场景

- 自由问答/无锚定问题（措辞千变万化，模板覆盖不了）；
- 多步综合解读（倒排三步的「谁是重过载主因」需要判断）;
- 样本观察类发现（模板推不出趋势/对比措辞）；
- 澄清对话、追问改写。

### 风险与对策

| 风险 | 对策 |
|---|---|
| 答案僵化 | 模板留变量段（后续建议从历史 recommend 统计取 TopN） |
| 动态条件解析难（日期/客户名要填进 WHERE） | v1 只做「无动态条件」的精确命中；带条件仍走 Agent（【动态】片段机制留给场景路径） |
| 双路径答案风格不一致 | 渲染器与 A-E 契约共用文案常量；金标 eval 双口径回归 |
| 直通误触发 | sim≥0.95 从严 + 动态条件检测从严；直通率/准确率双看板监控 |

### 收益量化与排序

高频统计类问题：当前 ~25s（示例直通后 2 轮）→ 模板直出 **2-4s（0 轮）**，且完全确定性。实施排序：批1(P0) → 批2(减轮次) → **批4：模板直出 v1**（仅精确锚定+无动态条件，观察直通率后再扩）。

## 总览：五问一句话

| # | 问题 | 一句话答案 |
|---|---|---|
| 1 | 完全缓存？ | 协议不支持显式缓存；DeepSeek 自动前缀缓存可白吃（保前缀稳定即可）；但缓存省钱省 TTFT 不省轮次，治本靠减轮次 |

| 5 | 不让 LLM 总结？ | 可行且推荐分档：锚定+可枚举结果 → 模板直出（剧本里本来就有填空模板），高频题 0 轮 2~4s；自由问答保留 LLM |
