## 二、逐阶段详解

### S1 会话准备（data_intelligence_stream.py:100-110）

- 按 thread_id 取 agent 单例（`_GLOBAL_AGENTS` 缓存 + AsyncSqliteSaver），会话级锁防并发；
- `agent.aget_state(config)` 读 checkpoint：本问题是**首轮**，`last_skill` 为空 → 连续上下文不沿用，进入新路由（若是多轮追问且上轮已是 distribution-overload、本轮无新场景触发词，则直接沿用上轮 skill+step）。

### S2 追问改写（S3b，:112-147）

- 纯规则触发：`is_followup_question` 判「短问题(<12字) || 含指代词(那/它/上述/该/也/再)」；
- 本问题 18 字、无指代词 → **不触发**，`_effective_question` = 原问题；改写超时 8s 硬封顶/异常均回退原问题（不阻塞）。

### S3 路由（skill_router.py:85-103）

判定链：①连续上下文（无）→ ②精确场景匹配 → ③澄清（多命中）→ ④generic。

- `_match_scenarios`（:149-160）：遍历启用剧本，`match_any_keywords` 命中「户变关系」→ **distribution-overload** 单命中（无多场景冲突 → 不需澄清）；
- `_select_step`（:182-204）：步骤循环，relationship 步 triggers.any 含「户变关系」→ 选定；`step_hit_rule="step.triggers: 户变关系"`；
- 返回 RouteResult(route_type="scenario", skill_id="distribution-overload", workflow_step="relationship", ...)。

### S4 契约构造（QueryContract.from_step）

| 契约字段 | 本问题取值 |
|---|---|
| allowed_tools | [batch_entity_source_mode, execute_doris_sql, execute_api_sql, execute_entity_api, execute_sql] + 自动注入 read_file |
| template_ids | ["distribution-overload:templates/step1_household_transformer.sql"] |
| stop_when | ["sql_result.row_count >= 0"]（allowed_next 空 → 终端步骤） |
| route_type | scenario；rubric=None；template_mode=scenario_strict |
| output_mode | single_result_table；forbid_markdown_detail_table=True |
| engine | 未锁定（等 batch 裁决）；engine_reason="" |
| forbidden | task/write_file/edit_file/execute/grep/glob（剧本声明） |

### S5 契约注入 + G1 示例检索（:184-188 / data_intelligence.py:71,111-121）

- `input_messages = [SystemMessage(契约全文), HumanMessage(有效问题)]`；
- G1：`qa_example_service.build_examples_payload(question)` → Qdrant 检索 top-3（阈值 0.75）→ 命中写入 `_runtime["example_hits"]` + 累计 hit_count，追加到契约尾部「参考示例（仅供参考，禁止照抄）」；本问题语义与金标 5 条不贴近，大概率零命中/低相似度 → **示例不注入，靠模板兜底**（这正是场景模式的意义：示例引擎服务于 generic）；
- `aupdate_state` 写回 last_skill/last_step（:197-206）。

### S6 ReAct 循环（受控中间件栈内）

**中间件栈装配**（create_tupu_agent 内）：PatchToolCalls → SkillPolicy(契约闸门) → SkillEntityResolver(⟦⟧解析) → DataSummary → DecisionGate(下一步判断流) → 框架件(Skills/Filesystem/Memory/Summarization)。

**6a 读剧本与模板**：
- 模型按系统提示词规则（tupu_deepagent.py:100「不要用 glob/ls，用只读工具定位」）调 `read_file(SKILL.md)` 与 `read_file(templates/step1_household_transformer.sql)`；
- **SkillEntityResolverMiddleware**：把模板中 ⟦调压设备⟧⟦调压设备资产⟧⟦配电变压器⟧⟦用电户⟧⟦能源客户⟧⟦计量点⟧⟦台区⟧⟦发电户⟧ 按 SKILL.md `entity_aliases` 逐一替换为物理表名（cms20_adj_volt_dev / cms20_adj_volt_dev_asset / dim_grid_pub_dist_trans_resrc_standbk_e / dim_cst_elec_cons_cust / cms20_cst_cust / dim_cst_inst_elec_cons / dim_cst_dist_sta / dim_cst_gpc）——**表名不靠模型记忆，靠机制替换**。

**6b batch_entity_source_mode（源模式裁决）**：
- 模型按 SKILL.md 铁律「先一次 batch 查所有表」调用，契约允许 ✓（precheck 通过）；
- handler（kg_action_handlers.py:430）→ kg_api.batch_entity_source_mode 对 8 表查 kg_entities 源模式 → 返回逐表模式 + `recommended_tool`（api_integration→execute_entity_api/execute_api_sql；doris_catalog→execute_doris_sql；物理→execute_sql）；
- **postcheck 确认引擎并锁定**：SkillPolicy 依据返回写入 `contract.selected_engine`，此后一切数据工具必须匹配该引擎工具集（precheck 第 3 步强校验，:171-194）——**引擎一致性闭环**。

**6c 渲染模板并执行**：
- 模型用渲染后的模板 SQL（含批返回的 catalog 前缀，如 `pg_tupu.public.` 三段命名）调 `execute_doris_sql`（或按 recommended_tool 选 execute_sql/execute_api_sql）；
- **precheck 四关**（skill_policy.py:151-205）：
  1. 不在禁用集 ✓（contract.forbidden）；
  2. 允许集 ✓（step.allowed_tools）；
  3. 引擎匹配 ✓（batch 已确认）；stop_when 未命中（首个数据工具）✓；
  4. **模板指纹校验**（scenario_strict，:199-204 + template_guard）：候选 SQL 的表集合 ⊆ 模板表集合、SELECT-only、骨架结构指纹一致、无未渲染 ⟦⟧ 参数 → 通过 → 发 `template.bound` 事件（:231）；**户变关系模板自带 UNION ALL 合并用电户/发电户两段是模板守卫白名单特例**（template_guard.py:330）。指纹不一致 → 直接拒绝「SQL 未通过模板校验」→ 进纠错循环。
- **执行**：doris 池（SQLAlchemy pool_pre_ping / `/*+ SET_VAR(query_timeout=60) */` 超时）→ EXPLAIN 预检（坏 SQL 提前拦截）→ 执行 → 结果附 `verification`（row_count/空值率/告警）→ EngineQueryLog 写入；
- **postcheck**（:120-124）：`result_obtained=True`；`stop_reached` 判定 row_count>=0 恒真 → `_runtime["terminal"]` 生效 → 允许集收窄（数据工具全部移出，仅剩只读定位工具）→ 后续任何数据检索被 precheck 第 5 步拒绝「已命中终止条件，禁止重复/继续检索」。

### S7 终止（最小终止纪律）

- 系统提示词 :214 明示：**「户变关系查询只要 SQL 返回 row_count > 0，即立即基于结果生成最终答案」**，禁止为展示完整结果反复分页/启动子代理；:211 明示「所有/全部类查询一次查询即完成，row_count 就是全部数量，禁止拆段分别查询」；
- 本问题无「按台区分组统计/导出全量/算负载率」要求 → 只跑第 1 步即终止，不进入 overload/load_ratio 步骤。

### S8 最终答案（无 rubric）

- scenario → rubric=None → **RubricMiddleware 零开销直通**（无 rubric 不激活）；置信度按 S 阶段规则判「中」（无自评）；
- 输出模式 single_result_table + forbid_markdown_detail_table：**明细数据不进 markdown**（前端表承载），答案只给 A-E 段（conclusion/findings/warning/recommendation），且措辞口径遵守 AGENTS.md（无数据不臆断/数字来自工具返回）。

### S9 SSE 事件流（data_intelligence_stream.py 消费循环）

| 事件 | 载荷要点 | 本问题 |
|---|---|---|
| status | node/phase/text | running「小探正在运行中」 |
| route.card | 路由/范围/数据访问/执行决策/终止原因卡数据 | RouteCard=distribution-overload/relationship；DataAccessCard=8 表+引擎；StopReasonCard=stop_when 命中 |
| think | 下一步判断「已知/判断/因此」实时流 | 每轮 ReAct 决策 |
| trace/tool.* | 工具 start/completed + step_id/duration | read_file / batch / execute 三步 |
| template.bound | 结构指纹通过 | 执行前发出 |
| sql_result | 全量列/行/row_count/sql/step_id/data_snapshot_at | 户变关系 UNION 全量结果（DataSummary 已派发完整数据） |
| transition | step 转场「执行成功，继续下一步」 | 单步即止 |
| evidence | 路由/表/示例命中/verification/置信度聚合 | EvidenceCard 数据 |
| followup.rewrite | 改写透明性 | 本问题不发 |
| final / done | 最终答案流式 token / 收尾 | - |

### S10 前端渲染

FreePlanChat：ThinkStream（步骤决策动效）→ 六张业务卡（Route/Scope/DataAccess/ExecutionDecision/StopReason/**Evidence**）→ SqlResultTable（全量数据 + verification 徽标 + 图表 Segmented（若形态可识别））→ 最终答案（A-E 段）→ 👍/👎 反馈（改进入示例库的入口）。

### S11 持久化与治理

- EngineQueryLog：SQL/引擎/耗时/row_count（观测与偏差预警数据源）；
- RunEventSink：tool.completed / sql_result 等关键事件落库（freeplan 审计）；
- governance：route.scenario、template.bound、policy 事件（白名单未触碰即无 policy 拒绝）；
- checkpoint：消息历史 + last_skill/last_step（下一轮追问的连续上下文来源）。

### S12 会话回写

`last_skill="distribution-overload"`, `last_step="relationship"` 写入 checkpoint——用户下一轮追问「那重过载的呢」时，S1 读取并沿用（若含新触发词「重载」则新场景胜出覆盖）。

## 四、异常路径推演（同一问题在不同故障下的行为）

| 场景 | 机制响应 | 终态 |
|---|---|---|
| 模板中某表在 kg_entities 缺源模式 | batch 返回缺项 → 引擎裁决降级 recommended_tool；schema 漂移联动禁用相关示例 | 走可用引擎 |
| 模型写出的 SQL 骨架与模板不一致 | precheck 模板指纹拒绝 → 纠错指引「请按模板 step1 重写」→ 计数 1 | ≤2 次自愈，超限失败卡 |
| 列名报错（模板已核对，几乎不可能） | error_class=SYNTAX → 纠错指引 validate_attributes | 自愈/失败卡 |
| 执行超时（60s hint） | error_class=TIMEOUT → 指引精简 | 自愈/失败卡 |
| 引擎混用（batch 判 doris 却调 execute_sql 物理） | precheck 引擎一致拒绝 | 强制回正确工具 |
| 结果拿到后模型还想再查（分页/子代理） | stop_when 拒绝 + :214 纪律 | 单次即止 |
| 表缺失（schema 漂移） | scenario 自动降级一次（search_entities/list_tables 重定位），HITL 不打断 | 重定位后重试 |

## 五、关键设计观察

1. **确定性压倒自由发挥**：本问题的「正确性」不靠模型聪明，而由五重结构保证——路由定剧本、剧本定模板、模板定表名（⟦⟧替换）、指纹强校验（scenario_strict）、引擎锁定。模型只需「读模板→渲染→调用→终止」。
2. **模板自带的 UNION ALL 是特例合法**：template_guard 对「户变关系模板合并用电户/发电户两段」放行，这是经评审确认的业务合法形态，写入守卫白名单。
3. **最小终止纪律直接引用本问题**：系统提示词把「所有用电户与配变户变关系」作为「所有/全部类一次查询即完成」的示例词，说明该问题是受控平台打磨过的高频基准形态。
4. **scenario 路径刻意薄化**：无 rubric、无 HITL、示例大概率不注入——不是能力缺失，而是模板强约束已把自由度压到最低，额外自评/人审属过度设计（YAGNI）。
5. **链路观测完整**：template.bound→tool→sql_result→transition 的事件链 + EngineQueryLog + RunEventSink，任何一步失败都能定位到阶段（时序埋点 t0/timing 结构齐全）。
6. **学习入口在两端**：入口 G1 示例检索（generic 受益）、出口 👍/👎 反馈（可反哺示例库）——本问题若被用户点赞确认，将成为「户变关系」类问题的高置信示例，改善后续 generic 路径。
