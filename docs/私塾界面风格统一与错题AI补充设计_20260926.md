## 一、风格对比：私塾对话首页 vs 问数对话首页

### 1.1 结论先行
**骨架已一致，皮肤仍有差异。** 两者现在共用同一套聊天骨架（`ChatPanel.tsx` 承载分类页签、历史侧栏、消息流、输入区），`/e/sishu/chat` 真实渲染 `TutorHomeChat.tsx`（ExpertChat 的 sishu 死分支已删除，commit a1cacd9），布局结构与问数 `/e/wenshu/chat` 完全同构。但**主色没有统一**：

| 对比项 | 问数（/e/wenshu/chat） | 私塾（/e/sishu/chat） | 是否一致 |
|---|---|---|---|
| 聊天骨架/布局 | ChatPanel 统一骨架 | 同一骨架（TutorHomeChat 内嵌） | ✅ |
| 品牌主色 | `#2563EB` 蓝 | `#D97706` 琥珀（顶部色条、徽章、图标） | ❌ |
| 页签/分类条选中态 | `var(--brand, #2563EB)` | 琥珀色高亮 | ❌ |
| 顶部空间色条 | 3px 蓝色条 | 3px 琥珀条 `data-testid="space-color-bar"` | ❌（仅颜色） |
| 历史侧栏/输入区 | 相同组件 | 相同组件 | ✅ |

### 1.2 设计决策（二选一，需你拍板）

**方案 A：完全同色（推荐）**
- 私塾也使用 `--brand: #2563EB`，琥珀色仅保留在极小的"学科徽标"场景（如错题本科目 chip）。
- 做法：在 `TutorHomeChat.tsx` 删除硬编码 `#D97706`（共 3 处内联 + `text-amber-600`），改为 `var(--brand)`；`space-color-bar` 背景改 `var(--brand)`。
- 优点：用户在问数/私塾之间切换零割裂感，"一个产品"的心智最强。
- 代价：私塾失去独立色识别，只能靠标题与图标区分。

**方案 B：同骨架、异主色（现状）**
- 保留琥珀作为私塾子品牌色，但把所有硬编码收拢到 `tokens.ts` 的 `SISHU_ACCENT` 单一 token，禁止散落内联。
- 优点：专家空间有色彩辨识度；改动最小。
- 代价：两个首页第一眼观感仍"不一样"。

> 我的建议：**方案 A**。你此前明确要求"色素风格保持和问数相近"，且骨架已同构，颜色是最后一块碎片。若担心辨识度，可在私塾首页 Hero 区保留一个琥珀色小图标作为点缀。

### 1.3 实施清单（方案 A，预估 30 分钟）
1. `frontend/src/pages/tutor/chat/TutorHomeChat.tsx`：
   - `space-color-bar` 背景 `#D97706` → `var(--brand, #2563EB)`
   - 徽章 `color-mix(in srgb, #D97706 12%, transparent)` → `color-mix(in srgb, var(--brand) 12%, transparent)`
   - 文字色 `color: "#D97706"` → `color: "var(--brand)"`
   - `text-amber-600` → 使用 brand 色 class 或内联 `var(--brand)`
2. 全仓 grep `#D97706|amber-` 确认私塾域内无其他散落硬编码（错题本、H5 页面逐一核对，琥珀只保留在科目 chip 场景）。
3. 截图对比 `/e/wenshu/chat` 与 `/e/sishu/chat` 首屏，确认像素级观感一致。

## 二、错题管理「AI 补充」：详细解题步骤填充

### 2.1 需求复述
AI 补充时不仅要给出最终答案（`standard_answer`），还必须生成**详细解题过程**：
- `detailed_analysis`：完整文字讲解（"答案下面还有详细解题过程"）；
- `solution_steps`：分步数组 `[{step, text}]`，逐步列式。

### 2.2 已完成的代码改动（本轮已落，未跑测试）

**后端 `backend/app/api/sishu_learning/mother_question.py`**
- `_RECOGNIZE_TEXT_PROMPT` 改写：题目可解时 `detailed_analysis` 与 `solution_steps` **不得为空**；`standard_answer` 只放最终答案/结论，不混入过程。
- 新增 `_normalize_recognition()` 归一化：
  - `solution_steps` 为数组 → 拍平为"每行一步"的文本（兼容模型返回字符串的情况）；
  - `detailed_analysis` 缺失时 → 从 `solution_steps` 合成，保证前端永远有内容可显示。

**H5 前端 `frontend/src/pages/tutor/h5/H5WrongBook.tsx`**
- aiFill 回填 `setForm` 新增 `solution_steps` 映射，防御性拍平（数组/字符串两种形态都兼容）。

**桌面端 `MotherQuestionFields.tsx`**
- 无 `solution_steps` 独立字段，沿用已有的 `detailed_analysis` 映射即可，无需改动。

### 2.3 交互设计（答案 + 解题过程的展示层次）

```
┌─ AI 补充结果 ─────────────────────┐
│ 标准答案                          │
│ ┌──────────────────────────────┐ │
│ │ x = 3                        │ │  ← standard_answer（只有结论）
│ └──────────────────────────────┘ │
│ 详细解题过程                      │
│ ┌──────────────────────────────┐ │
│ │ 第1步：移项，得 2x = 6        │ │  ← solution_steps 逐行渲染
│ │ 第2步：两边同除以 2           │ │
│ │ 第3步：x = 3，验证成立        │ │
│ │ ─────────────────────────    │ │
│ │ 讲解：本题考查一元一次方程…   │ │  ← detailed_analysis 补充讲解
│ └──────────────────────────────┘ │
└───────────────────────────────────┘
```

- 渲染优先级：`solution_steps` 存在 → 分步卡片展示；否则降级展示 `detailed_analysis` 纯文本（后端归一化已兜底，前端无需判空分支）。
- 表单可编辑：分步文本域支持手动修改后再保存。

### 2.4 遗留风险（如实告知）
- 改动**未经过 pytest 验证**（你指示不跑测试）。`test_mother_question.py` 的 import 路径已修复并新增 normalize 断言，下次允许测试时一条命令即可回归：
  `pytest backend/app/services/sishu_full/learning/tests/test_mother_question.py -k "recognize or normalize"`
- 模型不保证 100% 遵守 prompt；归一化层已做双兜底（数组拍平 + 步骤合成讲解），最坏情况也能展示非空内容。

## 三、再次核实：tutor 是否真的"完全重写"

### 3.1 结论
**没有完全重写。对话/工具层已是新体系，但 book（互动教材生成）模块仍是 vendor 遗留。**

### 3.2 实证清单

| 模块 | 位置 | 状态 |
|---|---|---|
| 教学工具（TUTOR_TOOLS 11 件） | `backend/app/services/learning/tutor_inprocess.py`（SPECS 单源） | ✅ 已重写为 deepagent in-process 工具，MCP 化 |
| 学习服务核心（FSRS/掌握度/选课/路径） | `services/learning/`（fsrs/mastery/exercise_selector/scheduler 等 19 个新文件） | ✅ 新体系 |
| H5/桌面会话 | `h5_session_store.py` + 新 API `app/api/sishu_learning/` | ✅ 新体系 |
| **book 互动教材引擎** | `backend/app/services/sishu_full/book/`（29 个文件：engine/compiler/streaming + 5 个 agents + 13 种 blocks） | ❌ **vendor 原样存活，未重写** |
| math_animator | 依赖沙箱 9385 | ⚠️ 入口已下线（沙箱容器已建议废弃） |

### 3.3 影响评估
- 日常对话、错题本、练习推荐、学情：**走的全是新链路**，vendor 代码不参与。
- "生成互动教材/电子书"功能：仍走 `sishu_full/book` 的老 LangGraph 子图 + 自有 streaming 协议，与 deepagent 主链路的 SSE（astream_events v2）是两套流式协议——这正是你要求消除的"老技术债"。

### 3.4 R6 book 重写设计（待启动，给方案）

**目标**：book 生成能力迁为 deepagent 原生 agent，删除 `sishu_full/book` 整目录。

1. **agent 化**：5 个老 agents（ideation / spine / spine_synthesizer / page_planner / source_explorer）压缩为 1 个 deepagent 主 agent + 2 个子 agent（大纲规划、页面写作），通过 LangGraph `create_react_agent` 编排，复用主链路的 SkillPolicyMiddleware 与权限判定。
2. **blocks 工具化**：13 种 block（text/section/quiz/flash_cards/timeline/concept_graph…）改为工具函数（产出 JSON schema 校验过的 block 对象），前端渲染器不变——前端零改动。
3. **流式统一**：废弃 `book/streaming.py` 自定义协议，生成进度经 astream_events v2 SSE 推"阶段性产物"（大纲→章节→页面），与对话流同一通道。
4. **存储不变**：`book/storage.py` 的表结构保留，仅 DAO 移到 `services/learning/` 下，避免数据迁移。
5. **删除清单**：`sishu_full/book/` 29 个文件 + 相关路由注册 + `math_animator` 残留引用。

**工作量预估**：后端 3-4 天，前端 0.5 天（只换 SSE 事件名），回归 1 天。
**排序建议**：排在 ENABLE_AUTH=true 切换决策之后、Wave2 清理之前——因为它一删，vendor 域就只剩 Wave2-4 的纯清理了。
