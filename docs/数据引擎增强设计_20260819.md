# 数据引擎增强设计（Doris / DuckDB / 统一引擎层）

> 2026-08-19 · 设计窗口产出（不动代码）
> 范围：`doris_engine.py`、`duckdb_engine.py`、`query_engine_router.py`、Doris/ApiMapping 管理面、引擎观测与前端工作台。
> 定位：给"引用 Doris、引用 DuckDB"两套联邦能力做**体系化增强**，与受控 Skill 平台（QueryContract / EngineLock / SkillPolicy）正交兼容。

## 0. 现状诊断（先说清楚弱在哪）

### 0.1 Doris 侧（doris_engine.py，286 行）

| # | 现状 | 证据 | 问题 |
|---|---|---|---|
| D1 | 每次查询新建 pymysql 连接 | `get_conn()` 每调 `pymysql.connect(**_load_config())` | 无连接池，握手开销叠加；并发下连接风暴 |
| D2 | 无查询超时/取消 | 仅 `connect_timeout: 10` | 慢 SQL 挂死请求，BE 资源被占 |
| D3 | 无 EXPLAIN / Profile | 全文件无 EXPLAIN | 慢查询不可诊断，黑盒 |
| D4 | Catalog 管理仅支持 JDBC | `create_catalog` 只拼 `type=jdbc` | `es_tupu`（ES catalog）不可纳管、不可探测、不可刷新 |
| D5 | 无健康检查/熔断/重试 | — | Doris 挂了才在用户查询里以原始报错暴露 |
| D6 | 无指标/慢查询日志 | — | 引擎运行状况完全不可观测 |
| D7 | 错误不分类 | 统一 `{"ok": False, "error": str(e)}` | 「表不存在」和「连接失败」对上层（受控降级判定）不可区分 |
| D8 | 无热查询加速 | — | 高频聚合（如客户总数）每次实时算 |

### 0.2 DuckDB 侧（duckdb_engine.py，395 行）

| # | 现状 | 证据 | 问题 |
|---|---|---|---|
| K1 | 全局单例 `_conn` **无锁** | `_conn: Optional[...]` 模块级，无 Lock | LangChain 同步工具默认在线程池执行 → 并发工具调用同一连接，**崩溃/数据错乱风险** |
| K2 | API 结果零缓存 | `_call_api` 每查询实时 requests | 同一问题重复问 = 重复全量拉 API；上游限流风险 |
| K3 | 无分页协议 | 单次请求即全量 | 大数据量 API 拉不全或一次巨响应 |
| K4 | 无类型推断 | DataFrame 原样 register | 数值列是 object → SUM/比较/排序行为错误 |
| K5 | requests 同步 30s | `timeout=30` | 阻塞事件循环（全链路无 to_thread，见 0.3） |
| K6 | 下推仅 EQ 常量 + JOIN 等值 | sqlglot 解析段 | IN/范围/前缀条件全部内存过滤，API 传输浪费 |
| K7 | 无限速/熔断 | — | 上游 API 抖动直接放大为查询失败 |
| K8 | 无内存/行数上限 | `:memory:` 裸跑 | 大结果集可能 OOM |
| K9 | 扩展离线困境 | 注释明写「INSTALL 会挂起」 | postgres/mysql scanner 可用性靠运气 |

### 0.3 横切面

- **整条执行链同步阻塞**：全仓 grep 无 `to_thread/run_in_executor`（引擎路径），异步事件循环里跑同步 IO。
- **观测空白**：无查询历史、无耗时统计、无血缘（哪次 run 摸了哪些表/API）。
- **引擎选择不可感知健康**：`query_engine_router.py` 只按 source_mode 裁判（这个设计是对的，保持），Doris 宕机时模型仍会拿到 `execute_doris_sql` 然后必败。

## 1. 设计目标与原则

1. **引擎成为一等公民**：健康、指标、诊断、缓存、加速全部体系化，不再是两个孤立 service 文件。
2. **不动受控平台语义**：`ENGINE_TO_TOOLS`、引擎锁定、batch_entity_source_mode 唯一裁判、空结果不换引擎——全部保持。本设计只做"引擎自身变强 + 可观测 + 可诊断 + 可降级"。
3. **零新增重依赖**：连接池用已有 SQLAlchemy；调度复用 `TaskWorker`；指标用内存环形缓冲 + JSON 端点（不引 Prometheus）。新增依赖仅允许 `httpx`（异步 HTTP，替代 requests）与 `pyarrow`（parquet 缓存落盘，DuckDB 查询天然加速）——两者均为 DuckDB/pandas 生态常规件。
4. **分五批施工**，P1 是稳定性地基（不加任何新功能，先把风险清零）。

## 3. L0 稳定性地基（P1，纯风险清零）

### 3.1 异步执行包装

所有引擎入口（`execute_doris_sql / execute_api_sql / execute_entity_api / execute_sql` 的 handler）统一走：

```python
await asyncio.to_thread(engine_adapter.execute, req)   # 引擎调用全部移出事件循环
```

API 拉取改 `httpx.AsyncClient`（连接池 + 精确 timeout 分级：连接 5s / 读取 30s）。

### 3.2 Doris 连接池（复用 SQLAlchemy，零新依赖）

```python
# doris_engine 内部：pymysql 直连 → SQLAlchemy engine
_engine = create_engine(
    f"mysql+pymysql://{user}:{pwd}@{host}:{port}/{db}",
    pool_size=5, max_overflow=5, pool_pre_ping=True, pool_recycle=1800,
)
# execute: with _engine.connect() as conn: conn.exec_driver_sql(sql)
```

`pool_pre_ping` 顺带解决 Doris 重启后的陈旧连接问题。配置变更（DorisConfig 保存）时 `_engine.dispose()` 重建。

### 3.3 DuckDB 并发安全（v1 串行锁）

```python
_DUCKDB_LOCK = asyncio.Lock()          # v1：读写全串行，简单且绝对正确
async with _DUCKDB_LOCK:
    await asyncio.to_thread(_execute_federated, ...)
```

> 取舍说明：v1 串行锁会把联邦查询并发压到 1。单用户演示场景（本项目现状）完全够用；若未来并发上来，v2 方案是 `conn.cursor()` 派生线程隔离游标（DuckDB 官方并发模式），注册视图改挂公共 catalog。**先锁后测，勿过早优化。**

内存护栏（get_conn 时一次性设置）：

```sql
SET memory_limit='2GB'; SET threads=2; SET enable_progress_bar=false;
```

外加**每 endpoint 拉取行数上限**（默认 200,000 行，配置可调），超限即报 `CAPACITY` 类错误并在结果中明示。

### 3.4 查询超时

- **Doris**：SQL 注入 hint `SELECT /*+ SET_VAR(query_timeout=60) */ ...`（Doris 原生 per-query 超时）；外层 `to_thread` future 再套 75s 硬超时兜底（超时后下发 `KILL QUERY <id>`，连接池自动回收）。
- **DuckDB**：联邦查询整体套 `asyncio.wait_for(..., timeout=120)`，超时取消（锁释放，连接可复用；不 kill 进程）。

### 3.5 错误分类学（EngineErrorClass，横切核心）

统一枚举，两引擎各自实现 `classify_exception(e) -> EngineError`：

| 类别 | Doris 判据（示例） | DuckDB 判据 | 可重试 | 允许受控降级 |
|---|---|---|---|---|
| `CONNECTION` | pymysql OperationalError 2003/2013 | httpx ConnectError | ✅ 1次 | ❌（报引擎不可用） |
| `AUTH` | 1045 Access denied | 401/403 | ❌ | ❌ |
| `SYNTAX` | 1064 You have an error | ParserException / BinderException | ❌ | ❌ |
| `TABLE_MISSING` | 1051/1146 Table doesn't exist | CatalogException: Table does not exist | ❌ | ✅（唯一契约内降级口） |
| `CATALOG_MISSING` | Unknown catalog | ATTACH 失败 | ❌ | ✅ |
| `TIMEOUT` | query_timeout / 外层超时 | wait_for 超时 | ✅ 1次 | ❌ |
| `CAPACITY` | BE 内存类报错 | 行数超限 / Out of Memory | ❌ | ❌ |
| `UPSTREAM_API` | — | endpoint HTTP 5xx / 熔断 OPEN | ✅ 退避 | ❌（报上游不可用） |
| `UNKNOWN` | 其余 | 其余 | ❌ | ❌ |

> **与受控平台的对接点**：SkillPolicy 的「一次受控降级」判定今后以 `TABLE_MISSING / CATALOG_MISSING` 为唯一许可条件（错误对象随 ToolMessage 结构化返回，替代裸字符串匹配）。

### 3.6 查询打标（血缘地基）

所有出栈 SQL 注释打标，Doris Profile / 查询历史均可关联：

```sql
SELECT ... FROM pg_tupu.public.xxx /* dsh run_id=run_ab12 skill=distribution-overload engine=doris */
```

打标在 EngineAdapter 内统一注入（sqlglot 解析后附加，不破坏 SQL 合法性；DuckDB 原样保留注释）。

## 4. L1 EngineAdapter SPI（统一引擎抽象）

新文件 `backend/app/services/engine/`（包结构，旧文件逐步迁移不改外部接口）：

```
engine/
  __init__.py          # get_adapter(engine_name)
  base.py              # EngineAdapter 抽象基类 + EngineError + CapabilityMatrix
  doris_adapter.py     # 包装 doris_engine（外部签名不变）
  duckdb_adapter.py    # 包装 duckdb_engine
  physical_adapter.py  # 包装 sql_executor（PG 直连）
  health.py            # 健康状态机 + 探测
  metrics.py           # 环形缓冲指标
  history.py           # EngineQueryLog 落库 + 慢查询
  taxonomy.py          # 错误分类学（§3.5）
```

```python
class EngineAdapter(Protocol):
    name: str                                   # doris | duckdb | physical
    capabilities: CapabilityMatrix
    async def execute(self, req: ExecRequest) -> ExecResult        # to_thread 内跑，含打标/超时/历史落库
    async def explain(self, sql: str) -> ExplainResult             # §5.2
    async def probe(self) -> HealthStatus                          # §7.1
    def classify(self, e: Exception) -> EngineError                # §3.5
```

**能力矩阵**（前端工作台 & 路由提示共用，写死在 base.py）：

| 能力 | doris | duckdb | physical(PG) |
|---|---|---|---|
| 跨源 JOIN | ✅ catalog 联邦 | ✅ ATTACH + register | ❌ 单源 |
| 谓词下推出库 | ✅（ES catalog 原生 / JDBC 部分下推） | ⚠️ 仅参数化 API 下推 | ✅ PG 自身 |
| EXPLAIN | ✅ | ✅ | ✅ |
| 查询 Profile | ✅ FE 18030 | ❌（EXPLAIN 替代） | ❌ |
| 结果缓存 | ❌（靠加速层） | ✅ API 数据缓存 | ❌ |
| 分布式执行 | ✅ BE | ❌ 单机内存 | ❌ |

## 5. Doris 深化（P4）

### 5.1 Catalog 全生命周期（补 D4）

现有 `DorisCatalog` 模型（models/base.py:618）与 `create_catalog(type=jdbc)` 扩展为三类：

| 类型 | properties 要点 | 用途 |
|---|---|---|
| `jdbc` | 已有（type/url/driver/user/password） | PG 等关系源纳管（pg_tupu 即此模式） |
| `es` | `es_nodes=http://127.0.0.1:11200`、`user/password`（elastic/...，走后端配置注入不落前端） | **ES 联邦 + Doris 原生谓词下推**（Doris on ES 自动下推 filter/limit） |
| `internal` | 无 | 内部库（加速层目标表所在） |

管理动作补齐（API + 前端）：
- `probe`：`SHOW DATABASES FROM <catalog>` 探活，返回毫秒耗时 + 错误分类；
- `refresh`：`REFRESH CATALOG <name>`（外部元数据变更后手动刷新）；
- 变更联动：catalog 增删改 → DuckDB `reset_conn()`（已有钩子复用）+ 健康快照失效。

> 架构收益：ES 数据源今后两条路径——**优先 Doris ES catalog 联邦（下推强）**，DuckDB API 虚拟表退居「无 Doris / 轻量单源」兜底。batch_entity_source_mode 的路由建议规则同步加一条：实体绑定 ES endpoint 且 es catalog 健康 → 推荐 `execute_doris_sql`。

### 5.2 诊断能力（补 D3）

- **EXPLAIN**：`EXPLAIN` / `EXPLAIN VERBOSE` 两档包装，返回结构化文本；前端 SQL 编辑器一键 explain（DorisConfig 页已有 SQL 试跑入口，就地增强）。
- **Profile 代理**：后端代理 FE HTTP（`http://<fe>:18030`）的 profile 查询（QueryProfile 页面接口），避免前端直连 FE 暴露凭证；慢查询列表（§8.2）每行挂 profile 链接，靠 §3.6 的 run_id 注释在 profile 里反查。
- FE 18030 端口来自不可变端口表，只代理不改动。

### 5.3 加速层：热查询预聚合（补 D8）

**模式选择：预聚合表 + 调度刷新**（不用自动 MV，理由见 §13）。

```
EngineAccelerator（新表）
  id / name / entity_codes(JSON) / agg_sql(模板) / target_table(internal db)
  schedule_cron / enabled / last_refresh_at / last_status / last_duration_ms / staleness_note
```

- **刷新**：复用 `TaskWorker` + `TaskQueue`（core/task_worker.py 优先级队列现成），按 cron 投递刷新任务：`INSERT OVERWRITE internal.agg_xxx SELECT ... FROM <catalog>.<db>.<table> ...`；
- **命中**：batch_entity_source_mode 返回时附带「可用加速表」提示；场景 SKILL.md 可在步骤里直接声明目标表（受控路径，模型不自行改写 SQL 指向加速表）；
- **新鲜度披露**：命中加速表的回答在 DataAccessCard 标注「数据截至 HH:MM（预聚合，TTL N 分钟）」——这是口径审计要求，不是可选项。

首批内置两个加速器（对应落地页示例问题的两个高频聚合）：`客户总数`、`配变重过载统计`。

## 6. DuckDB 深化（P3）

### 6.1 API 数据缓存（补 K2，收益最大）

```
backend/data/duckdb_cache/
  ep_<endpoint_id>__<sha1(normalized_params)>.parquet   # 参数指纹命名
  meta.json                                              # {fetched_at, params, rows, source_hash}
```

- **键**：`(endpoint_id, 规范化下推参数)` 排序后哈希；**值**：parquet 文件 + 元数据；
- **TTL**：ApiEndpoint 新列 `cache_ttl_seconds`（默认 300，0=禁用）；过期后下次查询触发刷新（可配 stale-while-revalidate：先回旧数据再异步刷）；
- **失效**：endpoint 配置保存即失效全部指纹 + 手动失效按钮（前端）；
- **register 路径**：命中缓存 → `duckdb.read_parquet()` 替代 `_call_api` → DataFrame（pyarrow 零拷贝）；
- **观测**：每个 endpoint 的 hit/miss/refresh 计数进指标环形缓冲，前端可见。
- **一致性披露**：命中缓存时 DataAccessCard 标注「数据快照 HH:MM（缓存 TTL Ns）」。

### 6.2 分页协议（补 K3）

ApiEndpoint 新增配置组 `pagination`（JSON 列）：

```json
{ "type": "none | page_number | cursor",
  "page_param": "page", "size_param": "pageSize", "page_size": 500, "start_page": 1,
  "cursor_path": "data.nextCursor", "max_pages": 50 }
```

- 拉取循环：逐页合并 DataFrame，直到取空 / `max_pages` 封顶（封顶即记 `CAPACITY` 警告事件并明示截断）；
- 每页拉取发 `run.api_fetch` 事件（page n, rows 累计），前端 ProgressFlagsCard 可见进度；
- 进度事件走现有 run_event_sink 通道，不新开轮询。

### 6.3 类型推断与 Schema 治理（补 K4）

- **采样推断**：endpoint 测试/首次拉取时对样本做类型推断（int/float/decimal/date/datetime/bool/string），写入 `columns` JSON 的 `dtype` 字段；
- **注册时转换**：`df = df.astype(inferred_dtypes)` 后再 register——SUM/MAX/日期比较从此正确；
- **漂移检测**：响应字段集 vs 注册 columns → 新增字段自动扩展（nullable）并记 `schema.drift` 治理事件；字段消失仅告警不阻断；
- 手工覆盖：columns 配置界面允许显式指定 dtype（推断只做初值）。

### 6.4 限速与熔断（补 K7）

- 每 endpoint：`concurrency=1` 默认 + `min_interval_ms`（默认 200ms）令牌间隔——保护上游；
- 熔断器：连续 5 次失败 → OPEN 60s（期间直接快速失败 `UPSTREAM_API`，不再打上游）→ 半开探测 1 次；
- 状态暴露在引擎工作台 endpoint 卡片上（CLOSED/OPEN/HALF_OPEN 徽标 + 最近失败原因）。

### 6.5 Pushdown v2 + 下推审计（补 K6）

现有 sqlglot 解析扩展：

| 谓词 | v1 | v2 行为 |
|---|---|---|
| `col = 'x'` | ✅ 下推 | ✅ 不变 |
| JOIN 等值传递 | ✅ | ✅ 不变 |
| `col IN (a,b,c)` | ❌ 内存过滤 | ✅ 多值参数（或逐值并发受 6.4 限速约束） |
| `col >= x AND col <= y` | ❌ | ✅ 映射为起止参数对（若 endpoint 模板声明支持） |
| `col LIKE 'xx%'` | ❌ | ✅ 前缀 → 通配参数（仅前缀形态） |
| ORDER BY + LIMIT | ❌ | ❌ 保持内存（复杂度不值） |

**下推审计（Pushdown Trace）**：`execute_api_sql` 返回值新增 `pushdown` 数组：

```json
[{"table": "vw_customer", "param": "custType", "value": "居民", "from": "WHERE col='居民'"},
 {"table": "vw_meter", "param": "areaId", "value": "A01", "from": "JOIN 等值传递"}]
```

未下推的 WHERE 谓词列清单一并返回（`not_pushed: [...]`）——前端 Pushdown 调试器可视化「什么下推了、什么留在内存」，这是排查联邦查询慢的金钥匙。

## 7. 健康与降级体系（P2）

### 7.1 健康状态机

每引擎独立状态机：`HEALTHY → DEGRADED → DOWN → RECOVERING`。

- **探测**：adapter.probe()（doris: `SELECT 1` + 连接池取放；duckdb: `SELECT 1`；physical: PG `SELECT 1`）；
- **节拍**：懒探测 + 60s 缓存（避免空转轮询），后台线程 60s 刷新一次快照（daemon thread，随进程生死）；
- **判据**：探测失败 ×2 → DOWN；p95 > 5s 或 5 分钟错误率 > 20% → DEGRADED；
- **恢复**：DOWN 后每 30s 半开探测，成功 → RECOVERING → 连续 3 次 → HEALTHY。

### 7.2 路由联动（batch_entity_source_mode 增强）

返回体新增（不改既有字段，向后兼容）：

```json
"engine_health": {"doris": "healthy", "duckdb": "healthy", "physical": "healthy"}
```

- 推荐 engine 处于 DOWN → recommended_tool 返回前**提前失败**并附明确原因（「Doris 引擎当前不可用」，错误类别 CONNECTION）——把失败从"模型调用后撞墙"提前到"入口即知"，省一轮无效推理；
- DEGRADED → 照常推荐，但 reason 附带延迟告警。

### 7.3 事件通道

健康状态变更 → `engine.health` 事件（run_event_sink + skill_governance 双落）→ 前端工作台实时徽标（SSE 既有通道推送，不新开连接）。运行中查询遇引擎故障**不换引擎重查**（受控平台铁律不动），按 §3.5 分类明确报错。

## 8. 观测与治理（P2）

### 8.1 EngineQueryLog（新表）

```
id / run_id / skill_id / engine / sql_hash / sql(打标后原文) / pushdown_summary(JSON)
rows_returned / duration_ms / status(ok|error|timeout) / error_class / slow(bool)
profile_id(Doris) / endpoint_ids(JSON) / created_at
```

- 保留策略：默认 30 天，TaskWorker 低优先级任务清理；
- 写入点：EngineAdapter.execute 统一落库（调用方零改动）。

### 8.2 慢查询与指标

- 慢阈值 3s（配置），slow=true 的查询在工作台慢查询页置顶 + Doris profile 链接；
- 指标：内存环形缓冲（deque maxlen=1000）按引擎聚合 QPS / p50 / p95 / 错误率 / 缓存命中率，`GET /api/engine/metrics?window=1h` 输出 JSON——**不引 Prometheus**（YAGNI，单机演示场景）。

### 8.3 血缘

§3.6 打标 + EngineQueryLog 的 endpoint_ids/表清单 = 每次运行「摸过哪些表/API」完整留痕；治理审计（skill_governance）已有事件流，加 `query.executed` 一类即可串起来。

## 13. 不做清单（YAGNI 边界，防过度设计）

| 不做 | 理由 |
|---|---|
| Prometheus / OpenTelemetry 接入 | 单机演示场景，内存环形缓冲 + JSON 端点足够 |
| Doris 多 FE 负载均衡 | 单 FE docker 部署（端口表固定） |
| Stream Load / Routine Load | 平台无写入 Doris 的需求 |
| Workload Group / 资源隔离 | 单用户场景 |
| DuckDB 磁盘持久库 | parquet 缓存层已解决持久化诉求 |
| DuckDB 在线 INSTALL 扩展 | 网络约束（代码注释已证实挂起）；改为离线检测报告 + 文档指引 |
| 自动物化视图（async MV） | 版本兼容风险高；预聚合表+调度先验证价值，MV 留 v2 |
| 任意 SQL 结果缓存 | 正确性风险（缓存失效判定复杂）；只缓存 API 数据层 |
| 引擎间透明改写（跨引擎 SQL 自动翻译） | 与受控平台"引擎唯一选择"语义冲突，路由仍由契约裁判 |
| DuckDB 并发连接池 v2 | 先串行锁压测，未达瓶颈不动 |

## 14. 风险与对策

| 风险 | 对策 |
|---|---|
| Doris Profile REST 路径随版本变化（2.x/3.x） | probe 双路径兼容 + 失败降级为 EXPLAIN VERBOSE（诊断不空窗） |
| DuckDB 串行锁造成排队 | EngineQueryLog 观测排队时长；>2s 排队占比 >10% 才启动 v2 游标方案 |
| API 缓存带来数据陈旧误读 | 新鲜度强制披露（DataAccessCard 快照时间）+ TTL 默认保守 5 分钟 |
| 类型推断误判（如学号识别为 int） | 采样只做初值 + 界面可改 + 漂移事件留痕 |
| 加速层口径与实时口径不一致 | staleness_note 强制展示；加速器 agg_sql 模板纳入 template_guard 模板治理 |

## 15. 与既有设计的衔接（合规声明）

- **受控 Skill 平台**：`ENGINE_TO_TOOLS` / 引擎锁定 / 空结果不换引擎 / batch 唯一裁判——语义零变更；本设计新增的 engine_health 只是"入口提示"，不参与运行中改道。
- **错误分类学** 成为「一次受控降级」唯一判据（替代字符串匹配），是本设计与 SkillPolicy 的唯一交叉点。
- **前端规范**：全部新组件遵循《前端组件级规格》tokens/图标/z-index/动效铁律；图表色板强制走 chartPalette。
- **端口铁律**：Doris 9030/18030、ES 11200、PG 25432 全部只引用不改动；前端零硬编码端口（profile 走后端代理正是为此）。
