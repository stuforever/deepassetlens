# Agent 状态栏对照分析：我们的实现 vs 上下文蒸馏理论

## 一、总判断

我们没有名为「状态栏」的单件组件，但四类构成全部有对应物；且实现路线上有一个根本分歧：

> **书的方法论：把状态算好放给模型看，靠模型「瞥一眼」改变行为（软引导）。**
> **我们的方法论：凡是必须成立的约束，不放进状态栏让模型自觉——用代码强制执行（物理收窄/调用拒绝/工具移除）；只有建议性信息才走告知通道。**

这个分歧的根源在目标域：通用助手无法预知哪条约束重要，只能靠模型自觉+状态提醒；问数域约束清单是有限且可枚举的（只读/单查/模板/引擎），可以直接代码化。

## 二、四类构成对照

| 书的构成 | 我们的对应物 | 形态差异 |
|---|---|---|
| **任务规划**（TODO 列表防遗忘原始诉求） | 契约消息的场景/步骤声明 + last_skill/last_step checkpoint 跨题沿用 | 我们的任务规划是**路由器预编译**的（剧本步骤写死），不是模型动态维护的 todo |

| **环境状态**（重复调用计数/异常提醒） | SkillPolicy 纠错计数（同错误≤2 次拒绝）、stop_when 后数据工具移除、引擎健康（batch 返回 recommended_tool） | **形态相反**：书注入「已打 3 次(3/3)」读数靠模型停手；我们不显示计数，直接移除工具/拒绝调用 |
| **可用能力清单** | 技能目录（system 区）+ 契约 allowed_tools 显式列表 | 双份：技能目录管「会什么」，契约白名单管「这题准用什么」 |

## 三、实验五技术逐个对照

| 书的技术 | 我们的状态 |
|---|---|
| 时间戳跟踪 | 🟡 部分（个别工具返回带时戳；无统一前缀方案） |
| 工具调用计数器 | ❌ 不做读数显示——**替代物更强硬**：stop_when 物理移除工具、纠错≤2 直接失败卡。「到顶就停」这种显然规则，代码执行比教会模型更可靠 |
| TODO 列表管理 | 🟡 write_todos 工具随框架可用但实践中不用；单题流程短（≤6 轮），剧本步骤即计划 |
| 详细错误信息（类型/参数/栈/修复建议四层） | ✅ **最强对应**：错误分类学（TABLE_MISSING→先 search_entities 重定位、语法错→validate_attributes、超时→精简 SQL）正是「针对性修复建议」，实测驱动了从盲目重试到分析性解决的转变（与书 60%→95% 同构） |
| 系统状态感知（时间/工作目录/平台） | 🟡 引擎模式/推荐工具经契约注入；系统时间不注入（无需求） |

## 四、三条经验逐条对照

### 经验一：状态栏用代码维护，别拿 LLM 维护 —— ✅ 完全一致
我们的蒸馏全部代码计算：DataSummary 聚合（row_count+10 行样本）、SkillPolicy 计数、Router 预解析、EngineQueryLog 计时。链路里没有任何「让 LLM 先总结历史再注入」的环节。

### 经验二：删原文前确认状态栏覆盖所有问题 —— ✅ 结构性满足
DataSummary 对模型截断为样本，但**原文从不删除**——全量直推前端表格展示；任何全量问题按纪律必须 SQL 显式重聚合（样本≠全量）。有损投影的安全网是「投影失真时可随时回到原始数据重新计算」。
诚实登记：LIMIT 500 截断是唯一未闭环的有损点（超 500 行静默丢弃），已知隐患沿用。

### 经验三：状态栏准确率当生产指标盯（模型无条件信任注入状态） —— ⚠️ 已有真实案例！
上一轮户变关系 trace 里：「受控工作流已预解析主体实体为 `dwd_cst_bus_be_accs_lfcyc_df`（业扩办电业务申请全流程）」——**这就是一次状态栏污染事故**：错误的预解析实体作为事实断言注入契约，模型原样写进了自己的「已知」（无条件信任，正如书所说既不核对也不重算）。这次没出事仅因场景模板把表钉死。教训完全命中书中警告：
- 注入状态必须来自可靠观测（checkpoint 沿用的要标注来源）
- 已登记整改：实体预解析加相似度阈值+来源标注

## 五、更新策略：我们是「持久追加」派

契约消息每题新建追加，**旧契约永久留在轨迹中不删改**（checkpoint 天然如此）；工具结果注记也是 append-once。这正是书的实现二（Claude Code 式），理由也与书的经验法则吻合：

- 我们的轨迹短（单题 ≤6 轮、会话通常几题），陈旧契约累积的 token 代价可忽略；
- 每轮替换会反复 bust 尾部缓存——违背缓存优先原则；
- 陈旧契约的歧义风险由硬闸门消化：即使模型看错旧契约，SkillPolicy 按当前契约拦截。

## 六、时间感三轴：我们全部「外部强制化」

| 轴 | 书的方案（读数+操作手册） | 我们的方案 |
|---|---|---|
| 紧迫度 | 时间戳+预算读数配策略手册 | 无模型感知——5 分钟硬超时由 Harness 层直接击杀（stream.py:278-284），不商量 |
| 坚持度 | 计数器读数教模型分辨真假墙 | 错误分类学直接告诉模型墙的类型（重试无益类 vs 可修复类）+≤2 封顶 |
| 警觉度 | 慢调用读数升级为假设 | Doris 超时 hint 60s；慢查询进 EngineQueryLog 供人看，不给模型 |

书的关键发现「光给读数不改行为，必须配操作手册」反过来支持了我们的选择：**既然规则显然（到顶就停、真墙绕开），把规则写成代码比训练模型看懂读数便宜且可靠一个数量级。** 状态栏适合「规则难以预先枚举」的开放域；我们的规则可枚举，所以强制优于告知。

## 七、可低成本偷师的两点（登记，暂不立项）

1. **微型状态行**：ToolMessage 尾部追加代码计算的键值对（`[状态] 第3轮/上限8 · 已用42s/300s · 已获数据=是`）——纯 append、KV 友好、零 LLM 成本。价值场景：长剧本多步任务防漂移。当前单题短流程收益低，YAGNI；
2. **多步场景的步骤进度显式化**：连续追问跨步骤时（relationship→overload 分析），契约里注入 `[进度] 步骤2/共4 · 上一步已完成`——last_step 数据已有，只差格式化注入一行。若线上出现「跨步骤遗忘」案例再启用。

## 八、一句话总结

> 状态栏理论说的「提前算好、显式呈现、代码维护、警惕污染」我们全部在做（DataSummary/错误分类学/EngineQueryLog 就是我们的蒸馏仪器）；唯一的路线分歧是我们把「必须成立的约束」从状态栏里拿出来交给了强制执行——书里的电话计数器实验恰恰证明了纯读数方案的脆弱（小模型照样违规），而我们的答案是根本不让第 4 通电话打得出去。
