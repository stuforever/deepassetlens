## 一、14-A 场景 COUNT 出口（模板层扩展）★主件

### 1.1 缺口证据链（为什么会打结）

「统计重过载台区数量」这类 COUNT 题命中 distribution-overload 场景后，模型被困在三条互相拧的约束里：

1. **结构冻结无 COUNT 形态**：`scenario_strict` 模式下候选 SQL 必须匹配本步骤已注册模板的结构指纹（skill_policy.py L319-358 `_check_sql_against_templates`，L322 注记「scenario_strict 结构指纹不一致即拒绝」）。现有 overload 步骤注册的 4 个模板全是**逐台区明细行形态**（step2_power_aggregation.sql 终端 SELECT 返回 负荷类型×台区 行），模型要出数量只能写 `SELECT COUNT(...)` → 指纹不匹配被拒；
2. **答案结构强制四段**：SKILL.md L70-74 `output.final_sections: [conclusion, findings, warning, recommendation]` + L247「一句话结论」模板是四段式总结（含 Y/Z/A-D 计数）——与「用户只要一个数」拧着；
3. **契约层极简注入被显式排除**：data_intelligence.py L138 `if question and is_count_intent(question) and getattr(contract, "route_type", "") != "scenario"` —— 13-L 实施时实测强注极简段**加剧**冲突（L134-136 注记），故场景排除、留待模板层扩展。

实测结果（主文档 13-L 登记）：模型 reasoning 1652 tokens 打结 163s。

### 1.2 设计目标

COUNT 题命中场景时：模型走**合法 COUNT 模板**出数，答案一句结论+口径注（对齐 13-L generic 侧 `_CONTRACT_COUNT_ANSWER` L97-102 同款形态）；现有明细场景题、直通 COUNT 题零回归。**机制零新增**（零后端代码改动，全部落在技能数据文件——与 13-W「接口形状不变」同款哲学）。

### 1.3 详细设计（四件）

**件1：新模板 `templates/step2_count_overload.sql`**

派生规则：前 4 个 CTE（计量点台区/台区容量/dist_power/flagged）与 step2_power_aggregation.sql **逐字节一致**（同表集合、同 JOIN 骨架 → 模板表集合校验天然通过；且同前缀对 13-I C1 前缀缓存友好），仅终端 SELECT 换聚合形态。骨架草案（实施时以真实模板为准，发布清单五条保证自洽）：

```sql
WITH 计量点台区 AS ( /* 与 step2_power_aggregation.sql L6-16 逐字节一致 */ ),
台区容量 AS (     /* L17-28 一致 */ ),
dist_power AS (   /* L29-41 一致 */ ),
flagged AS (      /* L42-49 一致 */ ),
判定 AS (
  SELECT 负荷类型, 台区编号,
         CASE WHEN MAX(over_run8) >= 8 THEN '过载'
              WHEN MAX(heavy_run8) >= 8 THEN '重载'
              ELSE '正常' END AS 判定
  FROM flagged GROUP BY 负荷类型, 台区编号
)
SELECT COUNT(DISTINCT CASE WHEN 判定 IN ('重载','过载') THEN 台区编号 END) AS 重过载台区数,
       COUNT(DISTINCT CASE WHEN 判定 = '过载' THEN 台区编号 END) AS 过载台区数,
       COUNT(DISTINCT CASE WHEN 判定 = '重载' THEN 台区编号 END) AS 重载台区数,
       COUNT(DISTINCT 台区编号) AS 判定台区总数
FROM 判定
```

单行四列，`row_count=1`。注：判定逻辑从 step2 终端 SELECT 的 MAX(over_run8)/MAX(heavy_run8) 口径平移（L59-61），阈值口径不变（重载≥80% 连续 8 点、过载≥100% 连续 8 点，rules.md）。

**件2：SKILL.md 步骤注册**

`steps[].templates` 的 overload 步骤（L117-120）追加一行 `- templates/step2_count_overload.sql`。生效链（全部已有机制，无需改码）：
- `_resolve_step_templates(contract)`（skill_policy.py L326）自动带出 → COUNT 形态成为合法指纹；
- 契约消息「本次允许的 SQL 模板」行（data_intelligence.py L124）自动含新模板 id；
- 13-G 模板预载自动读新模板文件进契约消息（同 skill_id+步骤逐字节一致约束不受影响）。

**件3：SKILL.md 两处正文**

- 「按需读取子文件」表（L193-201）加一行：`| 统计/多少/几个/数量类（如"统计重过载台区数量"） | 第2步 COUNT | /skills/scenarios/distribution-overload/templates/step2_count_overload.sql | - |`
- 「输出规范」新增 COUNT 例外条款：**COUNT 类问法（问数量/多少/几个）只输出一句结论（含具体数值）+ 一句口径注（阈值口径/时间范围/数据源），合计 ≤150 字，`answer_type=aggregation`；不展开结论/发现/风险/建议四段**。此为 `output.final_sections` 的问法级例外——已核实 final_sections 是提示词层协议（skill_policy.py 无代码强制，仅契约消息文本），正文例外条款即可生效。

**件4：契约层不动**

data_intelligence.py L138 的 `!= "scenario"` 排除**保持不变**——场景 COUNT 的极简指令由 SKILL.md 正文（件3）承载，契约层不再强注（13-L 实测强注会两头拧）。

### 1.4 备选升级路径（B 方案，件3 不够时启用）

若 e2e 仍见模型选明细模板不选 COUNT 模板：在 L138 增加场景分支，但注入文案**引用具体模板 id**（「本次为计数型问题，使用模板 step2_count_overload.sql 派生单行聚合」）而非泛化极简指令——与结构冻结兼容（指路不破笼）。切换条件与结果登记进主文档。

## 三、14-C AB-4 两项 e2e 豁免收口

### 3.1 TTL 降级：env 旋钮 + e2e

现状：query_result_store.py L10 `_RESULT_TTL = 600` 硬编码（L4 注记 TTL 10min+上限 64 双淘汰）。设计：
- 旋钮：`_RESULT_TTL = int(os.getenv("TUPU_QRS_TTL_SECONDS", "600"))`，容量同款 `TUPU_QRS_CAP`（默认 64）。默认值不变=零行为变化；
- e2e 剧本：设 TTL=5 重启后端 → 提问 → 等待 >5s 触发 result_ref 过期 → 断言前端收到降级提示而非表格 → 恢复默认。验收即勾销 AB-4 豁免登记第一条。

### 3.2 并发帧序：转单元级（设计裁决）

并发 e2e 与 Playwright 串行铁律**结构性冲突**（曾出现模型「未收到用户请求」串扰，AGENTS.md 定调）。裁决：帧序正确性改在 translator.py ThinkRoundClassifier（四态七动作码，13-D 产物）做**单元级不变量测试**——乱序/交错输入帧 → 输出序确定；e2e 层豁免永久登记（不是欠账，是铁律下的正确取舍）。主文档 13-AB 豁免登记第二条据此改写。
