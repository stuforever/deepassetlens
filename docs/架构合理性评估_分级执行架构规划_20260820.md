# 架构合理性评估：分级执行架构（L0/L1/L2）规划

> 2026-08-20 · 设计窗口产出
> 问题：「每次问答需要这么多链路，是否真的对？时间也太长了。」
> 方法：把 40+ 步清单按耗时归类，分离「护栏成本」与「智能成本」，再回答架构该不该改、怎么改。

---

## 一、直接回答：架构对不对？

**分三层判，不能一概而论：**

| 层 | 判定 | 论据 |
|---|---|---|
| 护栏层（路由/契约/SkillPolicy/模板守卫/引擎锁/输出契约/审计三账） | ✅ **对，且便宜** | 全部是毫秒级代码检查，40 步里占 ~35 步、总耗时 <0.5s。它们是准确性与安全的来源，砍掉任何一层都会让某类事故回归 |
| 传输层（SSE/中间件栈/事件流/checkpoint） | ✅ 对，开销可控 | 中间件钩子微秒级；SSE 渲染是体验必需 |
| **执行模型（ReAct 循环作为唯一执行方式）** | ❌ **不对——冷热不分** | 这是 180s 的真正来源：一个问了上百遍的 COUNT 题，和第一次见到的多跳探索题，走同一条 5 轮探索链 |

**一句话诊断：护栏层是对的且便宜；错的是把「探索型执行模型」当成了唯一执行模型——已知问题的答案被反复重新推导。**

---

## 二、时间去哪了：链路多 ≠ 慢，LLM 轮次才 = 慢

以「统计用电客户数量」（generic 未锚定）实测结构：

| 成本类别 | 构成 | 耗时 | 占比 |
|---|---|---|---|
| **护栏成本**（35+ 步） | 路由正则/契约构造/五关 precheck/模板校验/事件流/三本账 | **<0.5s** | ~0.3% |
| 数据成本 | embedding+Qdrant 示例检索、SQL 执行、checkpoint 读写 | ~2-4s | ~2% |
| **智能成本**（6 次 LLM 调用） | R1 读技能/R2 定位/R3 源模式/R4 执行决策/R5 作答 + rubric grader（±重写一轮） | **~155-215s** | **~97%** |

**关键洞察：把 40 步链路砍一半，省不了 1 秒；把 LLM 轮次从 6 降到 0，省 175 秒。** 优化对象从来不是「步骤数」，是「模型调用数 × 单轮延迟」。

单轮 ~25s 的构成：大系统提示（基础提示+AGENTS.md+技能目录+契约+17 工具 schema）远程重发（无显式缓存控制）+ 生成时间。降单轮的杠杆有限（换更快模型=产品决策、缩提示=边际收益），**轮次数才是自由度最大的杠杆**。

---

## 三、根因诊断：为什么会这样？公不公平地说

这套架构是从一连串准确性事故里长出来的：P0 死循环催生契约收窄、schema 漂移催生模板守卫、措辞敏感催生金标 eval……**每一层都在关闭一个具体的洞，没有一层是为延迟而加的。** 所以它「正确但昂贵」——为信任付出了全额时间成本，而延迟从未被当作一等设计约束。

结构性失误只有一个：**ReAct 被当成了唯一执行模型**。场景剧本明明已经把确定性流程编码成了模板+步骤+【动态】片段，却还要让 LLM 每轮重新「决定」一次已经决定好的事——Agent 在扮演一个昂贵的剧本解释器。

---

## 四、目标架构：三级执行体系 + 学习飞轮

### 4.1 分级模型（类比 CPU 缓存层级）

```
用户问题
  → 路由分类器（规则+示例命中强度，毫秒级）
     ├─ L0 直通管道   锚定精确题：execute→渲染,  0 次 LLM,  2~4s
     ├─ L1 锚定代理   锚定+变化题：首选计划注入, 1~2 轮,  8~15s
     ├─ L2 完整代理   冷题/新实体：完整探索,     3~4 轮,  60~105s
     └─ 澄清分支      多义撞车：出卡问用户
学习飞轮：L2 的成功答案经 👍/金标 → 灌示例库 → 该题未来升级 L1/L0
```

### 4.2 各级触发条件与安全边界

| 级 | 触发 | 安全承接 | 已有设计 |
|---|---|---|---|
| L0 | sim≥0.95 + count 类意图 + 无动态条件 + 示例 enabled | 来源可信（验证 SQL 单源）+validate_sql+模板白名单；执行报错自动回退 L2 | 批9 |
| L1 | sim 0.85~0.95 或带动态条件 | SkillPolicy 五关照过 + 首选计划注入（模型只做微调与执行） | 批2-C |
| L2 | 无锚定/新实体/多跳/澄清后 | 现行全套护栏 + rubric 仅高风险启用 | 批1-B/2-D/E |
| 飞轮 | 👍确认/金标通过 → 示例库 | review 队列管 👎；管理页可禁用 | 批2-C/M4 |

### 4.3 延迟目标（诚实测算）

| 指标 | 现状 | 目标 | 手段 |
|---|---|---|---|
| L0 题（高频统计类） | ~180s | **2~4s（0 轮）** | 批9 直通管道 |
| L1 题（锚定+变体） | ~180s | **8~15s（1-2 轮）** | 批2-C/D/E |
| L2 题（冷题） | ~180s | **60~105s（3-4 轮+rubric 分档）** | 批1-B/2-E + 单轮压缩 |
| P50（混合流量） | ~100-180s | **<10s**（L0 占比上来后） | 飞轮推动 L0 占比至 60%+ |
| L0/L1/L2 占比目标 | 当前 0/0/100% | **60%/20%/20%** | 飞轮 + 金标扩容 |

## 五、什么必须保留 / 什么可以裁掉（诚实清单）

### 必须保留（动不得）
- 契约+SkillPolicy 五关闸门（fail-closed 安全底座）
- validate_sql 安全校验（所有执行路径含 L0）
- 引擎锁定语义（防混用）
- stop_when 终止纪律、纠错循环≤2
- 输出契约（明细唯一由前端承载）
- 三本账持久化 + Playwright e2e 验收纪律
- checkpoint 会话机制

### 可以裁掉/绕开（按题分级）
| 冗余 | 只对谁冗余 | 裁法 | 批次 |
|---|---|---|---|
| rubric grader（20-40s） | 锚定题/确定性输出 | 分档直通；L0 天然免评 | 批1-B |
| read_file 技能轮（25s） | 有指引预载的题 | 指令嵌契约 | 批2-E |
| search_entities 轮（25s） | 实体可预解析/示例带表的题 | 候选实体注入/直通用记录值 | 批2-D/批9 |
| batch 源模式轮（25s） | 引擎已记录的锚定题 | 直通按 example.engine 直取 | 批9 |
| 答案生成轮（25-40s） | 可枚举结果的题 | 模板渲染器填槽 | 批9 |
| 重复示例检索（0.5-3s） | 60 秒内重复提问 | 短窗 LRU | 批7 |

### 不能省但常被误以为能省的
- 每轮上下文重发：OpenAI 兼容协议无显式缓存控制，只能靠前缀稳定吃服务端隐式缓存（批5）——省 TTFT 和账单，不省轮次；
- checkpoint 读写：会话连续性的地基；
- 三本账写入：观测与评估的数据源，砍了就是盲飞。

## 六、与已设计批次的关系：批1-9 就是这张图的施工图

分级架构不是一个新项目，而是既有九个批次的**目标态命名**：

| 批次 | 在分级架构中的角色 |
|---|---|
| 批1（答案直出+rubric 分档） | 全部级别的展示层改造 + L2 减税 |
| 批2-C/D/E（减轮次三件套） | **L1 层的定义与实现** |
| 批7（检索单调用化） | 全级别共享的数据成本压缩 |
| 批8（混合检索） | L2 冷题的召回质量（减少探索失败重试） |
| 批9（直通管道） | **L0 层的定义与实现** |
| 批5/6（缓存/路由治理） | 全级别的基础设施 |
| 金标扩容+反馈闭环（M4 已落地） | **飞轮的燃料系统** |

不需要推倒重来，也不建议大爆炸式重写（现有系统在正确性上已被验证）。**增量路线：先把 L0 打出来（批9），再用飞轮把流量从 L2 逐步搬到 L0/L1。**

## 七、v3 方向登记（现在不做）

- **剧本编译执行**：场景契约编译为确定性执行计划（代码驱动工具调用，LLM 只填【动态】槽位）——比 L0 更彻底，但等于自建工作流引擎，等 L0/L1 飞轮数据证明仍有必要再做；
- **小模型分工**：路由/改写/grader 用轻模型、主答用旗舰——依赖连接治理成熟度；
- **预取**：用户输入时 debounce 预检索示例——交互复杂度不值当前阶段。

---

## 八、一句话回答

**架构的护栏层是对的且便宜（毫秒级），错的只是「所有问题都走完整 ReAct 探索」这一刀切——180s 里 97% 是 6 次 LLM 调用的智能成本，35 步护栏合计不到半秒。** 解法不是拆链路，是加层级：L0 直通（0 轮）/L1 锚定代理（1-2 轮）/L2 完整代理（3-4 轮）+学习飞轮把流量从冷搬到热。批1-9 已是它的施工图，无需推倒重来。
