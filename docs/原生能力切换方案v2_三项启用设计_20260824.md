# 原生能力切换方案 v2：response_format × store × interrupt_on 三项启用设计

> 2026-08-24 · 设计窗口产出 · 本文档修订并部分推翻《DeepAgents原生能力切换方案》中对此三件的保守结论
> 触发：用户明确要求使用这三项原生能力。重新解剖源码后确认——**三项都可以启用，且各有真实收益**。

---

## 〇、先修正我自己的两个过时判断（诚实记录）

| 我此前的说法 | 源码核实后的修正 |
|---|---|
| 「response_format 会禁用工具调用」 | **已过时**。langchain 1.x 的 create_agent 中 response_format 是循环结束后的结构化输出步骤，不禁用工具；框架自己的 rubric grader 就是带 response_format 跑的子代理（rubric.py 明文要求）。graph.py 仅做透传（L927），无任何工具互斥警告 |
| 「store 无向量索引被 Qdrant 替代」 | **只对示例库检索成立**。store 的正确定位不是替代示例库，而是我们根本没有的能力：**跨会话的用户级长期记忆**（示例库是题库，store 是「记住这个用户的偏好」） |
| 「interrupt_on 静态配置没用」 | **对了一半**。它确实表达不了运行时条件触发，但「按工具固定人审」是自研件没覆盖的另一类需求（演示模式/高危工具常审），且 graph.py 支持 `_merge_fs_interrupt_on` 与权限派生的中断合并——框架明显鼓励声明式组合 |

## 一、response_format 启用设计（与 v2 纯结构化交付天作之合）

### 为什么现在恰好该用它
交付体验 v2 定调「正文永不流式上屏、done 一次成型」——那么答案天然应该是**结构化对象**而不是一段要靠正则清洗的 markdown。schema 直出 → 前端交付卡槽位直接映射，scrub 从主力降级为兜底。

### 设计

```python
# app/services/answer_schema.py
class FinalAnswer(BaseModel):
    conclusion: str            # 结论（一句话）
    findings: list[str]        # 关键发现（逐条）
    risks: list[str]           # 风险与限制
    recommendations: list[str] # 后续建议

agent = create_deep_agent(..., response_format=FinalAnswer)
```

- 前端交付卡：`conclusion`→结论区，`findings[]`→发现列表，`risks[]`→风险区，`recommendations[]`→推荐 chips 数据源；
- 输出契约 validate_final_output/scrub_markdown_tables 降级为兜底校验（schema 缺字段时才介入），治理记录降级次数；
- 分路径推进：场景路径先行（答案形态最固定）→ generic 路径跟进；直通管道不涉及（模板直出本来就是结构化渲染）。

### POC 必验四点（实施窗口执行）
1. 与 stop_when/SkillPolicy 工具收窄的相互作用（结构化步骤发生在循环结束后，预期无冲突，需实测）；
2. 时延增量：是同轮强制格式还是额外一轮调用——若额外一轮，冷路径评估是否值得（快路径无碍）；
3. 中文内容 schema 遵从率（抽 20 条金标对比）；
4. 事件翻译器对该结构化调用的 token 归类（v2 下反正丢弃，确认不误触发状态机即可）。

量级：POC 0.5d + 接入 1d。

## 二、store 启用设计：用户级长期记忆层（新能力，非替代）

### 定位
```
Qdrant 示例库  = 题库（问题→SQL 的经验，检索注入）      ← 保持不动
store 长期记忆 = 用户偏好（「只要华东区域」「结果按状态分组」）← 新增层
checkpoint     = 会话内状态（last_skill/scope）          ← 保持不动
```

### 设计

```python
# 装配：store=AsyncSqliteStore()（起步用本地；多实例再切 Postgres）
# 命名空间：(user_id, "preferences")
# 读：prep 阶段取偏好列表 → 契约消息追加「已知偏好」段（≤5 条，带来源标注）
# 写：两条通道，全部走批11 审核制
#   ① 显式指令捕获：「记住我以后只要华东区域」→ 提取为候选偏好 → 待审
#   ② 管理页手工录入
# 可控性配套（呼应批11 三权）：TUPU_USER_MEMORY_ENABLED 总闸 +
#   管理页偏好列表（查看/编辑/删除/启停）+ 每条偏好注入时 EvidenceCard 可见
```

### 边界
- 不做自动归纳写入（不让 LLM 自行总结用户画像入库）——所有写入人工可审，吸取示例库教训；
- 偏好仅作提示词参考，不改变权限边界（路由/契约不受偏好影响——权限仍由确定性路由决定）。

量级：1d（含管理页最小 UI）。

## 三、interrupt_on 启用设计：策略级固定审批轨（双轨制）

### 发现
`interrupt_on={"tool": True | InterruptOnConfig(allowed_decisions=...)}` 在**每次该工具调用前暂停人审**，且框架会把文件系统权限派生的中断与之合并（`_merge_fs_interrupt_on`）——声明式组合是框架的设计意图。

### 双轨制设计

| 轨道 | 机制 | 管什么 |
|---|---|---|
| **静态策略轨（新增，框架 interrupt_on）** | 装配时按配置传入 `interrupt_on={工具: 审批配置}` | **策略级固定审批**：演示/培训模式一键「所有 execute 工具人审」、高危工具常审开关 |
| 动态异常轨（保持自研） | SkillPolicy 条件 interrupt | 运行时异常触发（TABLE_MISSING 且 generic 才审） |

### 落地要点
- 配置来源：批12-B 的 guard_policies 管理页加「审批轨」区块（勾选哪些工具需要人审）——与守卫策略同一张管理面；
- **Agent 单例缓存键必须纳入审批配置版本号**：interrupt_on 是装配期参数，配置变更需重建对应 Agent（否则改了不生效）；
- 恢复交互复用现有 HITL 前端组件（审批卡），决策枚举对齐 InterruptOnConfig.allowed_decisions（approve/reject/respond）；
- 远程 AsyncSubAgent 不继承 interrupt_on——我们不用 subagents，无影响。

量级：1d（含缓存键改造与管理页区块）。

## 四、修订后的切换全景

| 能力 | v1 结论 | v2 结论 |
|---|---|---|
| response_format | 有意不用（判断过时） | **T1-POC 启用**：场景路径结构化终答 |
| store | 替代方案更优 | **启用为新能力层**：用户偏好记忆（审核制+总闸） |
| interrupt_on | 静态表达不了条件触发所以不用 | **双轨制启用**：静态策略轨交给框架，动态异常轨保持自研 |
| PatchToolCalls / Summarization 参数化 | T1 | 维持 T1 |
| subagents/shell/sandbox/prompt_caching/langsmith | 不用 | 维持不用（理由不变） |
