# 执行链用处详解 × 框架承载性分析（以「统计用电客户数量」为例）

> 2026-08-20 · 设计窗口产出（只读分析）

# 上部：逐步用处详解

## 1. 请求接入与会话准备

### 1.1 handleSubmit → POST /freeplan/stream（SSE）
- **在干什么**：用户点发送，前端与后端建立一条 SSE 长连接，之后后端每有进展（思考/工具/数据/答案）就推一个事件过来。
- **本例**：点发送后约 1 秒内看到「小探正在运行中」，随后每个步骤实时上屏。
- **没有它会怎样**：普通 POST 请求要等全部跑完才返回——180 秒白屏转圈，用户必然以为死机。
- **坏处/代价**：SSE 是单向通道，网络断了整题要重问（无断点续传）；连接期间占用后端一个协程；若中间有反向代理默认开缓冲，事件会被攒批延迟到达（部署时注意关缓冲）。

### 1.2 chat_freeplan_stream() 编排主干
- **在干什么**：一个 1059 行的生成器函数，把锁、路由、契约、Agent 调用、事件翻译、收尾串成一条流水线。
- **没有它会怎样**：这些逻辑散在各处就没有「一条链」的概念，事件顺序和异常收尾无法保证。
- **坏处/代价**：**巨型函数，职责过载**——改任何一段都要在这一个文件里找位置；异常路径复杂（追问改写读历史时踩过 checkpoint_ns 的坑：`ns="freeplan"` 触发 Subgraph not found 被静默吞掉，后来改无 ns 读取）。这是全工程最需要拆的文件之一，但拆它有回归风险，所以一直没动。

### 1.3 _SESSION_LOCKS[thread_id] 会话锁
- **在干什么**：同一会话同时只允许一个问题在跑。
- **本例**：用户在 180 秒执行期间再点一次发送，第二个请求不会另起炉灶。
- **没有它会怎样**：两个 Agent 循环同时写同一个 checkpoint，消息历史交错污染，前端收到两条流混在一起。
- **坏处/代价**：进程内字典实现——**单机有效，多实例部署锁不住**（当前单机演示无影响）；第二个请求的体验取决于实现（等待或拒绝），没有排队机制。

### 1.4 create_tupu_agent() + 单例缓存
- **在干什么**：Agent 装配（连 MCP、挂中间件栈、挂文件后端、注册权限）很贵，按 llm_connection_id 缓存复用。
- **没有它会怎样**：每个问题都重新装配一遍，白白多花几秒且 MCP 连接反复建立。
- **坏处/代价**：单例跨请求共享 → **任何「每请求状态」都不能塞进 Agent**，只能走 context/checkpoint/contextvar（rubric 桥就是为绕这个限制）；换模型连接后缓存要失效（已按 connection_id 分键处理）。

### 1.5 agent.aget_state() 读 checkpoint
- **在干什么**：LangGraph 把每轮的消息和状态（含我们写入的 last_skill/last_step）持久化在 SQLite，这里读回来。
- **本例**：首轮读出空 → 走新路由。若第二轮问「那上个月的呢」，这里能读到上轮场景。
- **坏处/代价**：checkpoint 只增不减，长时间运行 SQLite 文件膨胀；SQLite 并发写能力一般（演示场景够，生产要换 PG checkpointer）。

## 2. 追问改写

### 2.1 is_followup_question() 规则判定
- **在干什么**：纯字符串规则——问题 <12 字或含「那/它/上述/该/也/再」→ 疑似追问。
- **本例**：「统计用电客户数量」18 字无指代词 → 直接跳过，零成本。
- **没有它会怎样**：所有问题都过改写 LLM，每问白加几秒。
- **坏处/代价**：规则有漏判误判——「再查一下客户数」含「再」但其实可独立作答（误判，多一次改写调用）；「上个月呢」4 个字完美命中（正确）。好在误判的代价只是多一次改写，改写结果还经路由，不致错答。

### 2.2 rewrite_followup_question() 单轮改写
- **在干什么**：触发时，把会话尾部几轮历史 + 追问发给 LLM：「改写成独立完整问题」。
- **没有它会怎样**：「那上个月呢」进路由后模型不知道「那」指什么，可能查错对象。
- **坏处/代价**：本身是 LLM 调用，实测 httpx timeout 在 OpenAI client 重试下不可靠（代码注释：曾拖到 69s），所以外层 `wait_for 8s` 硬切，超时后孤儿线程自行消亡；**改写可能改错意图**——所以前端显示「理解为：xxx」让用户能发现和纠正（设计内的透明性补偿）。

## 3. 路由与契约

### 3.1 route_user_input() 四级路由
- **在干什么**：毫秒级关键词匹配，四级优先：上轮场景沿用 → 精确场景剧本命中 → 多场景撞车要澄清 → generic 兜底。
- **本例**：「数量」不在任何场景的 triggers 里（sql-query 技能 frontmatter 压根没写 triggers）→ 落 generic。
- **没有它会怎样**：所有问题都走 generic 自由问答，场景剧本（模板强约束的确定性路径）形同虚设。
- **坏处/代价**：**关键词匹配的固有缺陷=措辞敏感**（金标 eval 发现过：「总数」稳过、「数量」一度不稳）；新增场景要维护 triggers 列表；触发词撞车时只能出澄清卡让用户选（体验断点）。

### 3.2 QueryContract.generic() 构造契约
- **在干什么**：生成「契约」对象：允许 17 个只读工具、绝对禁止 6 个（task/write_file/edit_file/execute/grep/glob）、拿到结果即停、带 rubric 自评标准、输出模式。
- **本例**：模型若试图调 write_file 写个文件，SkillPolicy 拿契约一查——禁止，直接拒。
- **没有它会怎样**：模型面对全部工具（含写文件/开子代理/跑 shell），问数系统变成通用 Agent，安全和准确性都失控。
- **坏处/代价**：契约内容代码写死，模型无法申请临时提权（安全设计的有意取舍）；白名单与 MCP 工具名册要手工同步——**之前 kg_api 幽灵工具 P0 就是名册脱节造成的**，现在有交叉校验测试（从 mcp.list_tools() 取唯一事实源）防回归。

### 3.3 detect_aggregate_intent()
- **在干什么**：命中「分布/占比/构成」类词 → 契约挂聚合意图标记，追加「必须 GROUP BY」指令 + 结果层硬校验钩子。
- **本例**：「数量」是计数不是分布 → 不挂。
- **没有它会怎样**：「各电压等级的用电客户分布」这类题模型会退化成返回明细全表（eval 实测三轮里两轮挂在这）。
- **坏处/代价**：纯关键词有边界 case（「各分类数量」是分布、「数量分布」双语义）；且分布意图判定只在路由期做一次，改写后的问题要补挂（stream.py:172-179 专门处理了这个边角）。

## 4. 契约消息与示例注入

### 4.1 _build_contract_system_message()
- **在干什么**：把契约翻成人话 SystemMessage：你能用什么、不能用什么、引擎还没定先去确认、拿到结果就停、明细别写进答案。
- **没有它会怎样**：模型不知道本轮的约束边界，只能靠 SkillPolicy 硬拦——拦了也不知道为什么，纠错效率低。
- **坏处/代价**：**提示词约束是软约束**（模型可能不听话），所以真正的硬约束在 SkillPolicy 中间件——双层设计：提示词引导 + 中间件拦截，缺一不可；这段文本每轮都在系统消息里占 token。

### 4.2 build_examples_payload() 示例检索
- **在干什么**：问题向量化 → Qdrant 搜「历史上验证过的同类问答」top-3，连同验证过的 SQL 一起追加进契约消息。
- **本例**：命中金标「统计用电客户总数」的示例（语义几乎同题），模型看到验证过的 `SELECT COUNT(*) FROM dim_cst_elec_cons_cust WHERE cust_id IS NOT NULL`，照猫画虎。
- **没有它会怎样**：模型每次从零构造 SQL，同类问题的稳定性全靠运气（措辞敏感就是这么来的）。
- **坏处/代价**：每问多一次 embedding HTTP + Qdrant 检索（0.5-3s）；Qdrant 挂了静默跳过（主链路零依赖，好设计）但命中率也归零；示例可能过时（schema 漂移）——有漂移事件自动禁用兜底；「仅供参考禁止照抄」是提示词约定，模型真照抄了还有 validate_sql + 纠错循环兜底，风险闭环。

### 4.3 input_messages 最小消息集
- **在干什么**：本次调用只放 [契约 SystemMessage, 用户问题 HumanMessage]，历史对话由 checkpoint 自动带。
- **坏处/代价**：契约消息每次请求都新建（不持久化进历史，故意如此——防止旧契约污染新问题的约束），所以每轮都重新构造一次，微秒级，无感。

### 4.4 aupdate_state() 写回 last_skill/last_step
- **在干什么**：路由定案后写回 checkpoint，下一轮 1.5 步读它判断「沿用还是新路由」。
- **坏处/代价**：多一次 SQLite 写；写失败只 warn 不阻断——下一轮失去沿用能力，退化为重新路由（体验略降，不出错）。

## 5. Agent 启动与状态注入

### 5.1 rubric 注入调用状态
- **在干什么**：把评分标准 4 条（数字必须来自工具返回/口径披露/空结果不臆断/量词对齐）放进 invoke state，激活 RubricMiddleware。scenario 模式置 None 不激活。
- **坏处/代价**：**每个 generic 问题固定 +20~40s grader 调用**——这是 180s 里那 30s 的来源；批1-B 分档直通（示例锚定免评）就是治它。

### 5.2 _RUBRIC_HOOK_CTX contextvar 桥
- **在干什么**：框架的评估事件走 stream_writer（custom 流），astream_events 收不到；用 contextvar 把评估结果桥到当前请求的 SSE 和治理记录。
- **坏处/代价**：contextvar 是隐式传递，跨请求串扰风险——所以 finally 里必须 reset（stream.py:1023-1025 已做）；调试时不直观（事件不走在主流里）。

### 5.3 agent.astream_events(v2)
- **在干什么**：LangGraph 事件流总线——模型每个 token、每次工具调用起止、中间件自定义事件全从这里出。
- **坏处/代价**：v2 事件语义繁杂（on_chat_model_stream/on_tool_start/on_custom_event 各有数据形态），编排层大半代码在做事件归一化；**框架升级若改事件语义，这里要跟着改**（0.6.12 固定版本的纪律就是为了压住这类漂移）。

## 6. ReAct 主循环（5 轮）

### 6.1 R1 read_file 读技能
- **在干什么**：Skills 渐进披露——系统提示里只有技能目录（一行简介），模型需要细节时自己 read_file 读全文。sql-query/SKILL.md 里有 COUNT/GROUP BY/TopN 写法对照表。
- **没有它会怎样**：全部技能全文塞进系统提示——上下文爆炸；不塞——模型不知道写法约定（比如「排名必须返回实体行+指标值，禁止只返回 COUNT」）。
- **坏处/代价**：**多花一整轮（~25s）**——批2-E 指引预载（按意图把对应写法段直接嵌进契约消息）就是省这轮。

### 6.2 R2 search_entities 定位实体
- **在干什么**：语义检索「用电客户」对应哪个实体/物理表（dim_cst_elec_cons_cust），附字段清单。
- **没有它会怎样**：模型凭训练记忆猜表名——猜错就是 TABLE_MISSING（P0 死循环的起点）。
- **坏处/代价**：检索质量依赖向量库；找不到时模型可能盲试 list_tables（现在有纠错指引把它拉回正路）。

### 6.3 R3 batch_entity_source_mode 引擎裁决
- **在干什么**：一次性查所有涉及表的数据源模式（物理 PG / Doris catalog / API 联邦），返回 recommended_tool；此后引擎锁定，禁止切换。
- **没有它会怎样**：模型可能拿 Doris 的表用物理 PG 工具查（报错或拿到错数据），或逐表查源模式浪费轮次。
- **坏处/代价**：recommended_tool 是优先级启发式（API>Doris>物理），多源混合的真实分布需要批量接口返回后模型综合判断——判断错了有引擎锁拦截兜底。

### 6.4 R4 execute_sql/execute_doris_sql 执行
- **在干什么**：真正跑 SQL，内嵌四道保险：①validate_sql AST 校验（只读/单语句/禁 sleep 类副作用函数/强制 LIMIT 500）②EXPLAIN 预检（坏 SQL 提前拦，省一次完整执行）③引擎连接池（预 ping/回收）④EngineQueryLog 落库（观测数据源）。
- **坏处/代价**：**强制 LIMIT 500 与「所有/全部」语义潜在冲突**（超 500 行静默截断，测试数据小未暴露，已登记）；**UNION 被 validate_sql 拒**（户变关系 P0，技能优先修复方案已定）；Doris 超时 hint 60s。

### 6.5 R5 答案生成
- **在干什么**：基于工具结果写 A-E 交付（结论/关键发现/风险/建议），明细不重复贴（前端表格承载）。
- **坏处/代价**：最长的一轮生成（300-500 token 流式，25-40s）；数字准确性靠 rubric + 输出契约双兜——模型引用摘要里的数字时是可靠的（DataSummary 的摘要含 row_count 等聚合事实），引用样本行下全量结论则靠 rubric 第 3 条拦。

## 7. 中间件栈（环绕每次调用）

### 7.1 SkillPolicyMiddleware —— 受控平台的心脏
- **在干什么**：每次工具调用前过五关：①禁用工具拒 ②不在允许集拒 ③引擎一致性（锁定了 Doris 就不许用物理工具）④已拿结果禁止再查 ⑤SQL 模板指纹校验。失败时给结构化纠错指引（错误分类学：表缺失→search_entities 重定位/语法错→validate_attributes/超时→精简 SQL），同一错误纠 2 次还不好→直接失败卡。
- **本例**：模型拿到 COUNT 结果后若想再调 execute_sql「确认一下」，第 4 关拒掉——单次查询纪律。
- **坏处/代价**：规则复杂，新增工具要同步三处（白名单/ENGINE_TO_TOOLS/提示词）——靠交叉校验测试防漂移；fail-closed 设计（契约丢失时全部拒绝）安全但极端情况下会误伤正常流；每工具调用多一次毫秒级检查，可忽略。

### 7.2 SkillEntityResolverMiddleware
- **在干什么**：剧本/模板里写 ⟦用电户⟧，read_file 返回时机制性替换成物理表名（查 SKILL.md 的 entity_aliases 映射，三方核对：技能↔元数据↔PG）。
- **没有它会怎样**：模型把模板里的中文占位符直接写进 SQL，或凭记忆翻译——错表名高发。
- **坏处/代价**：只对技能文件内容生效（模型自己写的 SQL 里的中文名不管——但场景模式下 SQL 必须与模板指纹一致，间接管住了）；映射表要随 schema 维护。

### 7.3 DataSummaryMiddleware
- **在干什么**：工具返回 101 行明细时，全量直推前端表格（sql_result 事件），给模型的 ToolMessage 只留 10 行摘要。
- **没有它会怎样**：几百行明细灌进模型上下文——token 爆炸、后续每轮更慢、可能撑爆窗口。
- **坏处/代价**：**模型只「看到」10 行**——样本≠全量的纪律靠剧本和提示词（distribution-overload :184 专条：对行内字段只能说「样本显示」，全量结论必须 SQL 显式聚合）；违反时靠 rubric 第 3 条拦。这是「省 token」与「模型视野」之间的有意取舍。

### 7.4 DecisionGateMiddleware（默认关）
- **在干什么**：启用后模型每次调工具前必须输出「已知/判断/因此」三段式理由，闸门校验格式与范围。
- **坏处/代价**：每轮多生成几十 token（耗时+成本）；**当前默认关闭**——你在日志里看到的决策文案是提示词规约的产物，格式不对也无人拦截，审计强度打折。

### 7.5-7.7 框架三件套（Skills/Filesystem/Memory）
- **在干什么**：技能目录注入 + read_file/ls/write_todos 文件工具 + AGENTS.md 常驻纪律（所有/全部类一次查完、户变最小终止等）。
- **坏处/代价**：Filesystem 默认带 write_file/edit_file 写工具——**问数场景必须排除**（HarnessProfile excluded_tools 就是干这个的，漏配就是安全事故）；AGENTS.md 写长了每轮都占 token（所以限一屏 60 行）。

### 7.8 Summarization 定制（子类化）
- **在干什么**：会话超 30k token 自动摘要旧消息（框架默认值不适配国产模型上下文，子类化改阈值），外加 compact_conversation 手动压缩工具。
- **坏处/代价**：**摘要是有损压缩**——被摘要掉的工具结果细节后续可能要用（模型只能重新查，好在有纠错路径）；子类化 + excluded_middleware 的技巧依赖框架内部命名，框架升级要跟验。

### 7.9 RubricMiddleware
- **在干什么**：答案写完后 grader 子代理对照 4 条标准评分，不满意注入修订消息让模型重写（封顶 1 轮）。
- **坏处/代价**：每问 +20~40s，重写再 +25~40s；**grader 本身可能误判**（好答案被打回重写， rewritten 版未必更好）；grader 用同模型则成本翻倍（批3-G 轻模型配置就是降这个成本）。

## 8. 终止与自评

### 8.1 stop_when 收窄允许集
- **在干什么**：拿到结果后把数据工具物理移出允许集——模型想再查，工具层面就不存在了。
- **没有它会怎样**：P0 死循环（反复分页/换引擎重查/盲探），5 分钟超时烧 token。
- **坏处/代价**：合理的补充查询诉求也会被拒（设计取舍：先终止，用户追问再起新一轮）；multi_engine 场景的复合终止（两源取齐才停）逻辑更绕，是测试重灾区。

### 8.2/8.3 rubric 评分与桥接
- 见 5.1/5.2/7.9。补一条：**评分发生在 agent 流结束前**，所以 final 事件被它压住——这是「答案上屏后还等 30s」的机制根源，批1-A/B 双管齐下治它。

## 9. 输出契约与收尾

### 9.1 validate_final_output + scrub_markdown_tables
- **在干什么**：答案收尾时校验输出契约（禁止 markdown 明细表），模型手滑写了就正则清洗掉 + 记治理事件。
- **坏处/代价**：正则级清洗对复杂表格语法可能洗不净或误伤（好在场景答案的 A-E 段格式相对固定）；「明细唯一由前端表格承载」的契约对模型是反直觉的（它天生爱贴表），所以剧本/提示词/清洗三层反复强调。

### 9.5 三本账（RunEventSink / governance / EngineQueryLog）
- **在干什么**：关键事件账（审计回放）、治理事件账（策略/模板/纠错轨迹）、查询日志账（耗时/行数/引擎）。金标评估、命中率统计、耗时归因全从这三本账取数。
- **坏处/代价**：每问多几次 DB 写（毫秒级，可忽略）；表只增不减，需要清理策略（当前未做——长期运行的运维债）。

## 10. 前端渲染

### 10.1 answer_draft → ThinkStream
- **在干什么**：答案 token 逐字上屏让用户感知「在写答案了」。
- **坏处/代价**：**投屏位置设计错了**——答案流进了思维链面板（像日志），输出区反而等 final 事件才亮。批1-A 改为直出答案气泡。

### 10.4 契约六卡
- **在干什么**：把受控过程可视化——路由卡（走了哪个场景）、范围卡、数据访问卡（查了哪些表/哪个引擎）、决策卡、终止原因卡、证据链卡（示例命中/验证/自评/纠错）。
- **坏处/代价**：信息密度高，普通业务用户可能看不懂——面向的是「想确认答案可信」的人，属于信任建设组件，可折叠。

### 10.5 👍/👎 反馈
- **在干什么**：用户确认的答案（含 SQL）进示例库反哺检索——学习闭环的出口。
- **坏处/代价**：恶意/误点会污染示例库——👎+修正走 review 队列人工审（👍 直接入库是信任用户的取舍，管理页可事后禁用）。

# 下部：自定义件的框架承载性分析

> 判定口径：框架（DeepAgents 0.6.12 / LangGraph）有没有对应物；有则应不应该换；MCP 工具按你说的「够呛」——协议框架接入、逻辑必然自定义，不逐工具赘述。

## 总表

| 自定义件 | 框架对应物 | 能否/应否框架承载 | 判定 |
|---|---|---|---|
| **SkillPolicyMiddleware** | AgentMiddleware 协议（wrap_tool_call hook）+ permissions 参数 | 机制**已经是**框架承载（它就是框架中间件的实现）；规则语义框架没有 | ✅ **姿势正确**：机制框架、规则自定义 |
| **DataSummaryMiddleware** | 同上 | 同上。「工具结果截断+另路推全量」的双通道概念框架没有 | ✅ 姿势正确 |
| **SkillEntityResolverMiddleware** | 同上 | ⟦⟧ 是我们自创标记语法，框架无概念 | ✅ 姿势正确 |
| **QueryContract 数据结构** | context_schema / state_schema | **承载位置已用框架**（runtime.context 传入，SkillPolicy 从 context 读）；数据结构必然自定义 | ✅ 姿势正确 |
| **rubric 机制** | RubricMiddleware | 已用框架件，GENERIC_RUBRIC 文案是内容层 | ✅ 已最优 |
| **技能/记忆/摘要** | SkillsMiddleware / MemoryMiddleware / SummarizationMiddleware | 已用框架件（摘要子类化调阈值） | ✅ 已最优 |
| **HITL 人审**（_check_hitl_interrupt） | **interrupt_on 参数 + langgraph interrupt/Command 原语** | 现在已是「框架 interrupt 原语 + 自定义触发条件（TABLE_MISSING 时才审）」。框架 interrupt_on 是**静态工具级**配置，我们要**条件动态**触发，纯框架配置表达不了 | 🟡 **可以更原生**：把恢复端点/事件协议向框架 Command(resume) 惯例靠拢，减少自研协议面 |
| **SkillRouter 路由** | 无（subagents/task 名义相近但已红线禁用） | LangGraph 条件边理论上能做，但毫秒级关键词路由放图节点里反而重 | ✅ **必须自定义**，且不该进图 |
| **template_guard 模板指纹** | 无 | 框架没有「SQL 模板」概念；sqlglot AST 比对是纯领域算法 | ✅ 必须自定义 |
| **错误分类学 + 纠错循环** | LangGraph retry policy（节点级异常重试） | 框架 retry 是「异常重试」，表达不了「TABLE_MISSING→先去 search_entities 重定位」这种**语义级纠错路由** | ✅ 必须自定义 |
| **stop_when 语义终止** | recursion_limit（暴力硬截断） | 框架只有「跑满 N 步砍断」，没有「拿到结果即收窄工具集」的语义终止 | ✅ 必须自定义 |
| **示例库 qa_example_service** | StoreBackend（长期记忆存储） | Store 是 KV 存储**没有向量索引**，替代不了 Qdrant；注入点现在手工拼 SystemMessage，理论上可做成自定义中间件在 wrap_model_call 注入 | 🟡 检索必须自定义（Qdrant）；**注入点可中间件化**（更干净，但收益小，不急） |
| **输出契约 output_contract** | response_format（结构化输出） | response_format 会禁用工具调用能力（红线排除的正当理由）；validate/scrub 只能自定义 | ✅ 必须自定义 |
| **追问改写 followup_rewrite** | 无 | 框架假设「用户输入即最终输入」，无改写概念；放在 agent 外（stream 层）是正确位置 | ✅ 必须自定义 |
| **引擎三件套 + batch 裁决** | 无 | 纯业务域（Doris/DuckDB/物理 PG 联邦），框架无数据源概念 | ✅ 必须自定义 |
| **观测三本账** | LangSmith tracing | LangSmith 是外接 SaaS 平台，单机演示场景过重（S 阶段不做清单已登记） | ✅ 主动放弃合理 |
| **17 个 MCP 业务工具** | MultiServerMCPClient（协议接入） | 协议框架承载，工具逻辑必然自定义（你的判断正确） | ✅ 姿势正确 |

## 四类归纳

1. **机制已被框架正确承载、逻辑自定义**（姿势正确的最大类）：三个自定义中间件（AgentMiddleware 协议）、契约传递（context）、rubric、技能/记忆/摘要、MCP 协议接入。——框架的价值就在这里：**事件流、checkpoint、中间件协议、工具协议、技能/记忆/自评这些通用件不重造**。
2. **框架有能力、我们主动不用的**（都有正当理由）：subagents/task（安全红线）、response_format（禁用工具调用）、LangSmith（过重）、StoreBackend（无向量索引）。
3. **必须自定义的**（框架无此概念）：路由、模板守卫、错误分类纠错、语义终止、输出契约、追问改写、引擎域、前端。——这些是**问数域的核心资产**，恰好是通用 Agent 框架不该有的东西。
4. **可以更原生、但收益有限的两个**：HITL 向 interrupt_on/Command 惯例靠拢（减少自研协议面）；示例注入点中间件化（更干净）。都列入「机会性优化」，不专门立项。

## 结论

**当前自定义/框架的边界划得是对的**：框架承载通用 Agent 机制（循环/状态/中间件/技能/记忆/自评/工具协议），自定义承载问数域语义（契约/路由/模板/引擎/纠错/证据）。没有出现「框架能做却自造轮子」的浪费，也没有「硬塞进框架」的扭曲。唯二登记项：PatchToolCalls 有测试未装配（批1 顺手补）；HITL 与示例注入存在「更框架化」的空间但收益小。
