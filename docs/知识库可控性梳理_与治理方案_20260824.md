# 知识库可控性梳理：示例库/记忆机制的失控点与治理方案

> 2026-08-24 · 设计窗口产出（API 面实测 + 本会话事故案例支撑）
> 用户定调：不喜欢不可控、自动生成的历史调用记录；改不了、错不能纠、可控力差、不放心。
> 结论先行：**抱怨成立。示例库是全链路唯一的半信任源，却拥有直达模型上下文的通道，而管理面存在硬缺口。**

---

## 一、现状盘点：哪些机制在「自动积累」并回流影响回答

| 机制 | 写入触发 | 回流路径 | 当前可控手段 |
|---|---|---|---|
| **示例库**（tupu_qa_examples + Qdrant） | ①用户👍点击**自动入库**②seed 脚本③手工 POST | 每次 generic 提问检索 top-3 **注入契约消息**（含 SQL 原文） | 列表查看/新增/删除/启停（PATCH 仅 status） |
| 金标库（golden_qa） | eval 脚本/手工 | 只用于评估，不进运行时 prompt | ✅ 完整 CRUD（GET/POST/PATCH/DELETE） |
| checkpoint 记忆（last_skill/last_step+历史消息） | 每问自动持久化 | 跨题沿用场景+实体预解析注入契约 | 无会话级查看/重置入口 |
| AGENTS.md | 手工编辑文件 | 每轮常驻注入 | ✅ 文件级完全可控 |
| EngineQueryLog/governance 三本账 | 自动落库 | 不回流模型，仅人看 | ✅ 只增不改，无风险 |

**风险集中在前三行；AGENTS.md 和三本账本来就是可控的，不在此列。**

## 二、问题清单（按严重度，全部有代码/案例实据）

### P1-a 编辑权缺失：「改也不让改」字面成立
API 面只有 `POST`（新建）/`DELETE`/`PATCH status`——**没有内容编辑端点**。发现某条示例 SQL 过时或错误时，唯一路径是删除再手工重建（且要自行确认 Qdrant 向量同步删除）。对比金标库有完整 PATCH——同一类数据两套待遇。

### P1-b 无审核流：「错了也不让指导」成立
feedback_service 中 👍 直接 upsert 入库（代码中 upsert 逻辑存在、无 pending/approved 状态机）——任何一次点赞即刻成为未来所有相似问题的 prompt 成分。👎 无法驱动修正：没有「这条答案错了→定位到影响的示例→修改→重新生效」的引导闭环。此前安全梳理已把「👍 直入」登记为全链路最弱一环，但一直没有排期修复。

### P1-c 注入不可见、不可归因
示例命中写进 EvidenceCard 的只是「命中列表」；**答案到底采纳了哪条示例的 SQL、改动多少，没有任何归因记录**。答案出错想追责到示例层面，只能靠人肉比对。

### P2-a 无版本化无审计
示例的每次变更（谁/何时/改了什么）不留痕；一次误操作批量 seed 无法整体回滚。

### P2-b checkpoint 跨题状态污染（已有真实事故）
户变关系 trace 中「受控工作流已预解析主体实体为 dwd_cst_bus_be_accs_lfcyc_df（业扩表）」——上一题的状态错误地注入了本题契约，模型无条件信任写进「已知」。用户对线程里沉淀了什么状态**不可见也不可清**。

### P3-a 检索行为不可调
无单条权重、无场景作用域（某条示例只在某场景生效）、无置顶/冻结；hit_count 有累计但看不到「命中后的答案好评率」——不知道哪条示例在立功、哪条在闯祸。

### P3-b 自动禁用是否静默待查证
schema 漂移自动禁用是保护性设计，但若不产生管理员可见通知，就是「悄悄变了行为」——同样折损信任。

## 三、与自身安全模型的冲突定位

我们的注入防御原则是：**进入模型上下文的规则必须是审查过的**。技能/剧本/契约/AGENTS.md 全部满足；唯独示例库——由不可控的用户行为（点赞）自动生成、未经审核、直接拼进契约消息——是我们亲口登记过的半信任源。**它不是设计疏漏，是已知债务一直没还。**

## 四、可控性三权评估

| 权利 | 定义 | 现状评分 |
|---|---|---|
| 知情权 | 影响回答的因素可见可追溯 | ★★☆☆☆ 命中列表有、归因无 |
| 修改权 | 错了能改、能指导 | ★☆☆☆☆ 无编辑端点、无修正闭环 |
| 否决权 | 随时能让任何一条/一类机制闭嘴 | ★★★☆☆ 单条启停/删除有；缺全局总闸与分来源开关 |

## 五、治理方案（批11：知识库受控化）

### A. 补齐修改权（紧急，0.5d）
- `PATCH /qa-examples/{id}`：编辑问题文本/SQL/route_type，保存即重新 embedding 并同步 Qdrant；
- 验证 DELETE 同步清理 Qdrant point（防幽灵向量复活）；
- 管理页行内编辑 UI。

### B. 审核制（核心，1d）
- 👍 不再直入：入库为 `status=pending_review`，管理页审核队列批准后方参与检索；
- 👎 关联修正流程：点踩时可定位本次命中的示例 → 一键带入旧 SQL 进入编辑器 → 修改保存即重嵌入（走 A 的端点）→ 原示例标记 superseded；
- golden 来源豁免审核（本身即人工产物）。

### C. 知情权落地（0.5d）
- 治理事件新增 `example_injected`：每次检索注入记录命中的 example_ids+分数，与 run 关联；
- EvidenceCard 展开项：「本答案参考示例 #N（相似度 0.xx）」，点开可见该示例 SQL 与本题实际 SQL 的对照。

### D. 否决权补全（0.5d）
- 总闸 `TUPU_EXAMPLES_ENABLED`（关=generic 提问不再注入任何示例，纯靠剧本+模板+模型能力）；
- 分来源开关：golden/user_confirmed/manual 各自独立启停；
- **纯确定性模式**（演示/审计用）：总闸关闭+仅场景路由——牺牲泛化换取 100% 可解释，给「非常不放心」的时刻一个一键安心的位置。

### E. 版本化与看板（二期）
- 示例变更 append 日志（谁/何时/diff）；快照导出/导入即伪回滚；
- 看板：每条示例的 命中次数×命中后好评率×差评率 四联指标——让「哪条在立功/闯祸」一眼可见；
- 漂移自动禁用产生管理员通知（补静默缺口）。

### F. checkpoint 可视可控（0.5d）
- 会话头部显示当前沿用的 last_skill/预解析实体（带来源标注「来自上轮」）；
- 「重置本题上下文」按钮：清 last_skill 后重新路由（修预解析错挂的现场手段）。

## 六、取舍提醒（不因噎废食）

示例库存在的理由依然成立：它是措辞敏感问题的解药（「总数」稳「数量」挂的年代就是没有它），也是直通管道 L0 的燃料来源——拆掉它等于退回「每题从零构造 SQL」和「直通永远没得开」。**正确方向不是拆除，是把「自动积累」改造为「受控运营」：默认收紧（审核制）、全程可见（注入审计）、随时可关（总闸+确定性模式）。**

治理后的理想姿态：示例库里每一条例外都知道自己为什么在（来源+审核记录）、干了什么（命中审计）、干得好不好（四联指标）、随时可以闭嘴（启停/总闸）。
