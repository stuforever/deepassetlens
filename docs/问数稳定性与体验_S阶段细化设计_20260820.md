### 1.2 设计错误与实施修正（两处，均已被实施窗口正确解决）

① **SummarizationToolMiddleware 误判**：融合设计把它当作自动摘要的公开替代品--源码核实它是「`compact_conversation` 手动压缩工具件，永不自动压缩」。实施采用更优方案：**子类 `_TupuSummarizationMiddleware(SummarizationMiddleware)` 显式装配 + HarnessProfile `excluded_middleware={"SummarizationMiddleware"}` 按名精确丢弃框架自动件**（子类名≠基类名故存活），测试断言三件（自动件丢弃/显式件存活/工具件存活）。该方案已固化为 test_m1_robustness 用例。

② **Rubric 事件通道**：设计假设 `astream_events` 可观测评估事件--实施发现 rubric 事件走 `runtime.stream_writer`（stream_mode="custom"），astream_events 收不到；改为 **`on_evaluation` 回调 + contextvar 桥**到当前请求的 run_event_sink/契约（tupu_deepagent.py:635-644）。这是设计遗漏的框架细节，实施修正正确。

### 1.3 评估暴露的三个新问题（S 阶段主攻方向）

最新基线（eval_golden_20260820_101447：repeat=3，首轮 100% / 稳定 80%，rubric=on）：

| # | 问题 | 证据 |
|---|---|---|
| P-A | **聚合退化不稳定**：唯一不稳定用例「各电压等级的用电客户分布是怎样的」run2 返回**全表明细**（7 列无 GROUP BY），run3 **零执行**（无 sql_result 事件）。该问题本身在金标集，孪生示例必然精确命中注入，提示词层（AGENTS.md 分布纪律 + 示例注入 + rubric）仍挡不住 | unstable[0] 三 run 记录 |
| P-B | **零执行成功歧义**：run3 reason="ok" 但 pass=false、digest=null、confidence=null--「无数据/失败/未执行」混在一个 reason 里，流异常/超时未分类 | unstable[0].runs[2] |
| P-C | **观测度量失效**：三个 run 的 tool_count 均=0，但 run1/run2 明明有真实查询结果--eval 脚本的 tool_start 事件采集与实际事件名/过滤不匹配；examples.injected 命中数也未采集 | 全部 runs tool_count=0 |

**核心判断**：措辞敏感已通过 3 条计数变体金标驯化（首轮 100%），当前不稳的是**聚合意图的结构性保障缺失**--prompt 三重锚定（纪律/示例/rubric）对「分布」类问题的 GROUP BY 行为约束不足，需要结果层硬校验兜底。

## 二、S1 稳定性攻坚（~2 天，最高优先）

### S1a 聚合意图结构化保障（三层防线，治 P-A）

**L1 路由层意图标记**（skill_router.py）：

```python
_AGGREGATE_TRIGGERS = ("分布", "占比", "构成", "比例", "各" + 任一维度词 + "的")
# _route_generic 命中触发词时：
contract.aggregate_intent = {"dimension_hint": "voltage_name",   # 可选：命中已知维度列名时给提示
                             "required_shape": "GROUP BY 维度列 + COUNT/SUM"}
```

契约 SystemMessage 追加一行受控指令：「本问题要求聚合分布视图（GROUP BY 维度列），禁止返回明细全表」。

**L2 结果层聚合校验**（治 run2 形态：全表退化为明细）：

落点：G4 verification 扩展（引擎出口 + skill_policy postcheck 消费）：

```
判定规则（问题带 aggregate_intent 时）：
  结果列数 == 目标表全列数 且 row_count >= 全表行数*0.9 且 SQL 不含 GROUP BY
  -> verification.warnings += "聚合类问题返回了明细全表"
  -> correction.attempt 注入指引：「请改为 SELECT 维度列, COUNT(*) FROM ... GROUP BY 维度列」
```

关键：**该判定走既有纠错闭环**（上限 2 次、超限失败卡），不新增机制。

**L3 rubric 文案增补**（query_contract.py GENERIC_RUBRIC 加第 5 条）：

```
5. 分布/统计类问题的结果必须是聚合视图（GROUP BY 维度列），不得返回明细全表。
```

**验证口径**：金标问题 1 单独 repeat=5 全过（当前 1/3）。

### S1b 零执行与流异常分类（治 P-B）

- eval_golden.py reason 细分：`no_sql_result` / `stream_timeout` / `stream_error` / `rubric_blocked`（有回答但无 sql_result 且 rubric 未 satisfied）四类独立 reason，替换现在的笼统 "ok"；
- 流式层兜底（data_intelligence_stream 最终阶段）：会话零 execute 工具调用但最终回答含数字 -> SSE 附 `evidence.missing_data_support: true`，前端 EvidenceCard 置信度直接判「低」并黄条提示「本回答未执行数据查询」；
- eval 脚本对超时/断流设独立重试计数（当前按失败计，混入稳定性分母）。

### S1c 观测度量修复（治 P-C）

- eval_golden.py 事件采集修正：对齐 astream_events v2 实际事件名（on_tool_start 等）与 SSE 事件名映射表，tool_count 修复后应 >0；
- 新增采集：每 run 记录 `examples_injected`（条数+最高相似度）与 `corrections`（次数）--S4 调优的数据基础；
- 回归验证：跑一次 eval，全部 run 的 tool_count > 0。

### S1d 方差与门禁口径

- 模型连接温度显式固化（LLMConnectionConfig 加 temperature 字段或连接参数透传，缺省 0.1--问数场景要稳不要浪）；
- 发布清单门禁改双口径：**首轮 ≥95% 且 repeat=3 稳定 ≥85%**（当前仅首轮口径；数据面 5 条时 100% 首轮含运气成分，扩容后按新口径）。

## 三、S2 金标集扩容（5 -> 40+，~2 天）

### 3.1 分层矩阵（设计即验收清单）

| 层 | 条数 | 覆盖 | 例 |
|---|---|---|---|
| 聚合分布 | 8 | 各维度列分布（电压/重要性/客户类别）、占比形态 | 「各电压等级的客户分布」「按重要性等级统计占比」 |
| 计数 | 6 | 总数/去重/条件计数 | 「某电压等级下有多少客户」 |
| 明细 | 6 | 清单/TopN/排序 | 「容量最大的前 10 个客户」 |
| 过滤 | 8 | 单条件/组合/时间/模糊 | 「重要性等级为一级且容量>630 的客户」 |
| 多表 JOIN | 4 | 客户×配变关联 | 「各配变下挂的客户数」 |
| 澄清 | 4 | 歧义应触发澄清而非乱查 | 「客户情况」（应问哪个维度） |
| 措辞变体组 | 6 组×3 问法 | 专测措辞敏感 | 计数/分布/TopN 各两组变体 |

- 生成方式：手写为主（口径准），EngineQueryLog 历史成功查询辅助挖掘；
- 全量以 `example_type=golden` 同步灌入示例库（命中即结构锚定）；
- 扩容后目标基线：首轮 ≥95%、稳定 ≥85%；不足则逐失败用例归因（eval 明细已支持）。

### 3.2 澄清层特别设计

4 条澄清金标的判定不是比对 digest，而是「触发了澄清事件/卡片」--eval_golden.py 加 `expect: "clarify"` 分支（比对 SSE 出现澄清类事件即 pass）。

## 四、S3 M5 补完（~2.5 天，组件级规格）

### S4a G8 自动图表（零依赖轻实现）

- **入口**：SqlResultTable 工具栏 `Segmented`「表格 | 图表」，仅形态可识别时渲染（不可识别不显示切换，避免空态）；
- **形态检测**（前端纯函数 `detectChartShape(columns, rows)`）：
  - 两列（维度 + 数值）-> 横向占比条 TopN=10；
  - 首列可解析为时间 -> 迷你柱状；
  - 其余 -> null（不切换）；
- **占比条规格**：行高 22px、行距 6px；条体高 10px 圆角 5px，宽度=值/最大值百分比，色取 chartPalette 顺序循环；左侧维度名 12px textSecondary（ellipsis 8 字符），右侧数值 `dal-num` 12px textPrimary；
- **迷你柱状规格**：容器高 120px，柱宽自适应（min 8px），柱色 chartPalette[0]，hover antd Tooltip（维度+值）；基线 1px 分割线 colorBorderSecondary；
- 全部 inline-style + tokens，零新依赖，遵循《前端组件级规格》图标/字号/动效铁律。

### S4b G9 追问改写

- **触发条件**（free_plan 入口，纯规则不打模型）：thread 有历史 &&（问题 <12 字 || 含指代词「那/它/上述/该/也/再」）；
- **改写**：单轮 LLM 调用（会话模型，temperature 用 S1d 固化值）：「结合会话上文与上一轮口径（实体/时间/过滤），将追问改写为独立完整问题，只输出改写结果」；
- **透明性**：SSE 输出 `followup.rewrite` 事件，前端最终答案上方渲染「理解为：xxx」12px textTertiary 小字（可点击展开原文对照）；
- **兜底**：改写 3s 超时或异常 -> 静默用原问题（不阻塞主链路）；
- **边界**：scenario 模式不改写（问题结构化强）；改写结果不进示例库（防污染）。

## 八、不做清单（S 阶段边界）

| 不做 | 理由 |
|---|---|
| 微调/换更大模型治方差 | 40 条金标 + 三层结构保障 + 温度固化先行；数据量不支持微调结论 |
| 重型图表库 | 占比条/迷你柱状覆盖问数 90% 图表诉求 |
| 追问改写进示例库 | 改写是会话态，入库污染口径 |
| 金标准确率前端趋势页 | eval JSON 存档已够（沿用 M4 决策） |
| S1a 用「新增分布场景剧本」解决 | 分布是 generic 高频形态，做成场景剧本会把自由问答碎片化；留在 generic + 结构保障更符合平台设计 |
| tool_count 之外的深度 tracing | LangSmith 等观测平台接入超出单机演示场景 |
