# 缺陷分析：户变关系 UNION 双重校验冲突（P0 级·场景结构性不可执行）

> 2026-08-20 · 设计窗口产出（只读分析 + 修复方向，不动代码）
> 现场：用户执行「所有用电户与配变户变关系」，失败卡在 execute_doris_sql，日志见会话记录（7 步定位、最终「SQL安全校验未通过: 不支持的语句类型: Union」）。

---

## 一、直接回答：卡在哪一步

**卡在 #4 execute_doris_sql 的 handler 内「安全 SQL 校验」（secure_query_executor.validate_sql）**——不是路由、不是读剧本、不是 batch 源模式、也不是模板守卫（前两步结构漂移是模型写错，被正确拦截）。

前 3 步全部成功：
1. read_file SKILL.md ✓（25ms）
2. read_file step1 模板 ✓（20ms）
3. batch_entity_source_mode ✓（1.9s，7 表，推荐 execute_doris_sql）

#4 起开始撞墙，且日志里出现了**两种不同校验层的拒绝语**：

| 次序 | 拒绝语 | 来源层 | 判定 |
|---|---|---|---|
| 尝试1 | 「同表但结构漂移」 | template_guard（SkillPolicy 预检） | 模型删了发电户 UNION 段，指纹不一致 → **正确拦截** |
| 尝试2 | 「同表但结构漂移」 | template_guard | 模型加了 `pg_tupu.public.` 前缀，表名 token 变 → **正确拦截** |
| 尝试3（#4） | 「SQL安全校验未通过: 不支持的语句类型: Union」 | secure_query_executor（handler 内） | **模板原样裸表名 → 模板守卫已放行，却被安全校验器拒绝** |

第三次模型已把 SQL 写得与模板完全一致（结构指纹通过，template_guard 放行），**却在执行层的安全校验被「不支持 Union」打回**。随后 5 分钟硬超时（data_intelligence_stream.py:278 `_task_deadline = time+300`）终止循环，输出「任务超过5分钟被终止」。

---

## 二、根因：两个校验层对同一段 SQL 结论相反（硬阻塞）

### 证据链

1. **模板自身含 UNION ALL**：`step1_household_transformer.sql` 根节点 = `WITH 台区配变 AS (...) SELECT 用电户段 UNION ALL SELECT 发电户段 ORDER BY ...`。

2. **模板守卫（预检层）明确放行**：
   - template_guard.py:330-331「UNION 处理：模板自身合法使用 UNION ALL（如户变关系模板合并用电户/发电户两段），因此不对 UNION 一刀切拒绝；防绕过靠表集合校验」
   - template_guard.py:186-187「UNION ALL 合法（模板自身用于合并两段查询），要求两侧都是 SELECT」
   - 结果：`template.bound` 通过。

3. **执行层安全校验（handler 内）一刀切拒绝**：
   - secure_query_executor.py:24 `_READONLY_STMT_TYPES = frozenset({"Select"})`——**只有根节点类型为 Select 的 SQL 能过**
   - :80-84：`stmt_type = type(tree).__name__` → 模板根节点 sqlglot 解析为 `Union` → 不在只读集 → 不在禁用集 → 落入「不支持的语句类型: Union」
   - **四个执行工具全调同一个 validate_sql**：execute_sql(:200)、execute_api_sql(:446)、execute_entity_api(:537)、execute_doris_sql(:597)——**四条路径全部拒 UNION**。

### 结论

**distribution-overload 第 1 步剧本在结构上永远无法执行成功**。模板守卫认为「模板 UNION 合法」，执行层认为「UNION 非法」，同一段 SQL 在两个校验层上判定相反，且执行层是最后一道闸——**结构性死锁**。

### 为什么之前没暴露

- P0 冒烟基准「统计用电客户总数」是 `SELECT COUNT(*) ...`（根节点 Select，无 WITH/UNION），能过；
- 金标 5 条里没有含 UNION 的模板用例（计数/明细/分布，最复杂的是 GROUP BY）；
- 该缺陷只在「含 UNION 的场景模板走执行」时触发——首个含 UNION 的模板就是户变关系。

## 三、次生缺陷（加剧卡死）

### 缺陷 2：SKILL.md 降级规则与 scenario_strict 直接矛盾

- SKILL.md :209「用户只问用电户/发电户 -> 只跑对应 UNION 段」；
- scenario_strict 要求「结构指纹与模板**完全一致**（含 UNION 两段）」。

模型第 1 次按 :209 只跑用电户段 → 漂移拒绝；白白消耗 1 次纠错预算，还让模型陷入「到底要全模板还是只一段」的困惑（从日志 #4 前两轮决策可见模型反复试错）。

### 缺陷 3：超时吞掉纠错机会 + 错误信息无引导

- 5 分钟硬超时（:278）在纠错循环耗尽前把整个循环杀了，最终答案只是回显原始错误文本「SQL安全校验未通过: 不支持的语句类型: Union」，无任何「已尝试 3 次/卡在安全校验」的过程归因；
- 该错误未被错误分类学归类（engine_errors 六类里没有「安全校验拒绝」），模型只能当普通执行错误反复重试。

---

## 四、修复方向（设计级，按优先级）

### 修复 1（根治）：validate_sql 放行合法 UNION 根节点

与 template_guard.py:186-187 同款处理，对齐两层语义：

```
在只读语句校验处：
  if stmt_type == "Union"（或含 exp.Union 根）:
      递归校验每个分支均为只读 SELECT/WITH（禁 DML/DDL/函数副作用）
      表集合由调用方模板守卫已兜底（模板内表 ⊆ 模板表集合）
      -> 放行，进入表集合/强制 LIMIT 流程
```

- 强制 LIMIT 注意点：`_ensure_limit` 对 Union 根要下推到最外层查询或跳过（模板已含 ORDER BY；户变关系是全量关系查询，**不应强制 LIMIT**——可对模板绑定场景放行无 LIMIT）；
- **安全不降级**：放行仅限「全部子分支都是只读 SELECT」，DML/DDL/UNION 引入模板外表仍被表集合校验拦截（template_guard 已有）。

### 修复 2：消除 SKILL.md 指令矛盾

- 明确语义：**scenario_strict 下骨架必须与模板完全一致（含 UNION 两段）**；「只跑用电户段」的降级规则改为 **WHERE 过滤/动态段 层面**（如 `AND inst_usage_cls='01'` 仍保留两段骨架），或为「仅用电户」提供**第二合法模板**（模板守卫可声明多模板，任一遍历命中即放行）;
- 推荐后者：新增 `step1_household_transformer_elec_only.sql` 单段模板，与全量模板并列，模型按用户意图选。

### 修复 3：错误分类 + 超时策略

- engine_errors 新增第 7 类 `SECURITY_VALIDATION`（安全校验拒绝），correction.attempt 指引改为「该 SQL 未过安全校验：{reason}。请检查语句类型（仅 SELECT/WITH/合法模板 UNION）」；
- 对「模板原样仍被安全校验拒」的情形（本次 #4），**直接失败卡**而不是让模型反复重试——语义上这是「模板与执行层不匹配」的工程缺陷，不是模型能自愈的；
- 5 分钟硬超时保留，但超时前的最终错误应带归因（已尝试 N 次/最后失败原因），不再裸回显。

### 修复 4（验收护栏）：金标集补 UNION 模板用例

- 金标库加入「户变关系（用电户+发电户全量）」用例（expected_digest 比 row_count + 首行）；
- eval_golden 跑通即证明模板链路（模板守卫放行 → 安全校验放行 → 执行）全绿；
- 冒烟基准补充一条含 UNION 模板的直查（加速器直查不受该链影响，需走 execute 工具链路才暴露）。

## 五、影响面评估

| 项 | 影响 |
|---|---|
| distribution-overload 第 1 步（户变关系） | **当前 100% 失败**（四条执行路径全拒 UNION） |
| 第 2/3 步（重过载/负载率） | 需查各自模板是否含 UNION（step2 大概率是 96 点功率聚合，需逐一核对）；**建议全场景模板 UNION 扫描** |
| 其余场景模板 | 需扫描全部 SKILL.md 模板是否含 UNION/WITH 根节点（`WITH ... SELECT` 若 sqlglot 解析为 With 根同样会拒） |
| generic 路径 | 不受影响（generic 无模板，模型不会写 UNION，且白名单路径相同 validate_sql） |

**建议先做一次「全模板 UNION/WITH 扫描」**（读全部 SKILL.md templates，sqlglot 解析根节点类型），把受影响面一次性摸清，再按修复 1 统一放行。

---

## 六、一句话结论

**卡在 execute_doris_sql 的 handler 内安全 SQL 校验**：模板守卫放行模板自身 UNION ALL，执行层 validate_sql（只认根节点 Select）却拒 Union——两个校验层对同一段模板 SQL 结论相反，导致户变关系场景第 1 步结构性不可执行；SKILL.md 降级规则与 scenario_strict 的矛盾又让模型前两次尝试无效消耗，最终被 5 分钟硬超时终止。
