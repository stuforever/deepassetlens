# 设计初衷还原：为什么用 DeepAgents，用了哪些能力（2026-09-06）

> 还原依据：五份决策文档 + git 历史 + 主文档状态表，全部锚点见附录。
> 本文回答两个问题：**①当初为什么选 deepagents ②用了它的哪些能力**（含后来的变化）。
> 定位：给未来的自己、新会话、新成员看的设计初衷存档——读完应能回答「这个平台和框架的边界在哪、当初怎么定的、现在到哪了」。

## 第一幕·选型初衷：我们买的不是引擎，是一套挂载点

### 1.1 平台的第一性问题

这个平台要做的是「受控问数」：用户问数据问题 → 平台按剧本生成 SQL → 查知识图谱/数据库 → 给出**可信**的答案。关键约束是**受控**——哪些表能查、SQL 结构允不允许、输出什么格式，都不能由大模型自由发挥。这是企业数据场景的底线。

所以平台的核心资产从第一天起就是三样**任何框架里都没有的东西**：

- **路由**（skill_router）：问题分给哪个剧本；
- **契约**（QueryContract）：这一问允许用哪些工具、哪些模板、什么口径；
- **守卫**（五类闸门）：SQL 结构、模板指纹、引擎、能力、输出的海关。

### 1.2 为什么 Agent 循环不自建、也不全托

两边都有坑：

- **自建 Agent 循环** = 重新发明一层 langgraph：多轮 ReAct 循环、流式事件、会话断点恢复、长会话摘要……全是通用轮子，自建又贵又容易踩深坑（流式中断、悬空工具调用、状态恢复，每一个都是事故源）；
- **全盘交给框架** = 怕失控：框架的默认行为可能绕过我们的守卫——契约就成了摆设。

### 1.3 deepagents 恰好卡在中间，当初看中四点

1. **AgentMiddleware 协议（最关键）**：我们自研的守卫可以按标准协议写成中间件，**插进 Agent 循环的主干道**——模型每次思考前、每次工具调用前后都能拦截。海关挂在主干道上，不是绕道检查。后来全链路对照把它总结为五张插件面之首；
2. **循环本体白送**：ReAct 多轮、astream_events 流式（SSE 数据源）、checkpointer 断点记忆、长会话摘要，全是成熟件；
3. **Skills 渐进披露**：SKILL.md 剧本当文件系统挂载，技能按需读取——天然契合我们的「剧本 + SQL 模板」模式；
4. **框架哲学克制**：能力全做成可选参数（18 个参数起步只用 8 个），用多少拿多少，不强加默认行为——这让我们「用一半、锁一半」成为可能。

事实锚点：deepagents 从仓库诞生（2026-08-06 首次提交）就是骨架，不是中途换的框架；全链路对照实测——九阶段链路里，六段业务（预处理/路由/契约/分流/守卫/交付）框架**全无对应、必须自建**，只有模型循环一段是纯框架。

### 1.4 一句话初衷

出自《图谱问数能力融合详细设计》的融合原则，三句话：

> **框架原生件优先于自研；红线不动；一切新能力过受控平台既有闸门。**

翻译成大白话：**框架管通用的循环，我们管业务的锁。**

## 第二幕·深度使用与红线：用了什么，坚决不用什么

### 2.1 深度使用清单（抽掉就瘫），分三组

**循环本体组**：
- `create_deep_agent` 装配入口（现为十步装配，见第三幕终态）；
- ReAct 多轮循环 + `astream_events v2` 流式事件（前端 SSE 的唯一数据源）；
- `AsyncSqliteSaver` checkpointer（跨题会话恢复）。

**挂载与数据组**：
- **AgentMiddleware 协议——自研海关的挂载面，全仓关键复用**（SkillPolicy 契约海关等自研件就是按这个协议插进框架循环的标准插件，增删=改装配列表一行）；
- SkillsMiddleware（SKILL.md 剧本渐进披露）；
- FilesystemMiddleware（read_file/ls 读模板与参考文件）；
- MemoryMiddleware（AGENTS.md 常驻纪律）；
- state_schema（契约/rubric/last_skill 的状态注入通道）；
- Backend 挂载：13-Y 起为官方推荐的 StoreBackend（/skills/ 与 /memory/ 路由）。

**用但定制组**：
- 摘要件：monkey-patch → 子类 → 13-AB 回退**官方工厂同名替换**（技术债清零，见第三幕）；
- 自评件：13-AB 后技能自评（skill_prompt）为代码基准，RubricMiddleware 为可选切换路径；
- HarnessProfile：排除写文件五工具（write_file/edit_file/grep/glob/execute），13-W 起反转为白名单勾选模式（MCP 18 件 + task = 19 件勾选域）。

### 2.2 有意不用清单——三类归因，每条登记在案

1. **主动排除（用了反而危险）**：
   - subagents/async_subagents（task 委派子代理）——逃逸面，会绕过契约闸门的确定性；
   - local_shell / sandbox 后端——问数零代码执行需求，shell = 任意命令面；
   - response_format——当时判定「会禁用工具调用，与 ReAct 根本冲突」。
2. **生态不适配（别家生态专属）**：
   - _prompt_caching / cache 参数——Anthropic/Bedrock 专属，我们走 OpenAI 兼容协议（缓存靠服务端隐式前缀缓存）；
   - langsmith ContextHub 云端后端——外接 SaaS 过重。
3. **替代更优（自己有更好的）**：
   - store 参数→Qdrant 示例库（无向量索引的 KV 替不了语义检索）；
   - interrupt_on→自研条件 HITL（表达不了「TABLE_MISSING 才审」这种动态触发）。

黑能力清单的原话值得原样传下去：**「未使用的部分不是损失，恰恰是边界清晰的表现」**。

## 第三幕·渐进翻案：红线不是永远的红线，是「没护栏前的红线」

13 系把当初的「不用」逐条改造成「带护栏启用」。**每一条翻案都是先造护栏、再点火、全部登记**：

| 当初的判断 | 翻案 | 护栏 |
|---|---|---|
| response_format 禁用（与 ReAct 冲突） | 13-F：FinalAnswer/CountAnswer 结构化终答 | POC 四点验证 → GLM 不兼容自动降级 → scrub 兜底 |
| store 不用（Qdrant 替代） | 13-F：AsyncSqliteStore 用户偏好记忆层；13-Y：StoreBackend 官方服务器模式 | 写入全审核制 + TUPU_USER_MEMORY_ENABLED 总闸；files_hash 保新鲜度 |
| task 委派绝对禁（契约红线禁 task） | 13-Z：distribution-overload 剧本激活（路线A） | 四护栏：SKILL.md 显式声明 allow_subagents + 白名单窄集 entity_locator + 只读委派 + 能力开关中心可视；未声明剧本默认拒绝（fail-closed） |
| 摘要 monkey-patch 属技术债 | 13-AB：官方工厂 create_summarization_middleware 同名替换 | 触发条件登记（超限重试日志出现→补 model profile） |
| PatchToolCalls「仍未装配」 | 认知修正：框架自动件恒装（无需手动装配） | —— |

**原则从头到尾没变**：不是放水，是受控启用。翻案的前置条件永远是护栏先于点火——总闸/白名单/契约声明/管理页可见，四件套缺一不点。

### 终态：十步装配 + 12-Tab 能力开关中心（13-W）

- 框架每个能力都是**可视可关的插件**：主 Tabs 12 区（manifest 总览 + 守卫独立区 + 步1-10），CAP_STEP_MAP 把每个能力映射到装配步骤；
- 白名单反转：管理页勾选域（19 件）→ 装配期换算 excluded，锁定三件（read_file/ls/task）运行时兜底；
- 改任何开关 → 缓存键 `{conn}#g{守卫版本}#c{能力版本}#f{文件指纹}` 变 → Agent 自动重装配生效（13-W 还修了缓存键的 sum(version) 缺陷——PATCH 非最大行时配置曾静默失效）；
- 最近一次收口：批15（2026-09-06）把 13-Y「改剧本=下次请求重装配」的承诺在文本缓存侧补全（SKILL.md 指纹键缓存）。

**设计初衷的最终形态：框架能力全部受控化——深度使用、定制、带护栏启用、有据排除，四选一，没有「糊里糊涂在用」的。**

## 尾声·初衷三句话

1. **deepagents 是骨架不是灵魂**：灵魂是契约/守卫/路由（必须自建，框架没有），骨架是循环/挂载/记忆（框架成熟件，白送不重复造）；
2. **红线是动态的**：护栏先行、逐条翻案、全部登记——「不用」永远带着理由和再评估的条件；
3. **终态是受控化**：每个框架能力都能回答「用不用、怎么用、谁批准、在哪关」。
