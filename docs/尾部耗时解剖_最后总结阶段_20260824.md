# 尾部耗时解剖：「最后总结」阶段的每一秒花在哪

> 2026-08-24 · 设计窗口产出
> 实测锚点（「查询项目数量」Agent 路径）：sql_result 49.2s → 首 token 52.2s → 答案流完 ~60s → done 67.5s（grader 报 12.2s）。
> 用户视角的「最后总结」= 从数据到手到界面停止转圈，约 **23 秒**。逐段拆解如下。

---

## 一、总账：23 秒的四段构成

```
49.2s          52.2s            ~60s           67.5s
  │── T1 ──│─── T2 ───│──── T4 ────│T5│
  数据到手    启动开销     答案生成       自评(rubric)   收尾
  ~3s        ~8s          ~12s         <0.5s
```

| 段 | 发生了什么 | 耗时 | 占比 |
|---|---|---|---|
| **T1 启动开销（TTFT）** | R5 轮发起：全量上下文重发（系统提示+契约+前4轮轨迹+工具结果）→ 远端预填充 → 首个 token 回来 | ~3s | 13% |
| **T2 答案生成（decode）** | 807 字符 ≈ 500-550 token，按远端解码速度 ~65 token/s 逐字生成 | ~8s | 35% |
| **T4 自评（rubric）** | 第二次完整 LLM 往返：整条轨迹压扁+nonce 围栏+交叉核对+结构化裁决（详见《自评耗时解剖》） | ~12s | 52% |
| **T5 收尾** | 输出契约校验/scrub、evidence 聚合、推荐提取、三本账写入——全部代码级操作 | <0.5s | 2% |

## 二、逐段深挖：为什么是这么多

### T1 启动 ~3s：上下文体积税
- R5 请求要携带全部历史（append-only 结构使服务端前缀缓存**可以**命中 R1-R4 已算过的部分），但新增后缀（R4 工具结果）和缓存命中与否仍决定 TTFT；
- 3s 在「大上下文+远端 API」下属正常水平；**批5-C4 的命中率观测落地前，无法确认缓存是否真在生效**——这是当前最大的观测盲区。

### T2 生成 ~8s：token 量 × 解码速度
- 解码速度（~65 tok/s）是模型/供应商属性，代码优化不了；
- **能优化的是 token 量**：A-E 四段式（结论/关键发现/风险/建议+口径披露）是输出契约强制的完整结构——对一道 COUNT 题来说，「共 3 条」的答案配了 800 字的解释框架，其中大量是模板化套话；
- 反向事实：明细禁止重复贴（前端表格承载）已经在省 token，否则更慢。

### T4 自评 ~12s：第二次完整往返
- 已有专文解剖（《自评耗时解剖_rubric过程分析》）：整轨迹压扁+nonce 围栏导致零缓存复用+交叉核对生成；
- 讽刺点重申：本题是干净 COUNT 题，这 12s 复核的是模板+闸门已结构性保证过的事。

### T5 收尾 <0.5s：不是瓶颈，永远不是
- 全部是毫秒级代码操作；有人怀疑「收尾慢」时可以用本节直接排除。

## 三、与整体延迟的关系：尾巴在 180s 里占多少、在快路径里占多少

| 场景 | 尾部（T1-T5） | 前部（路由+工具轮） | 尾部占比 |
|---|---|---|---|
| 冷题 ~180s | ~23s | ~157s（4 轮工具决策） | 13% |
| 本例 ~72s | ~23s | ~49s（3 轮） | 32% |
| L1 锚定题 ~15s（目标） | ~10s（无自评+精简格式） | ~5s（1 轮） | **67%** |
| L0 直通 <4s | ~2s（模板渲染，无 LLM） | ~2s | 50% |

**关键洞察：越快的路径，尾部占比越高。** 前部轮次被压缩后，T2 生成和 T4 自评成为主要矛盾——这就是为什么批13-A/B/C（单帧交付+自评后置+金标直通）全部火力集中在尾部。

## 四、治理手段对四段的精确作用（收益重估）

| 手段 | 作用于 | 效果 |
|---|---|---|
| 批13-C 金标直通 | 整个尾部 | 锚定题尾部整体消失（<4s 全程） |
| 批13-B'-1 规则跳过 | T4 | 干净统计题 -12s |
| 批13-B'-2 异步化 | T4 感知 | 不缩短真实耗时，但用户零感知（done 先行） |
| **分型精简格式（本篇新提出）** | T2 | COUNT 类答案只出「一句结论+口径注」（~150 字），生成 8s→2-3s；response_format 落地后定义 CountAnswer 子 schema 自然实现 |
| 批13-K grader 轻模型 | T4 | 仍需评分的题 -50~70% |
| 批13-I 缓存观测 | T1 | 先看见命中率，再谈优化；保住 R5 的低 TTFT |
| response_format 结构化 | T2/T4 中性偏正 | POC 实测；结构化解码可能略增 token，但省去 scrub 重试 |

## 五、结论

> 「最后总结慢」由两笔性质不同的账构成：**T2 生成 8s 是物理账**（token 量×解码速度，只能靠少写——分型精简格式和直通管道治它）；**T4 自评 12s 是架构账**（独立仪器复核=第二次完整往返，只能靠不评/后评/轻评——批13-B 三招治它）。T1/T5 合计不足 4s 且已有观测与兜底手段。按批13 排期执行后，尾部从 23s 压至：锚定题 0s（直通）、干净统计题 ~3s（跳评+精简）、复杂题 ~10s（异步自评不挡交付）。
