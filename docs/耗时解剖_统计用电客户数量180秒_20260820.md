# 180 秒全链路耗时解剖：「统计用电客户数量」为什么慢

> 2026-08-20 · 设计窗口产出（只读分析）
> 现象：执行约 180s；答案 markdown（## 结论/关键发现/后续建议）先以「日志」形态上屏，约 30s 后才在输出区出最终结果。
> 方法：逐段对照代码与运行配置（LLM 连接表实查），建立成本模型。

---

## 一、结论先行（三句话）

1. **180s = 约 5 轮 ReAct × 每轮 ~25s + rubric 自评 ~30s（+可能触发的答案重写一轮）**。慢的主因不是模型思考，而是「**轮次 × 单轮远程调用延迟**」：每轮都把全量上下文（基础提示 + AGENTS.md + 技能目录 + 契约消息 + 17 工具 schema + 逐轮增长的历史）重发给 DeepSeek-V4-Flash 远程 API，OpenAI 兼容端点**无 prompt 缓存**，每轮全价。
2. **「结果生成日志上屏」是当前设计行为**：答案 token 流被渲染进 ThinkStream 思维链面板（answer_draft 步骤项），不是输出区。
3. **「30s 后才到输出区」= rubric 评分把 final 事件压住了**：RubricMiddleware 的 after_agent 钩子在 agent 流结束前同步评分（一次全量 grader LLM 调用），final 事件只能等它跑完；若评分不满意还会**重写一轮答案**（再 25-40s）。

---

## 二、耗时分解（成本模型，基于代码结构）

路由定性：**generic 路径**。`sql-query` 技能**没有 triggers**（frontmatter 只有 name/description）——「统计用电客户**数量**」不命中任何场景触发词（对照：金标里的「统计用电客户**总数**」是 generic 基准锚点；场景触发词没有「数量」变体，这正是 eval 发现的**措辞敏感**问题再现）。generic ⇒ rubric 激活（GENERIC_RUBRIC，data_intelligence_stream.py:264-267）。

| 阶段 | 内容 | 估计耗时 | 代码依据 |
|---|---|---|---|
| 会话准备 | 锁 + checkpoint 读 + agent 单例 | 0.3-1s | stream :100-110 |
| 追问判断 | 规则判定（18字无指代词，不触发改写 LLM） | 0.3s | :112-147 |
| 路由 | 正则匹配，无场景命中 → generic | <10ms | skill_router |
| 契约+示例注入 | embedding HTTP + Qdrant 检索 | 0.5-3s | data_intelligence.py:111-121 |
| R1 模型轮 | 读技能指引（sql-query）或直判 | **~20-30s** LLM + read_file ms | on_chat_model_stream |
| R2 模型轮 | search_entities 定位用电客户 | **~20-30s** LLM + 工具 ~0.2s | |
| R3 模型轮 | batch_entity_source_mode | **~20-30s** LLM + 工具 ~1.9s | |
| R4 模型轮 | execute_sql COUNT(*) | **~20-30s** LLM + 执行 <0.1s（3 行小表） | |
| R5 答案生成 | 300-500 token 流式输出 | **~25-40s** | answer_draft 流 |
| **rubric 评分** | grader 带全 transcript + rubric 的一次 LLM 调用（after_agent 同步） | **~20-40s** | rubric.py after_agent |
| （条件触发）答案重写 | 评分 needs_revision → jump_to model 重生成 | +25-40s | max_iterations=1 |
| 收尾 | final / recommend / evidence / done | ms | stream :882-1009 |

合计 ≈ 150-215s，与实测 180s 吻合。

**每轮为什么 ~25s**：单轮延迟 = TTFT（大系统提示 + 历史，远程 API）+ 生成时间。配置实查：DeepSeek-V4-Flash、temp=0.2、quick 模式（**无 thinking**，排除深度思考嫌疑）、timeout=360s。所以慢在「轮次多 × 每轮全量重发」，不在模型思考模式。

## 三、两个 UX 问题的机制根因

### 3.1 答案为什么以「日志」形态上屏

```
模型流 token → on_chat_model_stream → 分类器判为 answer_draft
→ SSE think_token{kind:answer_draft}（stream.py:338-346）
→ FreePlanChat :813-815：answer_draft 渲染为 ThinkStream 的 'answer' 步骤项
```

**答案流被设计性地渲染在思维链面板**（作为一个步骤条目），而定稿答案要等 `final` 事件（:882）才进输出区。用户看到的「结果生成日志」就是这个 ThinkStream 里的 answer 步骤——行为是设计内的，**但形态设计错了**。

### 3.2 为什么上屏后还要等 ~30s

```
答案流完（用户已看到全文）
→ agent 自然停止 → RubricMiddleware.after_agent 同步评分（grader LLM 调用，~20-40s）
→ 若 needs_revision：jump_to=model 注入修订消息 → 答案重新生成（又一轮 25-40s）
→ agent 流结束 → 才轮到最后 yield final（:882）→ 输出区更新
```

**final 事件被 rubric 评分（+可能的重写）压在 agent 流结束之后**——这就是那 30s 死等。

## 四、设计调整建议（按收益排序）

### P0-1 答案直流产出区（消灭「日志上屏」+ 消灭观感死等）
- answer_draft token **直接流进答案气泡**（输出区实时成型）；ThinkStream 只保留决策/工具步骤；
- `final` 仅做全文校准（防丢字，已有机制），不再承担「首次展示」；
- rubric 事件（:974）到达后**异步更新置信度徽标**；若触发重写，气泡内显「校验修订中」并续流，而不是等 30s 后整体替换。
- 改动面：FreePlanChat 事件路由（answer_draft 的目的地从 ThinkStream 改为答案区）+ 修订态样式。零后端改动（事件都在）。

### P0-2 rubric 分档启用（消灭每问 30s 税）
当前**每个 generic 问题都交 grader**，这是对所有问题统一征税。分档：
- **低风险直通**（跳过 grader）：单表聚合 +（模板锚定或高相似示例命中）+ verification 无告警 + corrections=0——「统计用电客户数量」正是这类，确定性已有模板守卫/引擎锁定保障，自评边际价值≈0；
- **高风险才评**：多表 JOIN / corrections>0 / verification 有 warning / 示例无命中；
- 判定逻辑放契约构造期（`_build_contract_system_message` 处给 `contract.rubric` 置 None 即天然关闭——RubricMiddleware 无 rubric 零开销直通，机制已备好，只需一个分档函数）。

### P1-3 减轮次（每省一轮 = 省 ~25s）
- **示例直通**：question_norm 高相似命中（≥0.9）时，把已验证 SQL 作为「首选计划」注入契约——模型直接 execute + 作答，**5 轮 → 2 轮**。「统计用电客户数量」与金标「统计用电客户总数」norm 后几乎同题，本应直通（这也是 G1 示例库设计里没吃到满的红利）；
- **实体预解析注入**：路由期用语义检索把候选实体（dim_cst_elec_cons_cust）直接写进契约上下文，省 search_entities 轮；
- **指引预载**：generic 判为 SQL 类问题时，契约消息直接内嵌 sql-query 的对应写法段（聚合类就嵌 COUNT/GROUP BY 段），省 read_file 轮。

### P1-4 聚合统计场景化（对照证据：场景路径快一个量级）
早前测试表：aggregate-query「统计用电客户总数」**12.7s**（模板路径）vs 本次 generic **180s**。聚合/计数/TopN 是高频问法，值得做成带模板的场景（参照 distribution-overload 范式），**触发词必须覆盖全变体**：总数/数量/多少/有几个/统计——一并修复措辞敏感。

### P2-5 计时外露（让耗时可见、可归因）
- `_timing`（first_model_stream/first_tool_start/first_answer_token/total，:236-241）已在采集——done 事件加 `timing` 载荷，前端悬停可见分段耗时；
- rubric 评分耗时单独记录（run_event_sink），运营可看自评成本。

### P2-6 grader 用轻模型
`TUPU_RUBRIC_CONNECTION_ID` 机制已存在——给 grader 指一个更轻/更快的连接（grader 只看 transcript 打勾，不需要旗舰模型）。

## 六、一句话回答三个疑问

- **180s 花在哪**：~5 轮 LLM 全量调用（无 prompt 缓存，每轮 ~25s）+ rubric 评分 ~30s（+可能的重写）；SQL 执行本身 <0.1s，可忽略。
- **日志上屏**：answer_draft 被渲染进 ThinkStream 是当前设计行为——设计错了，应直接流进输出区。
- **总结慢/响应慢**：不是模型思考慢（quick 模式无 thinking），是 rubric 评分把 final 事件压住了 + 轮次多。两处 P0 调整（答案直出 + rubric 分档）即可把观感从 180s 死等变成「边生成边看」。
