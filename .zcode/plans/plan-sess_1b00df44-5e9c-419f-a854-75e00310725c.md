## Part A：数据清理（已有完整备份在 backups/20260805/）

### A1. MySQL tupu 库 — 只留项目域

**项目域边界**（保留集）：
- L0 域：`项目域`(2d7b34dd) 及其下 L3/L4 业务活动（成本/状态/预算管理）
- L1 分类：`项目主数据`(ee490880) 及其下 L2 实体（WBS元素/活动物料组件/网络/网络活动/里程碑/项目定义，共6个实体）

**删除范围**（按依赖顺序，先子后父）：
1. `kg_entity_relations` — 删除任一端实体不在项目保留集的关系
2. `kg_entity_api_mappings` / `kg_entity_source_mappings` / `kg_entity_modelings` / `kg_entity_bapi_links` / `kg_entity_concept_links` / `kg_entity_init_data` — 删除非项目实体的映射/建模记录
3. `kg_entities` — 删除 concept_id 不属于"项目主数据"分类下的实体（删 35 个，留 6 个）
4. `kg_source_tables` + `kg_source_fields` — 删除非项目物理表（table_en 不以 `dim_ps`/`dwd_ps` 开头的）
5. `kg_concepts` — 删除客户域(9776ff8d)、电网域(4531bfeb) 及其下 L3/L4；客户(39eb5231)、组织(936cbbf0)、设备(1fa7fd41) 分类及其下 L2
6. `kg_concept_relations` — 删除涉及已删概念的关系

**保留不动**：`kg_skills*`、`kg_doris_config`、`kg_doris_catalog`、`kg_data_source_configs`、`kg_knowledge_base*`、`kg_api_endpoints`、`kg_cypher_templates`、`kg_graph_schema`、`kg_metric*`（指标定义）、`kg_conversation*`、`kg_agent_runs` 等系统/配置表

### A2. PostgreSQL tupu 库 — DROP 非项目表

- 保留：`dim_ps_wbs_cost`（项目成本表，含少量演示数据）
- DROP：其余 116 张表（`dim_cst_*`/`dim_grid_*`/`dwd_cst_*`/`dwd_grid_*`/`dwd_psr_*`/`cms20_*` 等）
- 方式：生成 `DROP TABLE IF EXISTS <表名> CASCADE;` 批量执行（排除 dim_ps_wbs_cost）

### A3. Neo4j — 清空重建项目域

- `MATCH (n) DETACH DELETE n` 清空全库
- 调用后端 `POST /api/v1/sync/neo4j-all` 从清理后的 MySQL 重新同步（只同步项目域）

### A4. Elasticsearch — 不动

ES 12 个索引已全是 `tupu_dim_ps_*`（项目域），无需清理。`ragflow_*` 索引属 RAGFlow 服务，不动。

### A5. Doris — 自动反映

PG 表 DROP 后，Doris `pg_tupu` catalog 查询时动态映射，非项目表自动消失。无需专门清理 catalog。

### A6. LLM 配置 — 保留连接删 key

- `kg_llm_connection_configs` 表：`UPDATE ... SET api_key = '' `（保留 name/model_name/base_url/provider 等连接结构，清空 key 字段）
- 前端 LLMConfigManager 显示连接列表，key 为空需用户填

### A7. 脱敏检查

- 扫描项目域保留数据（项目定义/WBS/网络等）是否含真实人名、电话、地址、组织代码
- 从测试数据看负责人是"张工/李工/王工"占位名，proj_desc 是"某省电力公司110kV输变电工程"等脱敏描述，判断为演示数据
- 如发现真实敏感字段，做脱敏替换

3. **开源准备**：敏感信息清理(B1) → 移除文件(B2) → 补.gitignore(B3) → 新建标配文件(B4)
4. **最终验证**：`git grep` 扫描残留密码/key；确认 .env.infra 未跟踪；确认无调试脚本残留
