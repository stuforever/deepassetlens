# 验收断点修复计划

基于验收报告的 9 项断点，按优先级分 3 批修复。采用推荐方案（用户未回答时按技术判断选择）。

---

## 第一批：P0 安全断点（必须先修）

### P0-1：可信范围链路修复 — 首工具拦截 + 模型声明范围

**问题**：`_update_last_scope` 从模型"范围："文本写 `last_scope`，`_get_trusted_scope` docstring 撒谎说来自用户输入。第一轮 `last_scope=None` 时 scope 检查完全跳过。

**方案**（首工具拦截+模型声明范围）：
1. **decision_gate.py `_update_last_scope`**：保留从模型"范围："行解析逻辑（这是唯一可行的范围来源），但：
   - 修正 `_get_trusted_scope` docstring 诚实描述来源
   - 加 `source: "model_declared"` 标记，审计可区分
2. **decision_gate.py `awrap_tool_call` scope gate**：当 `_trusted is None` 时，**不再跳过**，而是对 scope_gated 工具要求模型必须声明范围（"范围: 无"也算合法声明）。如果决策文本里完全没有"范围:"行 -> 拒绝（格式不全）。这样第一轮也不能无范围执行 SQL。
3. **data_intelligence.py chat_freeplan_stream**：入口加正则尝试从 `user_input` 提取客户名（如"客户001"、"客户003"），提取到则写入 `state.last_scope`（`source: "user_input"`），作为优先于模型声明的可信来源。提取不到不阻塞，靠 P0-1.2 的首工具拦截兜底。
4. **测试**：新增 test_decision_gate 补判场景：首轮无 last_scope + 决策无"范围:"行 -> 拒绝；首轮有 last_scope(user_input) -> 模型"范围:"行不能覆盖它（source 优先级）。

**关键规则**：`source: "user_input"` 的范围不可被 `_update_last_scope` 覆盖（模型不能修改用户指定的范围）。

### P0-2：SQL 安全执行器统一接入 — 堵所有绕过入口

**问题**：4 个绕过点。

**修复**：
1. **kg_api.py `/api/kg/execute_sql`（line 204）**：加 `validate_sql` 校验，与 Agent 工具路径一致。校验失败返回 403。
2. **tupu_deepagent.py `execute_api_sql`（line 924-968）**：regex 改写后（pseudo_sql 替换 + pg. 前缀）**重新校验** `validate_sql(sql_text)`。对齐 `execute_doris_sql` 的"改写后校验"模式。
3. **tupu_deepagent.py 所有 validate_sql 调用**：传 `allowed_tables` 参数（表白名单）。从 Entity 表查允许的物理表名集合，传入校验器。
4. **tupu_deepagent.py execute_sql/execute_doris_sql/execute_api_sql**：加查询超时（SQLAlchemy `with_session_timeout` 或 Doris cursor timeout 30s）。
5. **测试**：test_secure_query_executor 加"改写后注入 DDL"场景；test kg_api execute_sql 端点拒绝非 SELECT。
